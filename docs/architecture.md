# Stargrep architecture

This doc explains how Stargrep is built and why. `docs/product.md` explains what it does. Once code exists, the Drizzle schema and the oRPC contracts are the reference, and this doc only explains the decisions behind them.

## Principles

- **Headless core.** All domain logic lives in `packages/core` as Effect programs. Each program declares the services it needs, such as `Db`, `GitHub`, `TextGeneration`, `Embeddings`, `Queue`, and `BlobStore`. Core has no imports from TanStack Start, Cloudflare, or oRPC. `bun test` runs it with in-memory layers and no network.
- **Effect conventions.** `docs/effect.md` sets how services, layers, errors, schemas, config, tracing, and tests are written. It follows T3 Code's conventions, adapted to Workers and `bun test`.
- **Platforms are layers.** Each service has one production layer, such as `Queue` on Cloudflare Queues, and one in-memory layer for tests. Moving a service to another platform means writing one new layer. Core does not change.
- **Parse at the boundary.** Effect Schema parses GitHub responses, environment config, model output, and API input into domain types. Code inside trusts those types and does not validate again.
- **One schema library.** Every schema in our code is an Effect Schema. Our code never imports zod, even though some dependencies install it. Schemas leave our code in two places, each with one bridge. oRPC takes Effect schemas directly through `@orpc/effect`. `packages/ai` wraps a schema with `Schema.toStandardSchemaV1` and `Schema.toStandardJSONSchemaV1` before passing it to the AI SDK or to a coding-agent CLI.
- **Shared repos, per-user stars.** Each repo is fetched, summarized, and embedded once, however many accounts starred it. An account's stars are rows that point at shared repos.
- **GitHub numeric IDs as keys.** Accounts and repos are keyed by GitHub's numeric IDs. Logins and repo names change on rename.
- **Idempotent pipeline steps.** Every ingestion step converges to the same state when it runs twice. Queues retry, so steps must survive retries.

Production code runs on the Workers runtime, not Bun. Code in `apps/` and every package they import must avoid Bun-only APIs. Bun runs installs, scripts, and tests.

oRPC 2.0 and Alchemy 2.0 are betas, and Drizzle 1.0 is a release candidate. Pin one exact version of each and upgrade on purpose.

`Db` exposes query functions from `packages/db`, each returning an Effect with a typed error. It never exposes the Drizzle database object, so core does not import Drizzle types. Tests use `layerMemory` from `@stargrep/db/memory`, which runs the same migrations and query code on PGlite, Postgres compiled to WASM with pgvector, inside the test process. Transactions are a separate service. A driver change then touches only `packages/db`.

The `Db` service uses `pg` because Hyperdrive documents `pg` and because Better Auth's Drizzle adapter awaits queries, which only the promise-based driver supports. One driver then serves both core and auth. Drizzle's JIT row mapping stays off, because Workers block `new Function`.

TanStack DB owns all client state, so the browser has no Effect atoms or second store. The browser loads Effect only in code-split routes where it does real work, such as the search box, which debounces input, cancels stale requests, and merges local and semantic results with `Stream`. A probe bundle of that code measured about 34 KB gzipped. Public pages such as profiles, collections, and discovery pages load no Effect code. The browser does not decode responses from our own API. The oRPC client takes its types from the contracts through type-only imports.

App code talks to Postgres through Hyperdrive with a standard driver and uses no Neon-only APIs, so moving to another Postgres host is a dump and restore. Development and preview branches scale to zero. Production does not scale to zero, because a woken compute starts with an empty cache and the first vector searches then read from remote storage.

Every stage's database runs in `aws-us-east-1`, and the main Worker and the web Worker have the placement hint `aws:us-east-1`, so Cloudflare runs their `fetch` handlers in the data center nearest that region. A request crosses the distance to the caller once, and its queries stay near the database. Placement moves only `fetch` handlers. Cron triggers, queue consumers, and Durable Objects run where Cloudflare starts them, and the debug Worker has no placement.

## GitHub access

GitHub limits each user token to 5,000 requests per hour. That budget is shared with every other app the user authorized. The Stargrep GitHub App's installation gets its own 5,000 requests and 5,000 GraphQL points an hour, and more only past 20 repositories or 20 organization members. Stargrep stays inside these limits with five sources, cheapest first.

1. **Event archives.** Public star history with account, repo, and time, loaded without API calls. "Event sources" below explains which archive covers which period.
2. **Incremental sync.** A sync reads the star list newest first and stops at the first star it already has, so an unchanged account costs one request. ETags do not help here. Each star list page embeds live repo stats such as `pushed_at`, so its ETag changes when any of its 100 repos changes, even when no star changed.
3. **README object IDs.** GraphQL returns the README's object ID with the repo. Stargrep fetches and summarizes a README again only when that ID changes. An object ID names fixed content, so R2 keeps each README under its ID, and a README already in R2 costs no request.
4. **The user's own token.** Work a signed-in user starts reads GitHub with their token: their own sync, the weekly full sync, an import of another login they start while signed in, and the facts batches and README reads that enrich the repos those syncs bring in. Stargrep takes at most 20% of what remained in each of the user's rate-limit windows when it opened, read from `x-ratelimit-remaining`. The user's gh CLI, IDE, and CI share the same 5,000 requests an hour, and a 3,000-star full sync needs about 33 of them.
5. **The server's token.** Prod reads with the Stargrep GitHub App's installation token, and previews and local stages with a personal token. It pays for signed-out syncs, lookups of accounts that GH Archive does not cover yet, sweeps, crons, icons, and the part of a user's work that falls back from their token. Every signed-out sync first waits its turn in an admission line sized to the token's share, as "Admission" in "API and MCP" explains.

A user's token is used only for work that user started. Stargrep never pools user tokens to crawl other accounts, and never uses one for a sweep or a cron. The token never leaves the server. The main Worker reads it from Better Auth by user ID when a job sends its first GitHub request, and queue messages carry only the user ID.

`packages/github` sends requests one after another per token, as GitHub's best practices ask. This keeps it under the secondary limit of 100 concurrent requests. It also sets the floor for a full sync. The REST star list is the fastest source, at about 1.35 s of GitHub server time per page of 100 and slower on deep pages, so 3,000 stars take about 45 s. GraphQL's `starredRepositories` takes about 2.5 s per page. An in-memory lock cannot do this, because many Worker isolates run at once. Each token gets a Durable Object that sends its requests in order and tracks its remaining budget from the response headers.

## Event sources

No single public source has every star.

- **GH Archive** is complete until 2025-05-24. It holds about 554 million star events, according to ClickHouse's full copy. After that date its collector captures a shrinking share, about 1% of stars by late 2026, and since September 2026 it has no push events. From 2015 on, star and fork events carry numeric account and repo IDs. Events from 2012 to 2014 carry logins only and need ID resolution.
- **The OpenDigger mirror** uses the same file format from 2026-09-06 and captures roughly 90 to 98% of stars, measured against GH Archive and the API. An hourly file is about 415 MB gzipped with about 650,000 events. Stargrep treats it as a best-effort input, not a dependency.
- **The GitHub API** gives an account's full star list with `starred_at` through `users/{login}/starred`. A repo's stargazer list is closed: `repos/{owner}/{repo}/stargazers` returns 404, and GraphQL returns only `stargazerCount`. So stars can be rebuilt one account at a time, never one repo at a time.

Between 2025-05-24 and 2026-09-05 no archive is complete. Per-account sync fills that window for the accounts Stargrep serves. Metrics that depend on that window are marked incomplete instead of showing a false dip.

Full star history lives in R2 as Parquet, about 5 GB for all of it. Postgres `stars` holds only the accounts and repos Stargrep serves. Holding all of it in Postgres would take 64 to 74 GB, mostly rows nobody reads.

Since October 2025 push events carry no commit list or count, so commit metrics come from the GraphQL commit history count of each tracked repo, fetched daily in batches. Merged pull requests are counted from both `action: merged` and `action: closed` with `merged: true`, because the payload changed in 2025.

## Ingestion pipeline

Each step is a queue message type. Each consumer is idempotent.

1. `sync-stars` fetches an account's star list newest first. It stops at the first star older than a star the last completed sync saw unchanged, so it reads every star that shares that star's `starred_at`. An account's first sync has no stop line, so it reads every star. After that, the owner's `viewer` call asks for a full sync once the last full read is a week old. For 3,000 stars that is about 33 GitHub requests a week: the account lookup, two GraphQL counts, and 30 pages. Stars that are gone mark `unstarred_at`. The list pages by offset, so a full read counts the stars through GraphQL before and after. When the counts differ, the read shifted, and the sync writes what it read but skips the unstars and does not record the run. A star added and another removed at different page boundaries during one read leave the counts equal, so that read can hide one star until the next full sync. An org cannot star repos, so its count is zero without a GraphQL request. A finished sync only moves the account's sync time forward, so an older run that finishes last cannot pull the stop line back. It enqueues the repos that need enrichment after it reads the last page, because enrichment shares the token's one request at a time and would otherwise hold it between the sync's pages.
2. `enrich-repo` runs for repos that are new or whose README object ID changed. It stores the README in R2, writes the summary, keywords, and kind, and computes the embedding. It also fetches the facts events do not carry, such as license and homepage.
3. `import-events` is an hourly cron. It streams the hour's archive file, keeps star, fork, pull request, issue, and release events, writes them to R2 as Parquet, and loads new stars for served accounts into `stars`. A streaming parse of a full OpenDigger hour measured under 15 MB of heap and about 12 seconds of CPU, inside a Worker's 128 MB and the 15-minute limit for hourly crons. Writing Parquet needs a JavaScript Parquet writer in the Worker or a hand-off to a container.
4. `snapshot-repos` is a daily cron. It fetches facts events no longer carry, such as the commit history count, for tracked repos through batched GraphQL queries.
5. `rollup-metrics` is a daily job. It turns events and snapshots into weekly series per repo and writes current values and changes into `repo_metrics`. DuckDB does not run in Workers, so the rollup runs in a container or a scheduled CI job.

Bulk enrichment, such as a backfill of popular repos, uses the Gateway batch API for summaries and `embedMany` for embeddings. The batch path serves the CLI and backfills only, because a batch job can take minutes to hours.

`apps/worker` runs steps 1 and 2 as queue consumers. `src/queues.ts` declares each queue, its dead-letter queue, and its consumer settings.

- A consumer decodes each message, calls one service method, and settles the message. Success acks it. `afterFailure` in `src/consumers/settle.ts` maps every failure tag to one settlement, and a new tag fails typecheck until it has a row.
- A failure that can pass on a second try, such as a lost database connection, a deadlock, a GitHub 5xx, a GitHub 403 that names no rate limit, or a model timeout, retries up to five times a minute apart, and then Cloudflare moves the message to the dead-letter queue. An enrichment failure that counts against the repo instead starts its backoff, so those retries settle as `Backoff` and the sweep owns the next try. A failure that cannot, such as a missing token or key, an unknown account, or a body that does not decode, goes to the dead-letter queue on its first attempt. A failure while the runtime layers build, such as a lost database connection or an embedding model conflict, fails the whole batch before any message is settled, and Alchemy retries every message in it.
- A spent token budget or a GitHub rate limit is not a failure. GitHub names the time the limit lifts, or asks for a minute when a secondary rate limit names no time, so the consumer sends the message again with that delay and acks the original. A long pause then spends none of the five retries.
- The `enrich-repo` consumer takes up to 100 messages per batch and runs one batch at a time. The Worker's text-generation layer has no batch API, so `enrichRepos` answers each repo with its own model call, and it reads each repo id once. A repo several accounts starred arrives once per account, and a later batch finds it enriched.
- GitHub answers each repo in a facts batch on its own. A repo it does not return, or reports as `FORBIDDEN`, settles as gone, and the rest of the batch enriches. The client logs the node IDs of forbidden repos. Any other GraphQL error fails the whole batch.
- A repo is read once it has a summary of its current README and an embedding, which is `pendingEnrichment` in `packages/db/src/schema.ts`, negated. `EnrichRepo` counts a repo's own failures when each batch chunk finishes: gone or forbidden, no node ID, a README GitHub no longer serves, a 4xx other than 403 on its README, or model answers that do not decode. A failure every repo would hit, such as a missing token or key, an outage, a rate limit, or a batch that aborts, never counts. Each counted failure adds one to `enrich_failures` and sets `enrich_retry_at` from `retryDelays` in `packages/core/src/repos/enrich-retry.ts`. A failure before the retry time has passed is a copy of one already counted and changes nothing. Saving the embedding sets both back. A pending repo with `enrichFailureCap` failures, 3, counts as failed, so a library's progress can reach its end.
- An incremental sync lists only new stars, so it never sends a pending repo again. A cron in `apps/worker/src/crons.ts` runs `EnrichRetry.sweep` every 10 minutes instead, with a 5-minute timeout. It sends at most 100 pending repos under the cap whose retry time has passed, the earliest first and then repos that never failed, such as one whose message was lost. A repo waits 10 minutes after its first failure and an hour after its second, so a repo GitHub forbids costs at most three lookups, each one node in a batched GraphQL request. A message that reaches a repo before its retry time, such as a queue retry of a counted failure or a second sweep send, settles as `Backoff` with no GitHub call. A partial index holds only pending repos under the cap, so capped repos never slow the sweep. A full sync or another account's first sync still sends a capped repo again.
- Each dead-letter queue has a consumer that logs the message ID, its attempts, and the IDs in its body, or only the body's type when the body does not decode. An enrich dead letter changes no failure count, because only `EnrichRepo` knows whether a failure was the repo's own.

The `GitHubGate` Durable Object holds the Worker's GitHub credential. Every GitHub request on the server's token from every isolate goes through it, so it sends them one at a time. It keeps the rate-limit windows GitHub reported in its storage and takes its share of each window from `GITHUB_BUDGET_SHARE`, so a restart keeps the windows and a new share applies at once. `STARGREP_GITHUB_SERVER_TOKEN` picks the credential: `app`, the default of the prod deploy, or `pat`, a personal token in `STARGREP_GITHUB_TOKEN` and the default everywhere else. Each Worker binds the kind it deployed with, and reads only that kind's credential. The share follows the token: 0.9 on the App, whose budget no one else spends, and 0.5 on a personal token, whose owner keeps half for their own tools. A preview stage may set another number above 0 and at most 1, and a `prod` deploy fails with any share but its token's. Requests and replies cross the RPC boundary as plain data, and the credential never leaves the object. A pull request stage may deploy without a token. It then binds no `GitHubGate`, and every GitHub call fails with `GitHubTokenMissing`.

The gate takes a `TokenSource` and reads its token once a request holds the gate, so a request that waited never sends one that expired meanwhile. A personal or user token is fixed. On the App, `AppToken.makeInstallationTokens` in `packages/github/src/app-token.ts` signs an RS256 JWT with WebCrypto and the App's client ID, finds the installation on the account that owns the App with `GET /app` and `GET /users/{owner}/installation`, and mints an hour's token with `POST /app/installations/{id}/access_tokens`. Installs on other accounts never change it. GitHub hands out the key as PKCS#1, which WebCrypto cannot import, so `app-jwt.ts` wraps it in PKCS#8. The token lives in memory only, and one state decides each request: use the held token, use it and start one refresh in the background in its last five minutes, wait while GitHub said to, or mint. The background refresh runs in a scope the object owns, and a request mints in the foreground only when no token has a minute left, so a slow or failing refresh delays no request. A 401 drops the held token and sends the request once more with a new one, because GitHub revokes an installation's tokens when its App is installed again, and a 404 for the known installation looks it up again. A rate limit on the App's endpoints defers the message until the time GitHub names, and no mint goes out before then. A refusal, such as a revoked key or a suspended App, fails the call with `GitHubTokenMissing` and logs the reason. `packages/github/src/rate-limit.ts` decides what counts as a rate limit, for the GitHub client, the fallback from a user's token, and the mint alike: `retry-after`, else the window's reset when nothing remains, else a minute.

A job a signed-in user started carries their user ID in its message: `userId` on `sync-stars` and on the `enrich-repo` messages that sync sends. `UserGates` in `apps/worker/src/user-gate.ts` gives the job a gate that reads the user's token once, through `GitHubTokens` in `packages/auth/src/tokens.ts`, and sends each request to the `UserGitHubGate` Durable Object named by that user ID. GitHub counts all of a user's tokens against one budget, so one object per user keeps their requests in order and their windows in storage, with `FallbackGate.userShare`, 0.2, as the share. The token comes with each call and is never stored. `FallbackGate.prefer` sends the job through the user's gate until the first of four reasons, then through `GitHubGate` for the rest of the job:

- `budget`: the user's share of the window is spent.
- `unauthorized`: GitHub answered 401, because the token expired or the user revoked the app.
- `rate-limited`: GitHub answered 403 or 429, or a GraphQL 200 whose errors name `RATE_LIMITED`, with nothing remaining, because the user's own tools spent the window.
- `token-unavailable`: Better Auth gave no token: the user has no GitHub account, GitHub refused the refresh, or the read took more than 10 seconds.

The first move logs once, as a warning for every reason but `budget`, and counts `stargrep_github_fallbacks` by reason. A secondary rate limit leaves quota, so the client waits it out on the user's token. `GitHubTokens` builds a Better Auth with only the GitHub provider and token encryption, on one connection it closes before the read returns. Alchemy evaluates a Worker's props again each time the Worker starts, against that Worker's own bindings, so `tokenClientBindings` reads every value as optional and gives the same bindings at deploy and at start. Better Auth refreshes a token within five seconds of its expiry with the app's client secret and stores the new one encrypted. GitHub refuses a used or revoked refresh token with a 200 that names an error. Better Auth would then write back the refresh token it read, over the one a concurrent refresh just stored, so `githubProvider` in `packages/auth/src/auth.ts` fails a refresh that returns no access token before Better Auth writes anything. Jobs of one user in one invocation also share one token read, so they never refresh the same token twice. Previews sign in through prod and bind no client secret, so a preview's expired token falls back instead of refreshing.

The `sync-stars` consumer runs the messages of a batch at once, so a user's sync never waits behind syncs on the server's token. The `enrich-repo` consumer groups a batch by `userId` and enriches each group over its own gate, so a group that aborts fails only its own messages.

## Search

Every search is hybrid. Full-text search and vector search run in one SQL query, and reciprocal rank fusion merges the two lists. Full text matches the words the user typed. The vector side embeds the planner's description of a matching repo, or the query itself when the planner is skipped. It keeps only repos within the embedding model's `maxMatchDistance` of the query, a cosine distance of 0.36 for `voyage/voyage-4` in `packages/ai/src/models.ts`, before the lists merge. Search reads the value from the model it runs, so the fake hash model in tests uses its own. Every query has nearest neighbors, so without that floor gibberish such as "dfsfgdsrg" came back with 20 results. `docs/evals.md` calibrates the floor. A repo whose name or `owner/name` equals a keyword query ranks first.

- **Your stars.** The candidate set is one account's stars, at most tens of thousands of rows. An exact vector scan over that set takes milliseconds, so this path uses no vector index.
- **Network.** The candidate set is the union of the stars of the accounts you follow. Results also rank by how many of those accounts starred each repo.
- **Global.** An HNSW index on `repos.embedding`. Filtered queries use pgvector's iterative index scans.

### Query plans

A query such as "open source apps like Wispr Flow with growing contributors" needs filters and a ranking, not only text matching. The planner turns each natural-language query into a typed `QueryPlan`.

- **Scope.** Your stars, your network, or everything. The caller sets it, never the model, so a plan cannot widen a search. Only your stars runs in the first milestone. The other scopes fail with `SearchScopeUnavailable`.
- **Semantic text.** The text to embed. "Like Wispr Flow" becomes a description of what Wispr Flow does, because the product has no repo to compare against.
- **Filters.** Kind, license, language, archived, starred date, and bounds on any metric. A bound is strict or inclusive, so "more than 200 stars" leaves out a repo with exactly 200. A language filter matches a repo written in that language or tagged with it as a topic, because a Python package manager is often written in Rust. A JavaScript filter also matches TypeScript.
- **Ranking.** Relevance alone, or the best matches reordered by a metric such as 90-day contributor growth. A metric never lifts a repo that did not match into the results.

The planner is `anthropic/claude-haiku-5.5` with structured output and reasoning turned off. With reasoning on, a plan took 2.1 to 4.6 seconds from a laptop, and with it off 1.2 to 2.1 seconds. It chooses metrics from a registry in `packages/core/src/search/metric-registry.ts`. Each entry holds an ID, the description the model reads, and a family and variant, such as stars and 90-day growth, that `packages/db` turns into SQL over `repo_metrics`. The model never writes SQL. The plan is parsed at the boundary, and a plan that names an unknown metric is rejected. When the planner fails or returns a plan that does not parse, search runs the query as typed.

The planner sets only the filters a query states, and code holds it to that after decoding. A kind filter stays only when the query restricts the kind with a word such as "only" or "not". The model returns each language with the words from the query that named it, such as Python with "питоне". A language stays only when those words appear in the query and are the language's name, one of its aliases, or a word in a non-Latin script, such as "питоне" or "パイソン". In Chinese, Japanese, and Thai, which have no spaces between words, the words match anywhere in the text. So a language named in any script stays, and one quoted from a framework, such as Java from "spring boot", is dropped. A quote in a non-Latin script is trusted as naming the language, so a transliterated framework name, such as "लारावेल" for Laravel, can still keep a language filter. `packages/core/src/search/vocabulary.ts` holds the languages and their topic names and the words that send a query to the planner. In the recall eval, filters the model inferred dropped relevant repos, such as Rich for "python framework for text user interfaces", because the summarizer called it a library. `docs/evals.md` has the numbers.

Each result shows the values that ranked it, such as "+38% contributors in 90 days".

`QueryPlanner.plan` and `QueryPlanner.planWithModel` set `search.plan.source` on their spans to `keyword`, `cache`, `model`, or `fallback`. `Search` counts each search once in `stargrep_search_plans`, under the source of the plan it ran, so a keyword search that needed the planner counts as `model` or `cache`. A fallback also sets `search.plan.failure` to the error tag, such as `AiTimeout`, so traces show how often Haiku's tail latency sends a search to the typed text.

A repo name, an `owner/name`, or two plain words skip the planner. When such a query matches no name, no word, and no repo within that distance, search plans it with the model and runs that plan, which is how a misspelled name such as "zustnad" still finds `pmndrs/zustand`. Gibberish costs that one planner call and still finds nothing. Words that still match as a prefix of a word in the account's stars skip that call, because they are most likely a word the user is still typing, such as "zust" on the way to "zustand". The web client searches as the user types, and on the eval corpus the prefixes of 28 typed queries would call the planner 151 times without that rule and 34 times with it, 24 of them for typos. When the planner fails, search answers with nothing instead of running the same words again. A query with a word that can name a filter, such as a language, a kind, a license, "only", "more", or a number, goes to the planner, so "only MIT libraries" keeps its filters. The `SearchCache` port caches plans and query embeddings under a SHA-256 of the normalized query text. Each entry records when it expires, 30 days after it was written, so an old entry is a miss on every backend. A corrupt entry is a miss too. A plan with a date filter is reused only on the day it was planned, because "starred last year" depends on today. Tests use the memory layer. The web Worker keeps entries in a KV namespace and sets each one's KV expiration from its TTL, at least the 60 seconds KV accepts.

## AI providers

`packages/ai` has two ports, because they have different providers. Production summarizes with `anthropic/claude-haiku-5.5` and embeds with `voyage/voyage-4` at 1,024 dimensions. `docs/evals.md` records the bakeoff that chose them. The query planner uses `anthropic/claude-haiku-5.5` with reasoning off through its own `TextGeneration` layer, `layerPlannerTextGeneration`, with a 4-second timeout and no retries. `TextGeneration` turns a prompt into a value of an Effect Schema, for summaries, query plans, and later reranking. `Embeddings` turns texts into vectors. Core code imports only the ports.

| Port | Adapters | Where it runs |
|---|---|---|
| `TextGeneration` | AI Gateway, Claude Code CLI, fake | Gateway everywhere. Claude Code and the fake only on a developer's machine |
| `Embeddings` | AI Gateway, fake | Gateway everywhere. The fake only on a developer's machine |

An adapter only sends the request and returns the raw output and token counts. The port's `make` does the rest for every adapter: it applies the adapter's timeout, decodes the output with the request's Effect Schema, counts tokens in `stargrep_ai_tokens`, and opens the span. So every adapter fails with the same typed errors: `AiOutputInvalid`, `AiRequestFailed`, `AiUnavailable`, `AiTimeout`, and `AiModelNotFound`. `AiUnavailable` is a failure the provider marks as worth a retry, such as a rate limit or a 5xx. The port never retries. The Gateway adapter lets the AI SDK retry each provider request three times, so `embedMany` retries only the request that failed. The SDK waits as long as the provider's `retry-after` asks when that is under a minute, and backs off exponentially from two seconds otherwise. The port's timeout covers the whole call, retries included, and a call that spends it fails with `AiTimeout`. No caller retries a model call again. Gateway batch API calls have no SDK retries, so the adapter retries those itself. Error fields hold short facts such as an exit code or an HTTP status, never a prompt, README text, model output, or key.

`TextGeneration.generateBatch` answers many prompts with one schema and returns one result per prompt, so one bad answer fails only its own repo. The gateway adapter submits one AI Gateway batch job through the AI SDK's experimental batch API, which accepts text requests only. The job's idempotency key is a hash of the requests, so a run that stops while it waits finds the same job again instead of paying for a second one. A replayed job returns its stored failures too, so a failed item gets one direct call. Adapters without a batch API, and a batch of one prompt, answer each prompt with its own call.

Deployed code uses the layers from `@stargrep/ai/gateway`. `layer` serves both ports with the models in `models.ts` and reads `AI_GATEWAY_API_KEY` through `layerProviderConfig`. `layerModels` serves both ports with a given provider and options. Each Worker reads the key once and passes it to `layerModelsForKey`, the main Worker's summaries and embeddings with no batch API, or `layerSearchForKey`, the web Worker's planner and embeddings. Without a key, or with an empty one, as on a local stage, both serve the ports with calls that fail with `AiKeyMissing`. Local tools use `layer` from `@stargrep/ai/local` instead. It reads `AI_TEXT_PROVIDER` (`gateway`, `claude-code`, or `fake`) and `AI_EMBEDDINGS_PROVIDER` (`gateway` or `fake`), both `gateway` by default, and needs Bun to spawn the CLI.

**The Claude Code CLI is for local development only.** It runs `claude -p` with the developer's own subscription, for experiments, small eval runs, and summary samples. Anthropic's terms let a person use the unmodified Claude Code binary with their own subscription, but products and pipelines must use API keys. So deployed stages, CI, and bulk backfills always use the AI Gateway. Four checks enforce this.

| Check | What it stops |
|---|---|
| The `@stargrep/ai` exports map has no `./claude-code` entry | Code outside the package cannot build the harness without `@stargrep/ai/local` |
| `@stargrep/ai/local` fails with `AiProviderNotAllowed` at startup unless `STARGREP_MODE=local` and `CI` is unset | A local tool run in CI, or with the wrong environment, cannot reach the harness or the fakes |
| The Biome rule `packages/config/no-local-ai-import.grit` | Code in `apps/`, except tests, cannot import `@stargrep/ai/local`, `@stargrep/ai/fake`, `@stargrep/ai/summarize.fake`, or `@stargrep/ai/claude-code` |
| The gateway layer's type does not require `ChildProcessSpawner` | A Worker that uses it never needs a process spawner, so typecheck catches a Worker wired to the local layer |

**Embeddings from different models cannot be compared.** Each database has one embedding model and size. The one-row `embedding_settings` table records them, and a migration creates it. When the `Db` layer starts, it reads that row. In a fresh database it writes the configured model once, and when the configured model or size differs from the stored one, the layer fails with `EmbeddingModelConflict` before any query runs. Reading the row costs one query per `Db` build. The Worker builds `Db` per request, because a Hyperdrive socket opened in one request cannot serve another, and passes a `Ref` it keeps for the isolate's lifetime. So only an isolate's first request reads the row. So a local run configured with fake or foreign embeddings can never write into a database that production reads. Every embedding carries the ID of the model that made it, every `repos` row stores it in `embedding_model`, and `saveEmbedding` refuses a vector from any model other than the stored one with `EmbeddingModelMismatch`. No `Db` function changes the stored model. To switch models on purpose, write a migration that clears `embedding` and `embedding_model` on every repo and updates `embedding_settings`, then re-embed every repo with the new model.

## Sign-in

People sign in with GitHub through a GitHub App, whose manifest is `.github/app-manifest.json`. `packages/auth` configures Better Auth on `pg` and `drizzle-orm/node-postgres`, the same driver as `Db`, with its own pool for each request that connects only when a query runs. Better Auth serves `/auth/*`, because `/api/*` is the REST API. The session cookie carries a five-minute cache of the session, so most API calls read no session row. Linking a GitHub account reads the session row, so a cookie copied before sign-out cannot start a link. Better Auth stores the user's GitHub token encrypted. The main Worker binds the same `BETTER_AUTH_SECRET` and the app's client ID and secret, so it can read and refresh that token for the user's own work, as "GitHub access" explains.

A new session imports the GitHub account with the user's own token: `GET /user` for the login and profile, and one GraphQL call for the number of repos the account starred. It claims the `github_accounts` row for the user and queues a sync. If that import fails, the first `viewer` or `library` call runs it again. Each `viewer` call also asks for a sync as the account's owner, so a star made on GitHub shows up when the user opens the search page. The page reads `syncStatus` only after `viewer` answers, so its first read already sees that sync as `queued`. The sync page compares the library's size with the starred count to show progress.

A GitHub App cannot match callback URLs by wildcard, and each preview stage has its own workers.dev host. So previews sign in through prod with Better Auth's `oAuthProxy` plugin. The preview sends GitHub's redirect to prod's callback and packs its own state, PKCE verifier included, into GitHub's `state`, encrypted with `AUTH_PROXY_SECRET`. Prod exchanges the code and redirects to the preview with the profile and tokens encrypted for 60 seconds. The preview creates the user and session in its own database. Prod creates neither. `AUTH_PROXY_ORIGIN` decides: unset, a stage signs in directly with the client secret, and set, a stage proxies through that origin and never reads the client secret.

Any branch's workflow can read the `preview` environment, so the design assumes the proxy secret leaks. Two guards on prod keep that leak inside preview databases. Prod installs the plugin without its endpoints and keeps only the hooks that forward a preview's sign-in, so prod has no route that turns a profile encrypted with the proxy secret into a session, under any provider ID. Prod forwards a sign-in only to its own origin or to a preview Worker of this account, so a forged state cannot send a user's GitHub token to another host.

## Client

The web app loads the signed-in user's whole library into a TanStack DB collection, one snapshot per load. For 3,000 stars that is about 200 KB compressed. Filtering, sorting, and keyword search then run in the browser on each keystroke, through a live query that matches every word of the query. Semantic results come from the server through an Effect `Stream` that waits for typing to pause and interrupts the request for a query typed over. They append after the keyword results, so no tile the user can see moves. While a sync runs, the page reloads the library every two seconds. Each library repo carries `read`, which says whether search by meaning can find it yet. To keep those flags fresh, a client polls `syncStatus` every few seconds while `state` is `queued` or `enrichment.read + enrichment.failed < enrichment.total`, and reloads the library when `enrichment.read` changes. The total is 0 until the sync writes stars, so the `state` check keeps the poll going. Each poll runs two small reads and one aggregate over the account's stars, at the same time.

The home page starts with light landing chunks, then hydration immediately loads the stars engine. `bun run --cwd apps/web budget` enforces two named gzip budgets in `bun run check` and CI. The landing budget covers the entry, index route, and their static dependencies. It allows 130,000 bytes and forbids Effect, TanStack DB, skullet, and oRPC. The engine budget covers `src/components/stars.tsx` and all its static dependencies, including shared landing chunks, once each. It allows 355,000 bytes. The baseline was 335,125 bytes, leaving about 6% headroom. These are sums of each emitted JS chunk compressed with gzip level 9, excluding CSS and source maps.

## API and MCP

`packages/api` defines the oRPC contract, one router that implements it, the wire errors, and one instrumentation middleware. `apps/web` is a TanStack Start app on Workers, and `src/server.ts` serves the router three ways before TanStack Start sees the request.

- `/rpc` serves the typed oRPC client.
- `/api` serves REST, and `/openapi.json` is the OpenAPI document generated from the contract.
- `/mcp` serves every procedure as an MCP tool over Streamable HTTP, named by its `operationId`.

The procedures are `search`, `triggerSync`, `syncStatus`, `getRepo`, `stars`, `config`, `viewer`, and `library`. The first six are public. `config` returns the demo account, `STARGREP_DEMO_LOGIN` or `stefanofa` by default in `packages/api/src/public-config.ts`, with its default query and example queries. It builds no database or model service. `stars` returns a login's synced stars newest first, up to 1,000 a page, ordered by `starred_at` and repo ID so a cursor of the last row's time and ID continues the page. The cursor decodes during input validation, so one Stargrep never issued answers `BAD_REQUEST` with its issues. It answers `ACCOUNT_NOT_SYNCED` when the login has no `github_accounts` row. `viewer` and `library` read the session cookie and answer `UNAUTHORIZED` without one, so they stay out of the MCP tool list and the OpenAPI document until MCP clients can sign in.

- **Errors.** Every outcome other than success is a tagged error, such as `AccountNotSynced` from search, `RepoNotFound` from `Db`, or `RateLimited` from the rate limiter. The router catches once per procedure and maps each tag to a wire error through one table, so a new tag fails typecheck until it has a row. A wire error has a stable `code`, such as `ACCOUNT_NOT_SYNCED` or `SERVICE_UNAVAILABLE`, a fixed message, and the call's `traceId` in `data`. `packages/api/src/errors.ts` holds each code's status and message. A failure outside the table becomes `INTERNAL_SERVER_ERROR` with the trace ID and no detail. oRPC decodes a request body before any middleware runs, so the web Worker's handler interceptor gives a body it cannot decode `BAD_REQUEST` with the request's trace ID, and MCP's own JSON-RPC errors, such as a parse error, carry it in `error.data`. Every API response, the OpenAPI document included, also has an `x-trace-id` header. A path under `/api`, `/rpc`, or `/mcp` that matches no procedure answers `NOT_FOUND` in that transport's error shape with the trace ID, and a failure outside the API answers `INTERNAL_SERVER_ERROR` the same way.
- **Services per request.** A Hyperdrive socket cannot outlive its request, so the web Worker builds `Db`, search, and sync services for each request, and only once a procedure has validated its input. A database outage then fails a search with `SERVICE_UNAVAILABLE`, while validation, the tool list, and the OpenAPI document keep working.
- **Tracing.** The middleware opens `Api.<procedure>` under the request's `Web.<transport>` span and sets `api.transport` and `stargrep.trace_id`. No span holds the query, the plan, or results. Cloudflare's own request span and invocation log record the full URL, so search takes its query in a POST body. Each response carries a `Server-Timing` header with the handler's total time and the procedure's time, so a stage measures transport overhead apart from the work.
- **Sync.** `triggerSync` and the signed-in owner's `viewer` call claim the login's row in `sync_requests` and queue a `sync-stars` message only when the claim wins. The claim is one `insert … on conflict do update … where` statement, which takes the row only when the login has no request or its request is at least one cooldown old, so of many triggers at once exactly one queues a job. `SyncRequests` sets the cooldown per requester. Anyone waits 10 minutes, and the owner waits 1 minute, so the owner's page loads queue at most one sync a minute and a trigger from anyone still waits 10 minutes after the owner's. While a request is queued, everyone waits 10 minutes for it, because its sync may still be reading pages and an account's first sync has no stop line. The owner's minute counts from the last finished or failed sync. A login synced inside the cooldown is not queued again either, and a request older than a day is forgotten. The owner's request is a full sync when the account's last full read is a week old and no request is queued, because only a full read finds unstars. A request still waiting in line has not started reading, so it does not hold back a full read that is due. Every other request is incremental. An incremental sync of an account that has synced before and has no new stars costs two GitHub requests, the account lookup and the first star page. An account that has never synced has no stop line, so its first sync reads every star whatever the mode. A `viewer` call whose sync fails to queue still answers and logs a warning. When the queue refuses the message, or the main Worker dead-letters it, the row is marked `failed`. The message carries its request time, and a dead letter marks the row only while the row still holds that request, so a late dead letter never fails a newer claim. An hourly cron in the main Worker deletes requests older than a day, so the table holds about a day of logins. `syncStatus` reads the row and the account's star sync time and says `queued`, `failed`, `done`, or `unknown`. Both procedures also return `enrichment`, the login's current stars counted as `total`, `read`, and `failed`. The router reads it by login in one query over `stars` joined to `repos`, beside the sync status. Repos are shared, so `read` can start above zero. Right after `triggerSync` the total is 0, and reading goes on after `state` leaves `queued`, so reading is finished only when `state` is not `queued` and `read + failed == total`.
- **Login check.** A signed-out request asks GitHub about the login before it claims it, with one GraphQL `repositoryOwner` request. The answer says whether the login exists, whether it is a user or an org, the account's facts, and its starred total. The web Worker has no GitHub token and no `GitHubGate` binding, so it calls `lookupOwner`, an RPC method on the main Worker's default export that the internet cannot reach, and gives up after 5 seconds. The lookup writes the account's facts and `starred_count`, and a first or full sync writes the total it counts too. `syncStatus` returns that total as `starredTotal`, so the page can show 640 of 2,431. A login GitHub does not have claims its row as `missing`, and `triggerSync` answers `LOGIN_NOT_FOUND` from that row without asking GitHub again until the 10-minute cooldown passes. An org cannot star repos, so its claim records an empty sync, starts at once, and answers `done` with a total of 0. Owners skip the lookup, because sign-in already read their account. "Admission" below gives the order of the steps.
- **Renamed logins.** GitHub lets a user rename their login, and Stargrep deletes nothing when one does. An account synced under the old login keeps answering `done` from `syncStatus` and keeps serving `stars/{old}`, because both read the account row. A trigger of the old login looks it up, finds no owner, and answers `LOGIN_NOT_FOUND`. A trigger of the new login upserts the account by its GitHub ID, which moves the row to the new login, so `stars/{new}` serves the stars and `stars/{old}` stops answering.
- **Admission.** Every sync a signed-out caller starts spends GitHub requests from the main Worker's token, so it first takes a turn in a rate line in Postgres, as "Admission" below explains. A signed-in caller's sync runs on their own token and takes no turn. `triggerSync` reads only the session for this, so a session it cannot read imports as a signed-out request.
- **Limits.** Each request works out its network once. A network is an IPv4 address, or the /64 of an IPv6 address, because one subscriber usually holds a whole /64. An IPv4-mapped IPv6 address counts as its IPv4 address, and a request without `cf-connecting-ip` is local and shares the network `unknown`. `Caller` carries the address and its key, the first 32 hex characters of an HMAC-SHA256 of the address under the stage's random `CALLER_KEY`. The address keys only the Workers rate limit bindings and is never stored or logged. Rows in Postgres hold the key.

  Four limits are exact, because they live in Postgres and hold across every Cloudflare location. The per-login claim above. The admission line. Each network's own line, the `caller/<key>` row of `rate_lines`, counted in GitHub units as "Admission" describes. And the model allowance. Every planner call and every query embedding that misses its cache takes one reservation in the network's `model/<key>` line, 30 calls a minute with a burst of 30, then one in `model/all`, 6,000 calls an hour with a burst of 600. Each reservation is one atomic upsert, so concurrent calls never share a slot. The network's line goes first, so a network past its own limit spends nothing from everyone's. A refused plan falls back to the words as typed and sets `search.plan.failure` to `ModelCallRefused`. A refused query embedding runs the typed words on full text alone and reports `fallback` too. Either way the search still answers. A meter that cannot be read refuses the call the same way, because a refusal costs only quality. `stargrep_model_calls_refused` counts refusals by call and by line, never by network. An hourly cron deletes the lines the clock has passed, because a passed line reserves the same as no row, so the table holds only the networks that asked for something recently.

  The Workers rate limit bindings are a cheap layer that turns away most of a burst before it costs anything. One `RateLimiter` service holds them: `SYNC_PER_CALLER` allows 5 syncs a minute per network and `SYNC_OVERALL` 60 for everyone, `SEARCH_PER_CALLER` 120 searches a minute per network, and `STARS_PER_CALLER` 60 pages of stars a minute per network. `search` and `stars` take theirs only when the answer cache misses. Cloudflare counts each binding per location and only approximately. In a burst test on a preview stage, 350 searches from one network got through in about 30 seconds, so these are not caps. Past a binding, the procedure answers `TOO_MANY_REQUESTS`, and a binding that fails answers `SERVICE_UNAVAILABLE`.

  In front of the Workers, prod's zone has one rate limiting rule, so most of a flood never reaches a Worker. `apps/worker/src/domain.ts` declares it, and only the `prod` stage deploys it, because previews have no zone. It counts requests to `/api`, `/rpc`, `/mcp`, and `/auth` and everything under them, per IP and Cloudflare location. Past 150 requests in 10 seconds, Cloudflare answers 429 itself for the next 10 seconds. Pages, assets, and `/icons` never count. The zone is on the Free plan, which allows one rule, a 10 second period and block, IP counting only, and path matching without regular expressions. One tab on a preview stage made about 8 limited requests per 10 seconds while importing 805 stars, and 34 in its busiest 10 seconds while typing a query at 300 ms a key during the import. That pace is just slower than the 250 ms search debounce, so every key sends a search. So 150 leaves room for a few such tabs behind one address. The deploy owns the zone's whole `http_ratelimit` phase, and Alchemy adopts the zone itself without changing it and keeps it on destroy.

`@orpc/mcp` registers tools and does no auth. The MCP SDK checks bearer tokens with a verifier the app supplies, serves protected resource metadata, and answers with the `WWW-Authenticate` challenge, but it is not an authorization server. So MCP sign-in needs Better Auth's OAuth provider plugin as the authorization server, and `/mcp` verifies the token and passes `authInfo` to the MCP handler.

### Admission

`SyncRequests` in `packages/core/src/stars/sync-requests.ts` admits every sync. A unit is one GitHub request.

#### The order of a signed-out request

1. It reads the login's row and the account. A sync that finished inside the 10-minute cooldown, or a request made inside it, answers its status. A `missing` row inside it answers `LOGIN_NOT_FOUND`.
2. It reads the wait of the `all` line. A turn more than 2 hours away answers `SYNC_BUSY`, before the request costs its network anything.
3. It reserves 1 unit on its network's line, then looks the login up. A lookup GitHub refuses for a spent budget answers `SYNC_BUSY`. A lookup GitHub answered pays 1 unit into the `all` line, forced, because the request is spent whatever comes of the sync.
4. It claims the row with the outcome already known. A missing login claims `missing`. An org claims and records an empty sync. A user claims `claimed`, takes its turn in the `all` line, sends its message, and moves the row to `pending` with `starts_at`. A turn the `all` line refuses releases the claim and answers `SYNC_BUSY`.

A request that loses the claim answers from the winner's row, so every trigger for a missing login answers `LOGIN_NOT_FOUND`. No request waits on another's lookup. Requests for one login at once each pay a lookup, and the network's line bounds that cost. A `claimed` row reads as `queued`, because its message goes out next. One narrow window answers `queued` with no job behind it: a trigger that reads a claim whose turn the `all` line then refuses. The request checked the line's wait just before its claim, so a refusal there means the line filled within that moment. The message goes out before the row moves to `pending`, so a crash in between leaves a `claimed` row that reads as `queued` while its job waits in the queue.

The owner skips the lookup and the network line, never waits, and reserves nothing in the `all` line, because their sync runs on their own token. A held row answers its status. The owner's claim takes over a request still waiting in line, and its sync is a full read when one is due. So a visitor who signs in from "is this you? skip the wait" gets their sync queued at once, on their token.

A signed-in request for another login follows the signed-out order without the `all` line. It skips the line's wait, keeps its network's charges for the lookup and a first read, and starts now. Like the owner's, its claim takes over a signed-out request it read as waiting in line, and that takeover charges no first read, which the waiting request's network already paid. A signed-out request that claims the login while a signed-in request looks it up wins, and the signed-in request answers from its row. The lookup still runs on the server's token and pays its unit into the `all` line.

#### The lines

`rate_lines` keeps each line as one time, `busy_until`, the generic cell rate algorithm with weighted cells. A reservation starts once `busy_until` minus the burst has passed. It is one `insert … on conflict do update … where` statement, so concurrent reservations queue on the row lock and never get the same start. A forced reservation never refuses, for work that pays into a line but never waits. `adjust` moves a line by a signed amount, and never earlier than now. An hourly cron in the main Worker deletes the lines the clock has passed, which reserve the same as no row.

- **The `all` line.** It holds every signed-out sync. `allRate` pays out 80% of `GITHUB_BUDGET_SHARE` of the token's 5,000 REST requests an hour, 3,600 units on the App's share of 0.9 and 2,000 on a personal token's 0.5, with a burst of 200. Both Workers bind the same share. The other 20% of the share is left to enrichment. A signed-in user's sync pays into the `all` line only for the requests that fell back to the server's token, after it runs, and never waits in it. Enrichment never pays into the `all` line, on either token. Its requests on the server's token, a user's fallbacks included, come out of the 20% left to enrichment. Lookups and counts spend GitHub's separate GraphQL window, so counting them as units overcounts on purpose.
- **A network's line.** `networkRate` pays out 150 units an hour with a burst of 150, and a reservation there never waits. Every signed-out lookup takes 1 unit, so a network that owes its burst gets `TOO_MANY_REQUESTS` before any lookup or claim. A login that never synced also puts its first read on its network, after the lookup prices it. That charge is refused once the network already owes its burst, so a network starts one huge import at a time, and a 100,000-star import holds its network for about 6 hours. A first read the `all` line refuses goes back to the network. "Limits" says how the network key is made.

#### The cost model

`costOf` prices a sync before it runs, and its test lists sample prices. A first or full read costs the account read, two GraphQL counts, and one request per page of 100 stars, 28 units for 2,431 stars. An incremental read stops at the first star older than the newest one stored, so it costs the account read and the pages that hold the stars added since, 2 units when nothing is new. Admission prices a signed-out request from the lookup's starred total and an owner from the stored `starred_count`. The price is an estimate. Stars removed or starred again since the last full read, stars swapped at an unchanged total, and a stale `starred_count` all move it, so each sync reconciles after it runs.

#### Reconciliation

The `sync-stars` message carries `reserved`, the units admission put in the `all` line for the sync's own requests, without the lookup. A signed-in user's message reserves 0. The consumer runs each message over `TokenGate.counting` on the server's gate, which counts each request sent on the server's token, the GitHub client's retries and failed requests included. A request on the user's token is not counted. After each delivery, whether it succeeded or failed, `reconcileSync` adjusts the `all` line by what the gate counted:

- A first delivery moves the line by the count minus `reserved`. It bills what the sync spent past its reservation and gives back what it did not use.
- A later delivery bills its whole count.
- A deferred message goes out again without `reserved`, because its first delivery already settled it.
- A message without `reserved`, such as an account sync or one from the debug Worker, bills its whole count.

So a dead-lettered message is already settled. A message the queue refuses at admission gives its reservation back at once. A reconciliation that fails to write is logged, and the message still settles, because a retry would read GitHub again. `GitHubGate`'s share stays the hard cap.

#### Waiting

A request records `starts_at` when its message is sent, set to now or to the start of its turn. When the turn starts later than now, the message goes out at once with `delaySeconds` set to the wait. `syncStatus` says `waiting`, with `startsAt` and how many waiting syncs start before it, and turns `queued` at `startsAt`. The claim's cooldown counts from `starts_at`, so a waiting login is not claimed again, except by its owner. The waiting message still runs after the owner's sync, which costs one more incremental sync. A request that is queued and no longer waiting holds the owner for its 10 minutes, as "Sync" says.

`stargrep_sync_admissions` counts each decision: `started`, `waiting`, `deduped`, `org`, `not-found`, `caller-limit`, `line-full`, `github-budget`, and `lookup-failed`. The `SyncRequests.request` span carries the decision, the cost, and the wait.

## Caching

| Layer | What it caches |
|---|---|
| Browser | The user's library in TanStack DB |
| Workers cache | Public profile pages, discovery pages, and OG images, with stale-while-revalidate. Search answers for the demo account, fresh for 5 minutes and then served for up to a day while a refresh runs. Public `stars` pages for 10 seconds |
| KV | Query plans and query embeddings, through the `SearchCache` port |
| Postgres | Summaries and embeddings, shared across accounts |
| R2 | README text by object ID, so GitHub serves each README once |
| R2 and the Workers cache | Repo icons as WebP, keyed by output version plus the git blob ID or the SHA-256 of the source bytes. The web Worker serves them at `/icons/<key>` on its own origin, through `caches.default`, with `immutable` caching. A change to the normalized output, or to what the normalizer rejects, bumps the version, so an icon URL never shows other bytes and a re-check never reuses an icon the new rules reject. The icon backfill counts a row whose key has another version as due, and every version stays servable until that row's next check |

The landing page answers the demo account's default query at first paint, and its server render calls `search` in the same Worker over `/rpc`. So the answer cache lives in the API package, not in front of HTTP GETs, and every transport gets it. `packages/api/src/answer-cache.ts` owns the policy: how long an answer stays fresh, the refresh, the `x-answer-cache` header, and the `stargrep_answer_cache` metric. The `AnswerCache` port only stores. `search` keeps answers only for the demo login, compared without case, in the `stars` scope, keyed by login, scope, limit, and the query trimmed, collapsed, and lowercased as the plan cache keys it. A hit builds no database, search, or model service. An answer older than 5 minutes is still served for up to a day while a refresh runs through the request's `background`. The web Worker runs it under `waitUntil` from `cloudflare:workers` with a freshly built request layer, because the request's own services close with its response, and gives up after 25 seconds. A stale answer starts at most one refresh per key per isolate every 5 minutes, however the refresh ends. An answer the planner could not plan, `planSource: "fallback"`, is never kept, so after such a refresh the stale answer stays and the next refresh waits 5 minutes. `stars` reads and caches pages of 100 stars for any limit up to 100 and pages of 1,000 above it, keyed by login, page size, and cursor, and answers the first `limit` repos with `nextCursor` at the last one it answered. So a client cannot miss the cache by asking for another limit. `caches.default` holds the answers under the request's origin, because result icons carry absolute URLs, and under a version made of the planner model, `PlannerPrompt.version`, and the embedding model, so a deploy that changes any of them starts cold. A cached answer never takes from the caller's rate limit. Each cached procedure answers with `x-answer-cache: hit`, `stale`, or `miss`, and `stargrep_answer_cache` counts them. `config` answers with `cache-control: public, max-age=300` and `stars` with `public, max-age=10`.

## Spend per visitor

Counted from the code paths. Model prices come from `docs/evals.md`: a plan takes about 3,500 input tokens of `anthropic/claude-haiku-5.5`, about $0.0004, a summary about $0.00076 a repo, and a query embedding about a millionth of a dollar.

**A first-time visitor who searches the demo account.** The page reads `config`, which touches nothing. Its default query is a cache hit: no GitHub request, no model call, no database query, one Cache API read. A miss, once per 5 minutes plus one background refresh, runs the search's two or three queries (the account by login, the hybrid search, and sometimes the prefix check), and a model call only when the plan or the query embedding is not in KV, where both stay 30 days. A query the visitor types costs the same queries, at most one planner call and two embeddings, and nothing from GitHub. The model allowance caps one network at 30 model calls a minute and everyone together at 6,000 an hour, in every location at once. If every call were a plan, that is about $0.73 an hour for one network and $2.40 an hour in all, plus up to $0.24 for the burst of 600 after a quiet hour.

**A visitor who imports a login Stargrep never synced, say 2,431 stars.** `triggerSync` runs about eleven database statements (the account and claim reads, the line's wait, the network's unit for the lookup, the lookup's unit in the line, the account write, the claim, the network's charge for the first read, the line reservation, the row's schedule, and the waiting count when it waits), one GraphQL request through `lookupOwner`, and one queue message. The sync then makes 27 GitHub requests: the account read, 25 star pages, and the two GraphQL counts of a first read. Enrichment adds, per repo no account has read yet, one README blob request, one GraphQL facts request per 25 repos, one summary, and one embedding. Repos are shared, so the share of new repos decides the cost; at $0.00076 a summary, 1,000 new repos cost about $0.76 and 1,000 README requests. While the page shows progress it polls `syncStatus`, two reads and one aggregate each time, and `stars`, which the cache serves at most once per 10 seconds per page.

## Everything as code

The repo is the source of truth. Each concern has one file or folder that defines it.

| Concern | Source of truth |
|---|---|
| Workers, bindings, queues, crons, routes, DNS | The Alchemy program. Each resource is declared in the module that binds it, such as `apps/worker/src`, and `infra/` holds the stacks, providers, state, and which Workers each stage deploys. Each pull request deploys to its own stage |
| Neon projects and branches | `infra/database.run.ts` owns the projects. Each stage's branch is declared with the Hyperdrive that binds it, in `apps/worker/src/database.ts`, which also decides that `prod` keeps its branch on destroy and that preview branches expire |
| Database schema | Drizzle schema in `packages/db`, with migrations generated by `drizzle-kit`. Each stage's Neon branch applies them before its Worker deploys |
| API, REST, and MCP | oRPC contracts in `packages/api`. The OpenAPI spec and MCP tool list are generated from them |
| Environment variables | Effect `Config` definitions, validated at startup |
| Models and prompts | `packages/ai` |
| Search metrics | `packages/core/src/search/metric-registry.ts` names each metric for the planner, and `packages/db/src/queries/search.ts` maps its family to `repo_metrics` columns. Both use `MetricFamily`, so the compiler keeps `MetricFamily`, `metricColumns`, and `nouns` in step |
| Search quality | The query set and its expected results in the repo. CI fails a pull request that lowers recall |
| GitHub App | Its manifest in the repo. Creating the app from it takes one click in the browser |
| Design tokens | `packages/ui` |
| CI and deploys | GitHub Actions workflows. Only CI deploys to production |

Some things stay outside the repo. Secret values live in Cloudflare secrets and GitHub Actions environment secrets, and the repo holds only their names. Only jobs on `main` can read the `production` environment's secrets. Previews read separate credentials from the `preview` environment. Account creation, billing plans, and domain registration are one-time manual steps, listed in `docs/setup.md`.

### Stages

The Alchemy program has two stacks, so no app stage's state holds a Neon project. `infra/database.run.ts` owns the projects in its only stage, `shared`. `infra/alchemy.run.ts` is the app stack, deployed once per stage: `pr-<number>` for each pull request and `prod` for `main`. Each app stage references one project and owns one branch of it, so destroying a stage deletes its branch and never the project. `prod` uses `stargrep-us-east`, and every preview stage uses `stargrep-previews-us-east`, both in `aws-us-east-1`, so a Neon key scoped to the previews project can't reach prod's branch. Only the deploy from `main` deploys `shared`. A pull request stage fails with a missing reference until `main` has deployed once.

`prod` deploys only the Worker, its database, the queues, R2 bucket, and Durable Object the pipeline needs, and the web Worker with its KV namespace. It serves on `stargrep.com`, and `www.stargrep.com` redirects there. The Worker holds the custom domain, and a zone route sends every path to the web Worker, because routes take precedence over custom domains. The web Worker passes `/health`, with any query string, to the Worker through a service binding, so the health check still reads the Worker's database connection. Cloudflare matches route patterns against the query string too, so a `/health` route would miss `/health?x=1`. Prod has no workers.dev URLs, so every request passes the zone's rules. Every other stage serves only on its workers.dev URLs and also deploys a debug Worker with a queue and consumer, KV, R2, two Durable Objects, and an hourly cron, so the checks in `docs/setup.md` can drive them. Its routes take a bearer token that the stack generates per stage, and a Durable Object caps them at 300 units of work a minute.

Deployed stages keep Alchemy state in the Cloudflare account through `Cloudflare.state()`. Under `alchemy dev`, state stays in `infra/.alchemy/` and the stage declares no Neon resources, so a local stage needs no credentials.

## Testing

- `packages/core` tests use `bun test` with in-memory layers. They cover behavior, such as "an unstarred repo gets `unstarred_at`", not internal calls. Time runs on `TestClock`, so tests never sleep. `packages/testing` provides `it.effect`, `it.live`, and `it.layer` for `bun test` and is the only place that calls `Effect.runPromise` in tests. `docs/effect.md` section 7 shows how to use it.
- `packages/db` runs each query test twice, on PGlite and on Postgres 17 with pgvector through `pg`. The `pg` run creates and migrates a database for each test file in the local container from the root `compose.yaml`, and CI starts the same container. The PGlite run starts each database from a migrated data directory that the first test process builds and keeps in the temp directory, keyed by the PGlite and pgvector versions and the migration files, because initdb takes seconds on a busy machine. The pipeline runs integration tests against a Neon branch made for each test run.
- `apps/web` and `apps/worker` tests run on workerd through `@cloudflare/vitest-plugin`. The first test in each file waits about 9 seconds while the module graph loads, so the config sets `testTimeout` to 30 seconds. Workerd test files are named `*.workerd-test.ts`, which `bun test` never matches from any folder, and the vitest config includes only that pattern. `bunfig.toml` ignores `repos/`, so a root `bun test` runs every other `*.test.ts` in the repo.
- `bun test` runs with `--parallel`, not `--concurrent`, so a test that times out still interrupts its fiber and runs its finalizers.

## Settled by prototypes

These ran locally on 2026-11-03, with no cloud account.

- **Alchemy 2.0 beta covers every resource Stargrep uses.** Under `alchemy dev` with Bun, one local stage ran a Worker with a queue producer and consumer, a Durable Object, KV, R2, a cron, a Workflow, and Hyperdrive to a local Postgres. Neon projects, branches, roles, and connection strings and GitHub secrets exist in its source. State needs an explicit store. Stargrep uses `Cloudflare.state()`, so CI needs only a Cloudflare token.
- **TanStack Start, oRPC 2.0 beta, and Effect run together on workerd.** One procedure with an Effect Schema input and an Effect handler answered over RPC, REST, and MCP, and the OpenAPI spec generated. The client bundle stayed free of Effect with type-only contract imports. One runtime import of the contract added about 27 KB gzipped, so a lint rule enforces type-only imports. Every `@orpc/*` package pins `2.0.0-beta.48`, because npm's `latest` tags mix 1.x and different betas.
- **`drizzle-orm/effect-postgres` works on workerd with `prepare: false`, and Stargrep does not adopt it.** With default prepared statements, 68 of 360 transactions failed behind a transaction-mode pooler. Better Auth's adapter fails on it. `pg` measured no slower and serves both core and auth.
- **`drizzle-kit` does not emit `CREATE EXTENSION vector`.** The first migration adds it by hand.
- **The `bun test` helper works.** It lives in `packages/testing`, and its tests cover what the prototype checked.
