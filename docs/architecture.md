# Stargrep architecture

This doc explains how Stargrep is built and why. `docs/product.md` explains what it does. The Drizzle schema and oRPC contracts define the stored data and public API. This doc describes the running system.

## Principles

- **Headless core.** All domain logic lives in `packages/core` as Effect programs. Each program declares the services it needs, such as `Db`, `GitHub`, `TextGeneration`, `Embeddings`, `Queue`, and `BlobStore`. Core has no imports from TanStack Start, Cloudflare, or oRPC. `bun test` runs it with in-memory layers and no network.
- **Effect conventions.** `docs/effect.md` sets how services, layers, errors, schemas, config, tracing, and tests are written. It follows T3 Code's conventions, adapted to Workers and `bun test`.
- **Platforms are layers.** Each service has one production layer, such as `Queue` on Cloudflare Queues, and one in-memory layer for tests. Moving a service to another platform means writing one new layer. Core does not change.
- **Parse at the boundary.** Effect Schema parses GitHub responses, environment config, model output, and API input into domain types. Code inside trusts those types and does not validate again.
- **One schema library.** Every schema in our code is an Effect Schema. Our code never imports zod, even though some dependencies install it. Schemas leave our code in two places, each with one bridge. oRPC takes Effect schemas directly through `@orpc/effect`. `packages/ai` wraps a schema with `Schema.toStandardSchemaV1` and `Schema.toStandardJSONSchemaV1` before passing it to the AI SDK or to a coding-agent CLI.
- **Shared repos, per-user stars.** Each repo is fetched, summarized, and embedded once, however many accounts starred it. An account's stars are rows that point at shared repos.
- **GitHub numeric IDs as keys.** Accounts and repos are keyed by GitHub's numeric IDs. Logins and repo names change on rename.
- **Idempotent pipeline steps.** Every ingestion step converges to the same state when it runs twice. Queues retry, so steps must survive retries.

Production code runs on the Workers runtime, not Bun. Code in `apps/` and every package they import must avoid Bun-only APIs. Bun runs installs, scripts, and tests.

oRPC 2.0 and Alchemy 2.0 are betas, and Drizzle 1.0 is a release candidate. Pin one exact version of each and upgrade on purpose.

`Db` exposes query functions from `packages/db`, each returning an Effect with a typed error. It never exposes the Drizzle database object, so core does not import Drizzle types. Tests use `layerMemory` from `@stargrep/db/memory`, which runs the same migrations and query code on PGlite, Postgres compiled to WASM with pgvector, inside the test process. Transactions are a separate service. A driver change then touches only `packages/db`.

The `Db` service uses `pg` because Hyperdrive documents `pg` and because Better Auth's Drizzle adapter awaits queries, which only the promise-based driver supports. One driver then serves both core and auth. Drizzle's JIT row mapping stays off, because Workers block `new Function`.

TanStack DB holds the browser library. React holds view and request state. The server renders the stars page, and hydration loads the stars engine, including Effect and TanStack DB. The browser uses an Effect `Stream` to debounce search and cancel stale requests. API imports in client code are type-only, so the oRPC contract adds no runtime dependency.

App code talks to Postgres through Hyperdrive with a standard driver and uses no Neon-only APIs, so moving to another Postgres host is a dump and restore. Development and preview branches scale to zero. Production does not scale to zero, because a woken compute starts with an empty cache and the first vector searches then read from remote storage.

Every stage's database runs in `aws-us-east-1`, and the main Worker and the web Worker have the placement hint `aws:us-east-1`, so Cloudflare runs their `fetch` handlers in the data center nearest that region. A request crosses the distance to the caller once, and its queries stay near the database. Placement moves only `fetch` handlers. Cron triggers, queue consumers, and Durable Objects run where Cloudflare starts them, and the debug Worker has no placement.

## Data model

Better Auth owns `user`, `session`, `account`, and `verification`, declared in `packages/db/src/auth-schema.ts` so they migrate with the rest of the schema. Stargrep adds these tables.

| Table | Key | Holds |
|---|---|---|
| `github_accounts` | GitHub account ID | type (`user` or `org`), login, name, avatar, followers, public repos, total stars across owned repos, how many repos it has starred on GitHub as of the latest lookup, sign-in, or full read, `claimed_by` user, star sync state, including the time of the latest full star snapshot |
| `repos` | GitHub repo ID | owner, name, GitHub node ID, description, topics, language, license, homepage, created time, `pushed_at`, archived, README object ID from the latest facts fetch, summary with the README object ID it describes and the summary recipe that made it, keywords, `embedding halfvec`, embedding model, which text the embedding was made from, the summary or the repo's metadata, whether a newer text has replaced that one, full-text column, how many times enrichment failed since the repo was last read and when it last failed, whether the daily summary cap deferred its summary since then, GitHub's star count as a star list or a facts read last reported it, whether a signed-in user starred it, how many synced accounts star it now, and the knowledge columns: the input hash, the current receipt, `gone_at`, and one array of closed atoms per role and dimension |
| `repo_metrics` | GitHub repo ID | current totals and 30-day and 90-day changes for stars, forks, commits, active contributors, new contributors, merged pull requests, closed issues, and releases. A star sync stores the star total the list gives a repo with no metrics yet, and enrichment writes star and fork totals. Growth and activity rollups have no producer yet |
| `stars` | account ID and repo ID | `starred_at`, `unstarred_at`, the time of the latest observation, source (`gharchive` or `api`). Only `api` is written today. Archive star events are planned, see "Planned ingestion". Every star event carries the time it was observed: an API sync's start, or an archive event's own time. An event or snapshot observed at or before the row's latest observation, or at or before the account's latest full snapshot, changes nothing |
| `follows` | follower ID and followee ID | source (`github` or `stargrep`), created time |
| `collections` | ID | owner, slug, title, description, kind (`user` or `editorial`) |
| `collection_items` | collection ID and repo ID | note, position |
| `search_events` | ID | time, scope, query, result count, clicked repo, with no user identity |
| `api_usage` | key and day | request counts per procedure |
| `sync_requests` | lowercase login | when a sync was last requested, when its sync starts once its message is sent, and its outcome: `claimed` while admission reserves and sends, `pending` once sent, `failed`, or `missing` when GitHub has no such login |
| `rate_lines` | line key | the row's generation, the time given back from the line in all, and the time until which it is busy: `all` for every signed-out sync, and `caller/<key>` for one network's lookups and first reads, `model/all` and `model/<key>` for planner and query embedding calls, `stars/<key>` for one network's pages of `stars`, and `summary/all` for the summaries the Worker pays for, see "Admission", "Limits", and "Ingestion pipeline" |

The knowledge tables (`receipts`, `extraction_batches`, `decisions`, `subjects`, `subject_labels`, `subject_canonical`, `subject_closure`, `subject_matches`, and `repo_facets`) hold what the summary model said about each repo, the curated vocabulary, and each repo's subject atoms. `docs/knowledge.md` explains them. Enrichment keeps every summary answer as a receipt, projection writes atoms and mints subjects, and a one-off backfill wrote legacy receipts for summaries made before receipts.

The schema also reserves follows, collections, search events, and API usage. Their presence does not mean the app imports follows, serves collections, or records search analytics.

## GitHub access

GitHub limits each user token to 5,000 requests per hour. That budget is shared with every other app the user authorized. The Stargrep GitHub App's installation gets its own 5,000 requests and 5,000 GraphQL points an hour, and more only past 20 repositories or 20 organization members. Stargrep uses incremental reads, content-addressed READMEs, and separate user and server budgets.

1. **Incremental sync.** A sync reads newest first and includes every star at its stop timestamp. An unchanged user sync costs an owner read and one star page. ETags do not help here. Each star list page embeds live repo stats such as `pushed_at`, so its ETag changes when any of its 100 repos changes, even when no star changed.
2. **README object IDs.** GraphQL returns the README's object ID with the repo. Stargrep fetches a README again only when that ID changes. A new summary recipe can also require a new summary. An object ID names fixed content, so R2 keeps each README under its ID, and a README already in R2 costs no request. Enrichment and the prefill read the READMEs R2 lacks through GraphQL, 25 to a request for one point, by repo node ID and object ID. `packages/github/src/readme.ts` keeps a text only when its bytes hash to the object ID, then decodes them as fetch decodes a REST body, so both reads store the same string. A README the batch leaves out, such as one whose repo is gone or whose text GraphQL cut short, is read over REST, one request each. A batch GitHub fails to answer leaves all of its READMEs to REST, and a rate limit or a token problem fails the read instead.
3. **The user's own token.** Work a signed-in user starts reads GitHub with their token: their own sync, the weekly full sync, an import of another login they start while signed in, and the facts batches and README reads that enrich the repos those syncs bring in. Stargrep takes at most 20% of what remained in each of the user's rate-limit windows when it opened, read from `x-ratelimit-remaining`. The user's gh CLI, IDE, and CI share the same 5,000 requests an hour, and a 3,000-star full sync needs about 33 of them.
4. **The server's token.** Prod reads with the Stargrep GitHub App's installation token, and previews and local stages with a personal token. It pays for signed-out syncs, account lookups, sweeps, crons, icons, the header's star count, and the part of a user's work that falls back from their token. The star count costs one GraphQL point an hour per Cloudflare location, which the gate counts like any other request. Every signed-out sync first waits its turn in an admission line sized to the token's share, as "Admission" in "API and MCP" explains.

A user's token is used only for work that user started. Stargrep never pools user tokens to crawl other accounts, and never uses one for a sweep or a cron. The token never leaves the server. The main Worker reads it from Better Auth by user ID when a job sends its first GitHub request, and queue messages carry only the user ID.

`packages/github` sends requests one after another per token through a Durable Object. GitHub's best practices ask for serial requests per token, which keeps Stargrep under the secondary limit of 100 concurrent requests. An in-memory lock cannot enforce this across isolates. The one exception is `import-stars` on a developer's machine, whose `BulkGate` in `packages/github/src/bulk-gate.ts` sends a few requests at once on a personal token within a share of its limit, as "Import a list of logins' stars" in `docs/setup.md` explains. The sync reads the REST star list, which is faster per page than GraphQL `starredRepositories`. The object tracks remaining budget from response headers across Worker isolates. `packages/github/src/rate-limit.ts` classifies HTTP and GraphQL replies for the client, fallback gate, and installation-token mint. `packages/github/src/errors.ts` shares permanent-failure classification between enrichment and queue settlement.

## Ingestion pipeline

The sync and enrichment consumers are idempotent. A separate `fetch-icon` queue discovers and normalizes repo icons.

1. `sync-stars` fetches an account's star list newest first. It stops at the first star older than a star the last completed sync saw unchanged, so it reads every star that shares that star's `starred_at`. An account's first sync has no stop line, so it reads every star. After that, the owner's `viewer` call asks for a full sync once the last full read is a week old. For 3,000 stars a full sync takes 32 GitHub requests: two GraphQL owner reads and 30 REST pages. The first owner read supplies both the account facts and the initial count. Incremental user syncs and org syncs each spend one GraphQL point for owner facts instead of one REST account call. The admission lookup is a separate GraphQL point. Stars that are gone mark `unstarred_at`. The list pages by offset, so a full read counts the stars through GraphQL before and after. When the counts differ, the read shifted, and the sync writes what it read but skips the unstars and does not record the run. A star added and another removed at different page boundaries during one read leave the counts equal, so that read can hide one star until the next full sync. GitHub refuses any page of the list past the 400th, and it stops listing a very long list well before its end, so a full read can list fewer stars than GitHub counts. Such a read is partial. The sync writes what it read and records the run and its full read, but marks nothing unstarred, since it cannot tell a star GitHub no longer lists from one that is gone. A star removed and another added at page boundaries can also leave a read one star short, and it then counts as partial too. An org cannot star repos, so its count is zero without a GraphQL request. A finished sync only moves the account's sync time forward, so an older run that finishes last cannot pull the stop line back. It enqueues the repos that need enrichment after it reads the last page, because enrichment shares the token's one request at a time and would otherwise hold it between the sync's pages. Each page also stores the description, topics, and language the list carries for a repo enrichment has not read. Once it has enqueued them and recorded the run, the sync embeds new repos from that metadata for at most 30 seconds, as "Metadata embeddings" in `docs/knowledge.md` explains.
2. `enrich-repo` runs for repos that are new or whose README object ID or other prompt inputs changed. It stores the README in R2, keeps the model's answer as a receipt, writes the summary and keywords, projects the facts the answer states, and computes the embedding. It also fetches repo facts, such as license and homepage. `docs/knowledge.md` explains receipts and projection.

Bulk enrichment, such as a backfill of popular repos, uses the Gateway batch API for summaries and `embedMany` for embeddings. The batch path serves the CLI and backfills only, because a batch job can take minutes to hours.

`apps/worker` runs these queue consumers. `src/queues.ts` declares each queue, its dead-letter queue, and its consumer settings.

- A consumer decodes each message, calls one service method, and settles the message. Success acks it. `afterFailure` in `src/consumers/settle.ts` maps every failure tag to one settlement, and a new tag fails typecheck until it has a row.
- A failure that can pass on a second try, such as a lost database connection, a deadlock, a GitHub 5xx, a GitHub 403 that names no rate limit, or a model timeout, retries up to five times a minute apart, and then Cloudflare moves the message to the dead-letter queue. An enrichment failure that counts against the repo instead starts its backoff and settles on its first attempt, so the sweep owns the next try, and a queue retry never pays again for a repo that just reached the cap. A failure that cannot, such as a missing token or key, an unknown account, or a body that does not decode, goes to the dead-letter queue on its first attempt. A failure while the runtime layers build, such as a lost database connection or an embedding model conflict, fails the whole batch before any message is settled, and Alchemy retries every message in it.
- A spent token budget or a GitHub rate limit is not a failure. GitHub names the time the limit lifts, or asks for a minute when a secondary rate limit names no time, so the consumer sends the message again with that delay and acks the original. A long pause then spends none of the five retries.
- The `enrich-repo` consumer takes up to 30 messages per batch and runs one batch at a time. A summary thinks, so a round of four direct calls takes about 15 seconds, and 30 messages, three chunks of at most ten rounds each, end inside the deadline below. It runs and settles them 10 at a time, so a chunk's messages are acked or retried before the next chunk starts. Ten minutes after the batch starts, a chunk still running stops, and its messages and every later one retry, well before Cloudflare ends a queue invocation at 15 minutes. Deferrals are cached for the batch by the token that hit its limit. Each failure keeps that token even if a later request in the same job falls back. Later jobs consult the selected token's wait before sending. Signed-out chunks can skip the run, while a signed-in job can use its user's reset allowance even while the server still waits. The Worker's text-generation layer has no batch API, so `enrichRepos` answers each repo with its own model call. It saves each summary as its answer arrives, so a chunk the deadline stops keeps every summary it paid for, and its retry only embeds them. It reads each repo id once. A repo several accounts starred arrives once per account, and a later batch finds it enriched.
- GitHub answers each repo in a facts batch on its own. A repo it does not return, or reports as `FORBIDDEN`, settles as gone, and the rest of the batch enriches. The client logs the node IDs of forbidden repos. Any other GraphQL error fails the whole batch.
- A repo is read once it has a summary of its current README and an embedding, which is `unreadEnrichment` in `packages/db/src/schema.ts`, negated. Enrichment is also due for a read repo whose summary an older recipe made, or other prompt inputs than the ones `saveFacts` last saw, such as a new description or topic set. `saveFacts` stores those inputs as `input_hash`, and a saved summary records the hash it answered as `summary_input_hash`. `summaryRecipe` in `packages/ai/src/models.ts` versions the summary model, prompt, and output schema, and a test pins it to them. Such a repo stays read. Its new summary is saved as soon as it arrives, and its old embedding stays, marked `embedding_stale`, until the embedding of the new summary replaces it, so search keeps finding it and a failed embedding never costs a second summary. A repo embedded from its metadata keeps that embedding the same way. `pendingEnrichment` is the wider predicate. The sweep and its partial index use `sweepableEnrichment`, which also leaves out every repo the summary policy below holds back. A gone repo is never pending. `summary_recipe` defaults to the current recipe. The sweep's partial index and the metadata sweep's both name it, so a recipe bump comes with a migration that rebuilds both and changes that default. `EnrichRepo` counts a repo's own failures when each batch chunk finishes: gone or forbidden, no node ID, a README GitHub no longer serves, a 4xx other than 403 on its README, model answers that do not decode, or a refusal. A fact the model wrote that does not decode never counts. A failure every repo would hit, such as a missing token or key, an outage, a rate limit, or a batch that aborts, never counts. Each failed repo logs a warning with its ID, the failure's tag, whether it counts, and the error's message, which never holds README text, prompts, model output, or keys. Each counted failure adds one to `enrich_failures` and sets `enrich_retry_at` from `retryDelays` in `packages/core/src/repos/enrich-retry.ts`. A failure before the retry time has passed is a copy of one already counted and changes nothing. Saving the embedding sets both back. A pending repo with `enrichFailureCap` failures, 3, counts as failed, so a library's progress can reach its end.
- `enrich_retry_at` is also the attempt's lease. Before its paid summary calls, `EnrichRepo` leases the repos it will ask about, in one statement that takes only repos whose summary is due and that no other attempt holds. A repo due only for its embedding is never leased, so an attempt that planned a summary pays nothing once another attempt has saved one. It skips a repo it cannot lease as `Backoff`, so two consumers given the same repo make one paid call. A lease lasts `attemptLease`, 15 minutes, which outlasts the queue consumer's 10-minute deadline. An attempt that sends a provider batch of two or more prompts leases for the batch's timeout plus 15 minutes, 24 hours and 15 minutes on the Gateway, so no other attempt pays for a repo while the batch waits. The lease's end time names it, so capture clears only the lease its answer's attempt holds, saved or stale, and a late answer never frees a repo a later attempt holds. A failed call is settled while its attempt still holds the lease, before the chunk projects or embeds anything, in one statement. A counted failure adds one to `enrich_failures` and turns the lease into the failure's backoff. A refusal sets `enrich_failures` to the cap and clears the lease, since asking again only pays for the same refusal, so the sweep never sends the repo again. Any other failure gives the lease back. The queue dead-letters a refusal. A paid answer Postgres refuses fails only its own repo as `AnswerNotSaved` and counts toward the cap, so its chunk-mates are still saved. An answer capture could not save for a reason any repo could hit, such as a lock timeout, a lost connection, or a deadlock, counts nothing and keeps its lease. The queue dead-letters both, so the sweep sends the repo again after its backoff or once the lease runs out, and a repo that just reached the cap is not paid for again. A run cut short keeps its lease until it runs out, so the repo waits for the sweep instead of being paid for twice. A batch run of `enrich stars` that dies holds its repos for the whole batch lease, and a rerun inside it skips them, so the batch it paid for is never collected. Once the lease runs out, the sweep or a rerun pays for those repos again. Bulk runs belong to the prefill driver instead, which keeps a manifest of every batch it sends and resumes it after a crash, as "The prefill" in `docs/knowledge.md` explains.
- The Worker pays for at most `summariesPerDay`, 1,000, new summaries a day. `summaryAll` in `packages/core/src/limits/rate-line.ts` holds this daily summary cap as a rate line. Once `EnrichRepo` holds its leases, `SummaryAllowance` takes one unit per repo it will ask about, in the summary order below, before any model call, retries and the new summaries a recipe change asks for included. A clear line takes a day's units at once, such as for a big import, then pays out one every 86.4 seconds, so a steady backlog costs 1,000 summaries a day and any 24 hours at most 2,000. A repo the line refuses settles as `Capped`: its lease becomes a retry time at the line's next opening, it counts no failure, and its message acks, so the sweep below sends it again once the line has room. The same statement sets `summary_deferred`, and saving the summary's embedding clears it. `stars.enrichment` counts an unread repo with the mark and under the failure cap as `queued`, so a library waiting only on the cap reads as settled and its page stops the fast poll. An embedding takes no unit, and a stage on the stand-ins meters nothing, because a stand-in answer costs nothing. Each attempt the line refuses logs one warning, `Summary cap reached, N repos waiting`, and `stargrep_summary_cap` counts each repo as `allowed` or `capped`. A repo waiting for a summary still imports, and the library and keyword search show it from its facts. Search finds it by meaning from an embedding of its metadata, which the same attempt makes and which takes a unit of its own line, `metadataAll`, never of the summary cap. `prefill --pending` clears the backlog on a developer's machine through the leases above, so it and the sweep never ask about the same repo, and its summaries take no unit. `docs/setup.md` gives the command.
- The summary policy decides which repos get a paid summary at all. `summaryWanted` in `packages/db/src/schema.ts` wants a repo with at least `summaryPolicy.stars`, 200, GitHub stars, a repo a signed-in user starred, and a repo with neither a description nor topics and at least `summaryPolicy.bareStars`, 50, because only a summary lets search find that one by meaning. A repo whose count is unknown is wanted, so its first facts read can learn the count. `repos.stars` holds the count. A facts read always writes it. A star list writes it when it writes the row for another reason, and otherwise only when the count crosses 50 or 200, so syncs that list a popular repo many times a day do not rewrite its row for each new star. `repo_metrics` keeps the facts read's count for search, but a partial index sees only `repos`, so the policy reads this copy. `repos.user_starred` says a signed-in user starred the repo. Each sync of an account a user claimed runs `repos.markUserStarred` before it queues enrichment, which marks every repo the account stars now, so the first sync after sign-in also marks the repos an earlier signed-out sync stored. An unstar leaves the mark. `EnrichRepo` checks the policy on the stored row before it reads any GitHub facts, README, or icon. A repo whose summary is due and that the policy does not want settles as `Unwanted`. It gets its metadata embedding when one is due, its message acks, and the enrichment sweep never sends it, because that sweep's partial index leaves it out. If the embedding call fails or `metadataAll` refuses it, the metadata sweep embeds it later, as "Metadata embeddings" in `docs/knowledge.md` explains. A repo whose count was unknown pays one facts read, which saves the count, and settles the same way before its README is read. Once a star list or a facts read moves its count past a floor, or a signed-in user stars it, the repo enters the partial index again and the sweep sends it. `stars.enrichment` counts it as `queued` meanwhile. Both numbers are literals in the partial index, so a change to either ships with a migration that rebuilds it, as a recipe bump does. `prefill --ids` asks every repo its list names, whatever the policy says.
- The summary cap spends in one order, `summaryOrder` in `packages/db/src/queries/repos.ts`. Enrichment that needs no summary goes first, because it costs the cap nothing. Then come repos a signed-in user starred, then repos more synced accounts star now, then repos with more GitHub stars, then the lower ID. The sweep sends in that order, and `prefill --pending` asks in it. Within one attempt, `EnrichRepo` takes the cap's units in the order `repos.inSummaryOrder` gives the repos it leased. It asks after it saves the facts it read, so a repo whose count was unknown is ranked by the count GitHub just reported. The count of synced accounts is `repos.synced_stargazers`. Triggers on `stars` move it by one in the statement that starts or ends a current star, so a retried write adds nothing and two syncs that star one repo at once each add their own. Each trigger locks its repos in ID order. An upsert fires its UPDATE trigger before its INSERT trigger, though, and a snapshot writes stars in two statements, so `stars.upsert` and `stars.applySnapshot` lock the account's row and then every repo whose count they can change, in ID order, before they write. A `TRUNCATE` of `stars` sets every count back to 0. The order is the key of the sweep's partial index, `repos_sweep_order_idx`, so the sweep and `prefill --pending` read their first repos from the index and stop. The order used to count each repo's stargazers through `stars_repo_idx` as it ranked, which ranked every repo that waited before it sent the first. Once a bulk import filled the backlog, that sort outgrew the statement timeout on almost every sweep. On a local copy shaped like prod at about twice its size, 2 million repos and 8 million stars with 290,859 repos waiting, the sweep's statement took 10.0 s before and 37 ms after, the median of 3 runs each. A new star now costs a write to its repo's row. On that copy, a sync page of 100 new stars took 13 ms longer and wrote about 400 KiB more WAL. The triggers count from the migration that added them, so a database that held stars before it runs `bun run --cwd packages/db count-stargazers` once, as `docs/setup.md` says.
- An incremental sync lists only new stars, so it never sends a pending repo again. A cron in `apps/worker/src/crons.ts` runs `EnrichRetry.sweep` every 10 minutes instead, with a 5-minute timeout. It sends at most 100 repos under the failure cap whose retry time has passed and whose summary, when one is due, the policy wants, in the summary order above. A repo whose message was lost is among them. A repo waits 10 minutes after its first failure and an hour after its second, so a repo GitHub forbids costs at most three lookups, each one node in a batched GraphQL request. A message that reaches a repo before its retry time, such as a queue retry of a counted failure or a second sweep send, settles as `Backoff` with no GitHub call. A partial index, `repos_sweep_order_idx`, holds only those repos, in the summary order, so a run reads about as many entries as it sends, and neither repos at the failure cap nor the repos the policy holds back slow it. A full sync or another account's first sync still sends a repo at the failure cap again.
- Each dead-letter queue has a consumer that logs the message ID, its attempts, and the IDs in its body, or only the body's type when the body does not decode. An enrich dead letter changes no failure count, because only `EnrichRepo` knows whether a failure was the repo's own. A sync dead letter marks its request `failed`. An icon request's dead letter marks the repo's icon checked and keeps the icon it has, so the repo waits for the 30-day refresh instead of the next backfill. A homepage that fails, whether it times out, answers 5xx, or answers 429 without naming a time, is a miss rather than a failure, so it never spends the queue's retries. When that write fails, the dead letter retries up to five times a minute apart, and on its last attempt it is logged and acked, because a dead-letter queue has no dead-letter queue of its own.

The `GitHubGate` Durable Object holds the Worker's GitHub credential. Every GitHub request on the server's token from every isolate goes through it, so it sends them one at a time. It keeps the rate-limit windows GitHub reported in its storage and takes its share of each window from `GITHUB_BUDGET_SHARE`, so a restart keeps the windows and a new share applies at once. `STARGREP_GITHUB_SERVER_TOKEN` picks the credential: `app`, the default of the prod deploy, or `pat`, a personal token in `STARGREP_GITHUB_TOKEN` and the default everywhere else. Each Worker binds the kind it deployed with, and reads only that kind's credential. The share follows the token: 0.9 on the App, whose budget no one else spends, and 0.5 on a personal token, whose owner keeps half for their own tools. A preview stage may set another number above 0 and at most 1, and a `prod` deploy fails with any share but its token's. Requests and replies cross the RPC boundary as plain data, and the credential never leaves the object. A pull request stage may deploy without a token. It then binds no `GitHubGate`, and every GitHub call fails with `GitHubTokenMissing`.

The gate takes a `TokenSource` and reads its token once a request holds the gate, so a request that waited never sends one that expired meanwhile. A personal or user token is fixed. On the App, `AppToken.makeInstallationTokens` in `packages/github/src/app-token.ts` signs an RS256 JWT with WebCrypto and the App's client ID, finds the installation on the account that owns the App with `GET /app` and `GET /users/{owner}/installation`, and mints an hour's token with `POST /app/installations/{id}/access_tokens`. Installs on other accounts never change it. GitHub hands out the key as PKCS#1, which WebCrypto cannot import, so `app-jwt.ts` wraps it in PKCS#8. The token lives in memory only, and one state decides each request: use the held token, use it and start one refresh in the background in its last five minutes, wait while GitHub said to, or mint. The background refresh runs in a scope the object owns, and a request mints in the foreground only when no token has a minute left, so a slow or failing refresh delays no request. A 401 drops the held token and sends the request once more with a new one, because GitHub revokes an installation's tokens when its App is installed again, and a 404 for the known installation looks it up again. A rate limit on the App's endpoints defers the message until the time GitHub names, and no mint goes out before then. A refusal, such as a revoked key or a suspended App, fails the call with `GitHubTokenMissing` and logs the reason. `packages/github/src/rate-limit.ts` decides what counts as a rate limit, for the GitHub client, the fallback from a user's token, and the mint alike: `retry-after`, else the window's reset when nothing remains, else a minute.

A job a signed-in user started carries their user ID in its message: `userId` on `sync-stars` and on the `enrich-repo` messages that sync sends. `UserGates` in `apps/worker/src/user-gate.ts` gives the job a gate that reads the user's token once, through `GitHubTokens` in `packages/auth/src/tokens.ts`, and sends each request to the `UserGitHubGate` Durable Object named by that user ID. GitHub counts all of a user's tokens against one budget, so one object per user keeps their requests in order and their windows in storage, with `FallbackGate.userShare`, 0.2, as the share. The token comes with each call and is never stored. `FallbackGate.prefer` sends the job through the user's gate until the first of four reasons, then through `GitHubGate` for the rest of the job:

- `budget`: the user's share of the window is spent.
- `unauthorized`: GitHub answered 401, because the token expired or the user revoked the app.
- `rate-limited`: GitHub returned a classified rate limit with nothing remaining, because the user's own tools spent the window.
- `token-unavailable`: Better Auth gave no token: the user has no GitHub account, GitHub refused the refresh, or the read took more than 10 seconds.

The first move logs once, as a warning for every reason but `budget`, and counts `stargrep_github_fallbacks` by reason. A secondary rate limit leaves quota, so the client waits it out on the user's token. `GitHubTokens` builds a Better Auth with only the GitHub provider and token encryption, on one connection it closes before the read returns. Alchemy evaluates a Worker's props again each time the Worker starts, against that Worker's own bindings, so `tokenClientBindings` reads every value as optional and gives the same bindings at deploy and at start. Better Auth refreshes a token within five seconds of its expiry with the app's client secret and stores the new one encrypted. GitHub refuses a used or revoked refresh token with a 200 that names an error. Better Auth would then write back the refresh token it read, over the one a concurrent refresh just stored, so `githubProvider` in `packages/auth/src/auth.ts` fails a refresh that returns no access token before Better Auth writes anything. Jobs of one user in one invocation also share one token read, so they never refresh the same token twice. Previews sign in through prod and bind no client secret, so a preview's expired token falls back instead of refreshing.

The `sync-stars` consumer runs the messages of a batch at once, so a user's sync never waits behind syncs on the server's token. The `enrich-repo` consumer groups a batch by `userId` and enriches each group over its own gate, so a group that aborts fails only its own messages.

The main Worker has four crons in `apps/worker/src/crons.ts`. `*/10 * * * *` runs three sweeps from one handler: one for due enrichment, one for due metadata embeddings, and one that projects stale repo knowledge. `20 4 * * *` resumes the icon backfill, a chain of one message per page of 100 repos. The chain can outlast a day, so `icon_backfill` holds the one chain's position, and each page moves it from its own position to the next before it sends anything. The cron sends a page at that position, or at the start when no chain runs. So a chain that stopped resumes where it stood, and of two copies of a page only the first to move the chain sends anything. `30 3 * * *` recounts the repos each subject holds and then runs the usage floor, and `40 * * * *` prunes admission requests and rate lines. Every cron runs on a sweep minute on purpose. Neon suspends a compute after 5 idle minutes, and a query at any other minute would leave no idle window, so the database would never scale to zero. A failed sweep logs its error and never stops the others.

## Search

Search normally combines full text and vectors. If the model allowance refuses the query embedding, it uses full text alone. Any other embedding failure fails the search with `SERVICE_UNAVAILABLE`. Full-text search and vector search run in one SQL query, and reciprocal rank fusion merges the two lists. Full text matches the words the user typed, except each negation from its word through its target, because every repo those words find is one the exclusion drops. The vector side embeds the planner's description of a matching repo, or the query itself when the planner is skipped. It keeps only repos within the embedding model's `maxMatchDistance` of the query, a cosine distance of 0.36 for `voyage/voyage-4` in `packages/ai/src/models.ts`, before the lists merge. Search reads the value from the model it runs, so the fake hash model in tests uses its own. A repo whose summary waits matches through its metadata embedding under the same distance, which "Metadata embeddings" in `docs/evals.md` measures. Every query has nearest neighbors, so without that floor gibberish such as "dfsfgdsrg" came back with 20 results. `docs/evals.md` calibrates the floor. A repo whose name or `owner/name` equals a keyword query ranks first.

- **Your stars.** The candidate set is one account's stars, at most tens of thousands of rows. An exact vector scan over that set takes milliseconds, so this path uses no vector index.

### Query plans

A query such as "open source apps like Wispr Flow with growing contributors" needs filters and a ranking, not only text matching. The planner turns each natural-language query into a typed `QueryPlan`. Growth and activity metrics parse today but match nothing until a rollup producer fills `repo_metrics`.

- **Scope.** The public API accepts only `{ kind: "stars", login }`. Core rejects other scopes with `SearchScopeUnavailable`. The caller sets the scope, never the model.
- **Semantic text.** The text to embed. "Like Wispr Flow" becomes a description of what Wispr Flow does, because the product has no repo to compare against. Text that names nothing the model knows, such as "zzzzzz" or a made-up name, stays as typed, because a description such as "a repository with no clear purpose" matches repos whose own summaries say that.
- **Filters.** Kind, license, language, archived, starred date, and bounds on any metric. A bound is strict or inclusive, so "more than 200 stars" leaves out a repo with exactly 200. Kinds, licenses, and languages become atoms, described under "Atoms in search" below. A language filter matches a repo written in that language or for it, from GitHub's language, a language topic, or the summary model's claims, because a Python package manager is often written in Rust. A JavaScript filter also matches TypeScript.
- **Ranking.** Relevance alone, or the best matches reordered by a metric such as 90-day contributor growth. A metric never lifts a repo that did not match into the results.

The planner is `anthropic/claude-haiku-5.5` with structured output and reasoning turned off. With reasoning on, a plan took 2.1 to 4.6 seconds from a laptop, and with it off 1.2 to 2.1 seconds. It chooses metrics from a registry in `packages/core/src/search/metric-registry.ts`. Each entry holds an ID, the description the model reads, and a family and variant, such as stars and 90-day growth, that `packages/db` turns into SQL over `repo_metrics`. The model never writes SQL. The plan is parsed at the boundary, and a plan that names an unknown metric is rejected. When the planner fails or returns a plan that does not parse, search runs the query as typed.

The planner sets only the filters a query states, and code holds it to that after decoding. A kind filter stays only when the query restricts the kind with a word such as "only" or "not". The model returns each language with the words from the query that named it, such as Python with "питоне". It names a language the query excludes too, as Go in "a cli not written in go", because the compiler reads from the words whether each language is wanted or excluded. A language stays only when those words appear in the query and are the language's name, one of its aliases, or a word in a non-Latin script, such as "питоне" or "パイソン". In Chinese, Japanese, and Thai, which have no spaces between words, the words match anywhere in the text. So a language named in any script stays, and one quoted from a framework, such as Java from "spring boot", is dropped. A quote in a non-Latin script is trusted as naming the language, so a transliterated framework name, such as "लारावेल" for Laravel, can still keep a language filter. `packages/core/src/search/vocabulary.ts` holds the language names and aliases these guards read and the words that send a query to the planner. In the recall eval, filters the model inferred dropped relevant repos, such as Rich for "python framework for text user interfaces", because the summarizer called it a library. `docs/evals.md` has the numbers.

Search returns the values that ranked each result. Growth metrics remain unpopulated until a rollup producer exists.

### Atoms in search

Search filters and boosts by the atoms `docs/knowledge.md` describes. `compileQuery` in `packages/core/src/search/compile.ts` turns the query into atom groups. It is pure, so it reads no database and calls no model. `packages/db/src/queries/search-statement.ts` turns the groups into predicates inside the one hybrid statement.

- **Clauses.** The compiler splits the words into clauses, one per cue word. A clause with no cue describes the results. "for", "in", "on", "with", "using", "built with", "powered by", "runs on", and "written in" make a relation, "alternative to" and a trailing "alternative" make a comparison, and "not", "never", "without", "no", "non", "except", "excluding", "cannot", and every n't contraction, such as "don't", "won’t", or the typo "dosen't", with either apostrophe, negate. A negation reaches through a cue or a verb such as "support", "use", "need", or "work" that follows it at once, so "don't work with docker" excludes Docker. A period ends a clause. A relation, a comparison, or a negation reaches only its first run: either content words, which form label keys and split into alternatives at "or" and commas, or kind, platform, and status words that "or" or a comma joins. The words after that run describe neither the cue's target nor the results. So "no dependency cli tool" excludes "dependency" and leaves CLIs alone. A negation never applies a platform positively, so a platform after its target applies nothing, as "deno" in "without linux deno". A language there is one the planner read into the query, so it keeps its mode, as "go" in "web framework without orm go". "no-code", "non-blocking", and "no-std" are words, not negations, but "non-" or "no-" before a language, platform, or kind negates it, as in "non-rust". A generic noun such as "tool" or "repos" ends the words before it, as a kind word does, and names nothing.
- **Where closed atoms come from.** Languages and licenses come only from the planner's guarded output, as the filters above did, so a language word the planner did not report stays an ordinary word. A language or platform takes the roles its relation names: "built with node" is `with:platform:node`, "runs on linux" is `runs-on:platform:linux`, and "written in rust" is `written-in:lang:rust`. Extraction rarely records what a repo is built with, so a stated dependency reaches member atoms too. "built with rust" reaches `written-in:lang:rust` and `with:lang:rust`, "built on node" reaches `platform:node` and `with:platform:node`, and "powered by openai" reaches member and `with:` subject atoms. A bare negation names a language the same way, so "typescript orm, not javascript" keeps a TypeScript ORM whose topics say it is for JavaScript too. "for", "in", and "on" name no role, so they reach every default role. A negated relation excludes those roles alone. Kinds come from the planner's guarded kinds, or else from the last kind word "only" narrows in the clause that describes the results, so "only libraries for building apps" asks for libraries alone.
- **How each group applies.** `policy` in `compile.ts` is a table with one row per kind of run. Each row gives a mode, and a second mode for a clause "only" narrows, when "only" opens or ends it. Languages, licenses, relation targets, and a language or platform whose role the cue names filter. A negated run excludes. Platforms, comparisons, and bare subject words boost. Kind and status words apply only when "only" narrows them. A relation's words that a closed word cuts short, as "local" in "for local models", boost, because the closed word is most likely the noun they describe. "built with", "built on", "built using", "made with", and "powered by" name a dependency, so their target filters. "with" and "using" can name a feature, as in "editor with ai", or a dependency, so their target only boosts. Both reach member and `with:` atoms. A bare negation such as "without electron" reaches both too, and excludes. A boost is a third rank list, fused like full text and vectors, over the candidates those two found, so it reorders results and never removes one.
- **A filter the words imply never empties a search.** `Compile.relaxation` is a safety net for words the compiler reads wrong. Each stated group records whether the query's words implied it or the planner's guarded output named it. When the filters the words imply leave fewer than 3 results, `Search` runs the statement once more with those filters as boosts. If that finds at least 6, it answers with it, so the repos the filter named still rank first, and `applied` marks their atoms `relaxed`. Filters the caller or the planner named, and every exclusion, stay exact. Only a search that would have answered with almost nothing pays for the second statement.
- **Subjects resolve in the statement.** A subject group applies only when every key names exactly one accepted public subject, which `knowledge_key_meanings` decides. Every `Db` layer keeps every label key that names exactly one accepted public subject, the rule `knowledge_key_meanings` applies, read at most every 5 minutes (`acceptedKeysTtl`). The web server shares one set per isolate across its per-request layers. `search.hybrid` drops a group with a key outside that set before it writes any SQL. So a word no accepted subject holds costs nothing, and a subject accepted since the last read applies within 5 minutes. A key that curation rejected, merged, or made ambiguous since the last read passes every row of the probe shape. Full text and vectors see every word either way. The caller's explicit selection always filters, survives a refused query embedding, and fails the search with `FacetUnavailable` when it names a subject that does not exist, is private, or is rejected.
- **Closed atoms read `repos`.** A closed group is an array test on the `repos` row the statement already reads, ORed over every role the atom reaches. A filter or a boost adds the registry's expansions, so a JavaScript filter matches TypeScript. An exclusion tests the value alone, so excluding JavaScript keeps TypeScript.
- **Subject filters read `repo_facets` in one of two shapes.** Pipeline c, the probe shape, reads one `repo_facets` row per starred repo by primary key. When a filter can drive the index shape, the statement also holds pipeline b and runs one of the two. Pipeline b reads the filter's matches from a GIN index and runs when they fit in the account's star count. `subjects.repo_count` skips that scan when the subject is broader than the library. A negated filter uses an anti-join in place of b. `route` in `search-statement.ts` makes that choice and is pure, so its unit test needs no database.
- **Two known slow cases.** A subject broader than the library takes the probe shape. On a branch of prod with every subject accepted and 1,786 stars, two searches ran over the 3 ms target at p95, measured against today's statement. "apps without react" excludes such a subject, so it keeps most rows and ran 8.4 ms slower. "state management in react" filters on one and boosts the other words, and ran 3.7 ms slower. No subject is accepted in prod yet, so neither applies until curation accepts one.
- **The envelope.** Every row of the result carries what SQL resolved: each subject group's subjects, their labels, and the explicit subjects that are unavailable. `Search` returns them as `applied`, with the span of the query each atom came from.

`Compile.version` hashes the grammar, the policy, and `Compile.tables`, the registry and vocabulary tables the compiler reads, so a new alias or stop word changes it. The answer cache's version includes it. `bun run evals/recall.ts --accept-floor` measures recall after the usage floor accepts subjects as the nightly job does, and `--bare-filters` adds the promotion of bare subjects to filters.

`QueryPlanner.plan` and `QueryPlanner.planWithModel` set `search.plan.source` on their spans to `keyword`, `cache`, `model`, or `fallback`. `Search` counts each search once in `stargrep_search_plans`, under the source of the plan it ran, so a keyword search that needed the planner counts as `model` or `cache`. A fallback also sets `search.plan.failure` to the error tag, such as `AiTimeout`, so traces show how often Haiku's tail latency sends a search to the typed text.

A repo name, an `owner/name`, or two plain words skip the planner. When such a query matches no name, no word, and no repo within that distance, search first looks for a misspelled name. `db.search.nearNames` runs the typed words together and finds the account's repos at most one edit from them, matched against the name run together, each part of the name, and the owner and name run together. An edit inserts, deletes, changes, or swaps two neighboring letters. Postgres matches every spelling one edit away with one regular expression, so it needs no extension. One edit leaves the first or the last half of the typed text as typed, so only names that hold one of those run the expression, and the query takes about 30 ms over 20,000 stars on a local Postgres instead of up to 1.2 s. Those repos answer as similar names, the closest whole name first, so "pacsek" finds `moson-mo/pacseek`, "hlrags" finds `m-demare/hlargs.nvim`, and "tanstak query" finds `TanStack/query`. Typed text under five letters skips this step, because it sits one edit from too many names. The caller's own filter applies to the names as `search.hybrid` applies it, through the same atom tests, so a filtered search finds a misspelled name only among the repos the filter keeps. The step runs before the planner, because the planner cannot place a name it does not know and reads it as the nearest thing it does, such as "hlrags" as RAG, and a misspelled name carries too little meaning to rank its repo near. Otherwise search plans the query with the model and runs that plan, which is how a misspelling of more than one edit or of a description, such as "fuzy finder" for `junegunn/fzf`, still finds its repo. Gibberish costs that name query and one planner call, and still finds nothing. Words that still match as a prefix of a word in the account's stars skip both, because they are most likely a word the user is still typing, such as "zust" on the way to "zustand". The web client searches as the user types, and on the eval corpus the prefixes of 28 typed queries would call the planner 151 times without that rule and 34 times with it, 24 of them for typos. When the planner fails, search answers with nothing instead of running the same words again. A query with a word that can name a filter, such as a language, a kind, a license, "only", "more", or a number, goes to the planner, so "only MIT libraries" keeps its filters. The `SearchCache` port caches plans and query embeddings under a SHA-256 of the normalized query text. Each entry records when it expires, 30 days after it was written, so an old entry is a miss on every backend. A corrupt entry is a miss too. A plan with a date filter is reused only on the day it was planned, because "starred last year" depends on today. Tests use the memory layer. The web Worker keeps entries in a KV namespace and sets each one's KV expiration from its TTL, at least the 60 seconds KV accepts.

## AI providers

`packages/ai` has two ports, because they have different providers. Production summarizes with `anthropic/claude-haiku-5.5` and embeds with `voyage/voyage-4` at 1,024 dimensions. `docs/evals.md` records the bakeoff that chose them. The query planner uses `anthropic/claude-haiku-5.5` through its own `TextGeneration` layer, `layerPlannerTextGeneration`, with a 4-second timeout and no retries. Each request states whether the model may think, because Haiku 5.5 thinks by default and bills those tokens. A summary thinks at `high`, the level `Summarize.reasoning` names and the recipe digest pins, and a plan turns thinking off, because its 4-second deadline leaves no room for it. The Gateway adapter sends the setting on a direct call and on each item of a batch. The Claude Code adapter sets `alwaysThinkingEnabled` to true and passes `--effort` at the level, or sets it to false for none. `TextGeneration` turns a prompt into a value of an Effect Schema, for summaries, query plans, and later reranking. `Embeddings` turns texts into vectors. Core code imports only the ports.

| Port | Adapters | Where it runs |
|---|---|---|
| `TextGeneration` | AI Gateway, Claude Code CLI, fake | Gateway on prod, local stages, and opted-in previews. The fake on other previews and in local tools. Claude Code only on a developer's machine |
| `Embeddings` | AI Gateway, fake | Gateway on prod, local stages, and opted-in previews. The fake on other previews and in local tools |

An adapter only sends the request and returns the raw output and token counts. The port's `make` does the rest for every adapter: it applies the adapter's timeout, decodes the output with the request's Effect Schema, counts tokens in `stargrep_ai_tokens`, and opens the span. Input counts cached input too. An adapter whose provider reports its prompt cache, as the Claude Code CLI does, also returns the shares read from and written to the cache, which `stargrep_ai_cached_tokens` counts. Output counts thinking too, and `stargrep_ai_reasoning_tokens` counts the share of it the model spent thinking, when the Gateway or the CLI reports it. The Claude Code adapter names its model `claude-code/` and the model it was asked for, such as `claude-code/sonnet`, so a receipt it wrote never reads as the Gateway's. So every adapter fails with the same typed errors: `AiOutputInvalid`, `AiRefused`, `AiRequestFailed`, `AiUnavailable`, `AiTimeout`, and `AiModelNotFound`. `AiRefused` is a model that declined the prompt, such as when Haiku's safeguards flag a remote access trojan's README. The same prompt gets the same refusal. The Claude Code CLI prints a refusal as an error result with `stop_reason: "refusal"` and exits 1, so its adapter reads stdout before it judges the exit code. The AI SDK reports one as a `content-filter` finish, on a direct call and on a batch item alike. `AiUnavailable` is a failure the provider marks as worth a retry, such as a rate limit or a 5xx. The port never retries. The Gateway adapter lets the AI SDK retry each provider request three times, so `embedMany` retries only the request that failed. The SDK waits as long as the provider's `retry-after` asks when that is under a minute, and backs off exponentially from two seconds otherwise. The port's timeout covers the whole call, retries included, and a call that spends it fails with `AiTimeout`. No caller retries a model call again. Gateway batch API calls have no SDK retries, so the adapter retries those itself. Error fields hold short facts such as an exit code or an HTTP status, never a prompt, README text, model output, or key.

`TextGeneration.generateBatch` answers many prompts with one schema and streams each item with its answer as soon as that answer is ready, so one bad answer fails only its own repo and a caller can keep an answer before the slowest one arrives. The gateway adapter submits one AI Gateway batch job through the AI SDK's experimental batch API, which accepts text requests only. The job's idempotency key is a hash of the requests, so a run that stops while it waits finds the same job again instead of paying for a second one. A replayed job returns its stored failures too, so a failed item gets one direct call. Adapters without a batch API, and a batch of one prompt, answer each prompt with its own call. The prefill does not go through `generateBatch`. It uses the `Batches` port in `@stargrep/ai/batches`, which splits the batch API where a caller must record the provider's batch ID: `submit` starts the batch or finds the one an earlier submit of the same request started, and `collect` waits for it and reads every item. `collect` tells apart a batch the provider answered, one it failed, and one it does not know, and any other failure says nothing about the batch. A batch the provider failed after it completed some items is read anyway, since those answers are billed, and comes back answered with the other items missing. It counts as failed only when it completed none or its results cannot be read. `Gateway.layerBatches` serves it, with a deadline on each call and a status poll that backs off to a minute between tries.

Deployed code uses the layers from `@stargrep/ai/gateway`. `layer` serves both ports with the models in `models.ts` and reads `AI_GATEWAY_API_KEY` through `layerProviderConfig`. `layerModels` serves both ports with a given provider and options. Each Worker reads `aiSetup` from `@stargrep/runtime/ai-key` once. It holds `STARGREP_AI_PROVIDER` and, for the gateway, the key. `layerModels` there serves the main Worker's summaries and embeddings through `layerModelsForKey`, with no batch API, and `layerSearch` serves the web Worker's planner and embeddings through `layerSearchForKey`. Without a key, or with an empty one, both gateway layers serve the ports with calls that fail with `AiKeyMissing`. With `fake`, both serve the stand-ins from `@stargrep/ai/stand-in` instead, and make no network call. A stand-in summary is the repo's description and the start of its README, with the facts its description, language, and topics state: kind and platform words, the language, each topic, a named alternative, and a stated deprecation. A stand-in embedding hashes the words under the model ID `fake/hash-embedding`, and the stand-in planner fails with `AiKeyMissing`, so search runs the words as typed. Local tools use `layer` from `@stargrep/ai/local` instead. It reads `AI_TEXT_PROVIDER` (`gateway`, `claude-code`, or `fake`) and `AI_EMBEDDINGS_PROVIDER` (`gateway` or `fake`), both `gateway` by default, and needs Bun to spawn the CLI.

**The Claude Code CLI is for local development only.** It runs `claude -p` with the developer's own subscription, for experiments, small eval runs, and summary samples. Anthropic's terms let a person use the unmodified Claude Code binary with their own subscription, but products and pipelines must use API keys. So deployed stages, CI, and bulk backfills always use the AI Gateway. Four checks enforce this.

| Check | What it stops |
|---|---|
| The `@stargrep/ai` exports map has no `./claude-code` entry | Code outside the package cannot build the harness without `@stargrep/ai/local` |
| `@stargrep/ai/local` fails with `AiProviderNotAllowed` at startup unless `STARGREP_MODE=local` and `CI` is unset | A local tool run in CI, or with the wrong environment, cannot reach the harness or the fakes |
| The Biome rule `packages/config/no-local-ai-import.grit` | Code in `apps/`, except tests, cannot import `@stargrep/ai/local`, `@stargrep/ai/fake`, `@stargrep/ai/summarize.fake`, `@stargrep/ai/stand-in`, or `@stargrep/ai/claude-code`. Deployed code reaches the stand-ins only through `@stargrep/runtime/ai-key`, which picks them by stage |
| The gateway layer's type does not require `ChildProcessSpawner` | A Worker that uses it never needs a process spawner, so typecheck catches a Worker wired to the local layer |

One bulk run uses the CLI. `prefill --pending` clears the Worker's summary backlog from a developer's machine, with Claude Code signed in with an API key, never a subscription. It refuses to start with any other text provider, so it never pays the Gateway past the daily summary cap.

**Embeddings from different models cannot be compared.** Each database has one embedding model and size. The one-row `embedding_settings` table records them, and a migration creates it. When the `Db` layer starts, it reads that row. In a fresh database it writes the configured model once, and when the configured model or size differs from the stored one, the layer fails with `EmbeddingModelConflict` before any query runs. Reading the row costs one query per `Db` build. The Worker builds `Db` per request, because a Hyperdrive socket opened in one request cannot serve another, and passes a `Ref` it keeps for the isolate's lifetime. So only an isolate's first request reads the row. So a local run configured with fake or foreign embeddings can never write into a database that production reads. Every embedding carries the ID of the model that made it, every `repos` row stores it in `embedding_model`, and `saveEmbedding` and `saveMetadataEmbeddings` refuse a vector from any model other than the stored one with `EmbeddingModelMismatch`. No `Db` function changes the stored model. To switch models on purpose, write a migration that clears `embedding` and `embedding_model` on every repo, sets `embedding_source` back to `summary`, and updates `embedding_settings`, then re-embed every repo with the new model.

## Sign-in

People sign in with GitHub through a GitHub App, whose manifest is `.github/app-manifest.json`. `packages/auth` configures Better Auth on `pg` and `drizzle-orm/node-postgres`, the same driver as `Db`, with its own pool for each request that connects only when a query runs. Better Auth serves `/auth/*`, because `/api/*` is the REST API. The session cookie carries a five-minute cache of the session, so most API calls read no session row. Linking a GitHub account reads the session row, so a cookie copied before sign-out cannot start a link. Better Auth stores the user's GitHub token encrypted. The main Worker binds the same `BETTER_AUTH_SECRET` and the app's client ID and secret, so it can read and refresh that token for the user's own work, as "GitHub access" explains.

A new session imports the GitHub account with the user's own token: `GET /user` for the login and profile, and one GraphQL call for the number of repos the account starred. It claims the `github_accounts` row for the user and queues a sync. If that import fails, the first `viewer` or `library` call claims the account again, without a sync. `viewer` only reads. The owner's page asks `triggerSync` for its own login each time it opens in a visible tab, so a star made on GitHub shows up when the user opens the search page. The sync page compares the library's size with the starred count to show progress.

A GitHub App cannot match callback URLs by wildcard, and each preview stage has its own host, `pr-<number>.stargrep.com`. So previews sign in through prod with Better Auth's `oAuthProxy` plugin. The preview sends GitHub's redirect to prod's callback and packs its own state, PKCE verifier included, into GitHub's `state`, encrypted with `AUTH_PROXY_SECRET`. Prod exchanges the code and redirects to the preview with the profile and tokens encrypted for 60 seconds. The preview creates the user and session in its own database. Prod creates neither. `AUTH_PROXY_ORIGIN` decides: unset, a stage signs in directly with the client secret, and set, a stage proxies through that origin and never reads the client secret.

Any branch's workflow can read the `preview` environment, so the design assumes the proxy secret leaks. Two guards on prod keep that leak inside preview databases. Prod installs the plugin without its endpoints and keeps only the hooks that forward a preview's sign-in, so prod has no route that turns a profile encrypted with the proxy secret into a session, under any provider ID. Prod forwards a sign-in only to its own origin or to a preview's web host, `previewHost` in `apps/worker/src/domain.ts`, so a forged state cannot send a user's GitHub token to another host, a preview's debug Worker included.

## Client

`src/routes/{-$login}.tsx` serves `/` and `/{login}`. `/` selects the viewer's stars or the demo account. `/@{login}` also accepts reserved path names, and `/search` redirects home. `/?user={login}` redirects to that login's page, so the hero's username field works as a plain form before the page hydrates. `/privacy` and `/developers` are text pages, so a GitHub user with either login lives at `/@privacy` or `/@developers`. The developers page shows how to add the MCP server to a coding agent and lists its tools, and a test holds that list to the contract's public procedures. Their components ship in the engine chunk, because a second lazy chunk makes the bundler move React, the router, and the UI kit out of the landing entry into a shared chunk, which costs the landing about 2 KB gzipped. `src/lib/load-page.ts` loads the session on the server and uses an isomorphic page loader for server rendering and browser navigation. `src/lib/page-view.ts` builds the shared presentation model. Route errors and missing pages use `src/components/problem-page.tsx`.

The server paints keyword matches for shared `?q=` links from stars already imported, and the answer by meaning too when the API's answer cache already holds one for the query. It never starts an import or spends model work for such a link. The browser loads the whole library into a TanStack DB collection, filters and sorts locally, and appends semantic results after keyword matches. A search can land before the first import creates the login's account, and `ACCOUNT_NOT_SYNCED` then counts as no stars yet, so the page shows the import and searches again once reading settles. The URL holds the query, language, sort, view, and open repo. The `stargrep-view` cookie preserves the chosen view for the server's next paint.

`src/lib/sync-watch.ts` polls visible pages every 10 seconds while waiting, 2 seconds while queued, 5 seconds while enrichment is incomplete, and 30 seconds when idle. Repos the daily summary cap queued and repos the summary policy holds back count as settled, because their summaries can be days away or never come, so a library waiting only on the cap polls at the idle rate and its status says how many summaries are queued for later. A visibility change wakes the poll. Unknown accounts trigger admission only in a visible browser tab. Refused triggers wait for the visitor to retry. The owner's page asks for its own sync on every open instead, and a refusal of that ask reads the status, so the library stays on screen. Library reloads follow the first import, a transition out of queued, or changes to total or read counts, rather than every poll.

Every page's header links to Stargrep's GitHub repo. The root route's session loader reads its star count on the server through `src/server/repo-stars.ts`, so the header paints it at first render and keeps it across navigations. The web Worker asks the main Worker's `stargrepStars` RPC method, which takes no input and reads only Stargrep's repo, by name and ID, with the server's token through `GitHubGate`. The Workers cache keeps the count for an hour, so a location asks at most once an hour. On a miss the render waits at most 750 milliseconds, and the read goes on under `waitUntil` to fill the cache. A failed or late read renders the link without a count, and so does a count under 10, since a handful of stars helps no one decide.

The home page starts with light landing chunks, then hydration immediately loads the stars engine. `bun run --cwd apps/web budget` enforces two named gzip budgets in `bun run check` and CI. The landing budget covers the entry, the stars route at `src/routes/{-$login}.tsx`, and their static dependencies. It allows 130,000 bytes and forbids Effect, TanStack DB, skullet, oRPC, and Base UI. Base UI is about 4 KB gzipped, and only the engine needs it, so the error pages and the sign-in problem tile ship in the engine chunk, and `buttonVariants` lives apart from `Button` in the UI kit. A module the landing reaches pulls in everything it imports, whichever chunk uses it. The engine budget covers `src/components/stars.tsx` and all its static dependencies, including shared landing chunks, once each. It allows 355,000 bytes. ## API and MCP

`packages/api` defines the oRPC contract, one router that implements it, the wire errors, and one instrumentation middleware. `apps/web` is a TanStack Start app on Workers, and `src/server.ts` serves the router three ways before TanStack Start sees the request.

- `/rpc` serves the typed oRPC client.
- `/api` serves REST, and `/openapi.json` is the OpenAPI document generated from the contract.
- `/mcp` serves every procedure as an MCP tool over Streamable HTTP, named by its `operationId`.

The procedures are `search`, `triggerSync`, `syncStatus`, `getRepo`, `stars`, `config`, `lookupFacets`, `viewer`, `library`, `monthlyPicks`, and `setMonthlyPicks`. The first seven are public. `config` returns the demo account, `STARGREP_DEMO_LOGIN` or `stefanofa` by default in `packages/api/src/public-config.ts`, with its default query and example queries. It builds no database or model service. `stars` returns a login's synced stars newest first, up to 1,000 a page, ordered by `starred_at` and repo ID so a cursor of the last row's time and ID continues the page. A partial index holds each account's current stars in that order, so a page reads only its own rows. The cursor decodes during input validation, so one Stargrep never issued answers `BAD_REQUEST` with its issues. It answers `ACCOUNT_NOT_SYNCED` when the login has no `github_accounts` row. `viewer`, `library`, `monthlyPicks`, and `setMonthlyPicks` read the session cookie and answer `UNAUTHORIZED` without one, so they stay out of the MCP tool list and the OpenAPI document until MCP clients can sign in. `monthlyPicks` says whether the signed-in user asked for the monthly picks email, and `setMonthlyPicks` turns it on or off. The account menu reads it on its first open, moves its switch at once, and moves it back when the save fails.

- **Atoms.** `search` takes an optional `filter`, a selection key such as `lang:rust subject:812|subject:9031 -kind:list`, of at most 8 groups of at most 8 atoms. It decodes at validation, so a key that names no atom, or one past those bounds, answers `BAD_REQUEST` with its issues before any work. Each atom becomes a predicate inside the search statement, so the bound keeps the statement's size fixed. Search reads the filter sorted and without repeats, so `applied` is the same whichever request filled the answer cache. A subject that does not exist, is private, or was rejected answers `BAD_REQUEST` too. Its answer lists `applied`, every atom the filter and the words of the query applied, with its mode, its span, and `relaxed` when a filter the words implied fell back to a boost. Search results and `getRepo` carry `facets`, every atom the repo holds with its label and `listed`, primary kind first. The library and `stars` pages carry each repo's `atoms`, the keys chips count, and one `labels` dictionary per response. `lookupFacets` finds atoms by the start of a name, closed values and listed subjects, most-held first, from the nightly counts, so an MCP client can build a filter without an enum of subjects in `tools/list`. It takes the name in a POST body, as search does, because it is what someone typed. `docs/knowledge.md` says what each read holds. `kind` is the primary kind atom.
- **Errors.** Every outcome other than success is a tagged error, such as `AccountNotSynced` from search, `RepoNotFound` from `Db`, or `RateLimited` from the rate limiter. The router maps domain tags through an exhaustive error table. The oRPC instrumentation middleware wraps every procedure, records its span and outcome, and bounds unexpected failures. A wire error has a stable `code`, such as `ACCOUNT_NOT_SYNCED` or `SERVICE_UNAVAILABLE`, a fixed message, and the call's `traceId` in `data`. `packages/api/src/errors.ts` holds each code's status and message. A failure outside the table becomes `INTERNAL_SERVER_ERROR` with the trace ID and no detail. oRPC decodes a request body before any middleware runs, so the web Worker's handler interceptor gives a body it cannot decode `BAD_REQUEST` with the request's trace ID, and MCP's own JSON-RPC errors, such as a parse error, carry it in `error.data`. Every API response, the OpenAPI document included, also has an `x-trace-id` header. A path under `/api`, `/rpc`, or `/mcp` that matches no procedure answers `NOT_FOUND` in that transport's error shape with the trace ID, and a failure outside the API answers `INTERNAL_SERVER_ERROR` the same way.
- **Services per request.** A Hyperdrive socket cannot outlive its request, so the web Worker builds `Db`, search, and sync services for each request, and only once a procedure has validated its input. A database outage then fails a search with `SERVICE_UNAVAILABLE`, while validation, the tool list, and the OpenAPI document keep working.
- **Tracing.** The middleware opens `Api.<procedure>` under the request's `Web.<transport>` span and sets `api.transport` and `stargrep.trace_id`. No span holds the query, the plan, or results. Cloudflare's own request span and invocation log record the full URL, so search takes its query in a POST body. Each response carries a `Server-Timing` header with the handler's total time and the procedure's time, so a stage measures transport overhead apart from the work.
- **Sync.** `triggerSync` claims the login's row in `sync_requests` and queues a `sync-stars` message only when the claim wins. A signed-in caller whose claimed account is that login asks as its owner. The claim is one `insert … on conflict do update … where` statement, which takes the row only when the login has no request or its request is at least one cooldown old, so of many triggers at once exactly one queues a job. `SyncRequests` sets the cooldown per requester. Anyone waits 10 minutes, and the owner waits 1 minute, so the owner's page loads queue at most one sync a minute and a trigger from anyone still waits 10 minutes after the owner's. While a request is queued, everyone waits 10 minutes for it, because its sync may still be reading pages and an account's first sync has no stop line. The owner's minute counts from the last finished or failed sync. A login synced inside the cooldown is not queued again either, and a request older than a day is forgotten. The owner's request is a full sync when the account's last full read is a week old and no request is queued, because only a full read finds unstars. A request still waiting in line has not started reading, so it does not hold back a full read that is due. Every other request is incremental. An incremental sync of an account that has synced before and has no new stars costs two GitHub requests, the account lookup and the first star page. An account that has never synced has no stop line, so its first sync reads every star whatever the mode. An owner's trigger whose sync fails to queue still answers the login's status and logs a warning. When the queue refuses the message or the main Worker dead-letters it, the row is marked `failed`. The message carries its request time, and a dead letter marks the row only while the row still holds that request, so a late dead letter never fails a newer claim. An hourly cron in the main Worker deletes requests older than a day, so the table holds about a day of logins. `syncStatus` reads the row and the account's star sync time and says `waiting`, `queued`, `failed`, `done`, `missing`, or `unknown`. It says `missing` while a `missing` row still answers triggers, for 10 minutes, unless the login has stars synced before a rename. The wire schema is a union keyed by `state`, so waiting always has a start and place in line, and done always has a sync time. Both procedures also return `enrichment`, the login's current stars counted as `total`, `read`, `failed`, and `queued`, the unread ones the daily summary cap deferred. The router reads it by login in one query over `stars` joined to `repos`, beside the sync status. Repos are shared, so `read` can start above zero. Right after `triggerSync` the total is 0, and reading goes on after `state` leaves `queued`, so reading is settled for now only when `state` is not `queued` and `read + failed + queued == total`, and finished once `queued` is 0 too.
- **Login check.** A signed-out request asks GitHub about the login before it claims it, with one GraphQL `repositoryOwner` request. The answer says whether the login exists, whether it is a user or an org, the account's facts, and its starred total. The web Worker has no GitHub token and no `GitHubGate` binding, so it calls `lookupOwner`, an RPC method on the main Worker's default export that the internet cannot reach, and gives up after 5 seconds. The lookup writes the account's facts and `starred_count`, and a first or full sync writes the total it counts too. `syncStatus` returns that total as `starredTotal`, so the page can show 640 of 2,431. A login GitHub does not have claims its row as `missing`, and `triggerSync` answers `LOGIN_NOT_FOUND` from that row without asking GitHub again until the 10-minute cooldown passes. Until then a page render reads `missing` from `syncStatus`, paints "github has no one called", and answers 404 with no GitHub request. An org cannot star repos, so its claim records an empty sync, starts at once, and answers `done` with a total of 0. Owners skip the lookup, because sign-in already read their account. "Admission" below gives the order of the steps.
- **Renamed logins.** GitHub lets a user rename their login, and Stargrep deletes nothing when one does. An account synced under the old login keeps answering `done` from `syncStatus` and keeps serving `stars/{old}`, because both read the account row. A trigger of the old login looks it up, finds no owner, and answers `LOGIN_NOT_FOUND`. A trigger of the new login upserts the account by its GitHub ID, which moves the row to the new login, so `stars/{new}` serves the stars and `stars/{old}` stops answering.
- **Admission.** Every sync a signed-out caller starts spends GitHub requests from the main Worker's token, so it first takes a turn in a rate line in Postgres, as "Admission" below explains. A signed-in caller's sync runs on their own token and takes no turn. `triggerSync` reads only the session for this, so a session it cannot read imports as a signed-out request.
- **Limits.** Each request works out its network once. A network is an IPv4 address, or the /64 of an IPv6 address, because one subscriber usually holds a whole /64. An IPv4-mapped IPv6 address counts as its IPv4 address, and a request without `cf-connecting-ip` is local and shares the network `unknown`. `Caller` carries the address and its key, the first 32 hex characters of an HMAC-SHA256 of the address under the stage's random `CALLER_KEY`. The address keys only the Workers rate limit bindings and is never stored or logged. Rows in Postgres hold the key.

  Five limits are exact, because they live in Postgres and hold across every Cloudflare location. The per-login claim above. The admission line. Each network's own line, the `caller/<key>` row of `rate_lines`, counted in GitHub units as "Admission" describes. Each network's pages of `stars`. And the model allowance. Every planner call and every query embedding that misses its cache takes one reservation in the network's `model/<key>` line, 30 calls a minute with a burst of 30, then one in `model/all`, 6,000 calls an hour with a burst of 600. Each reservation is one atomic upsert, so concurrent calls never share a slot. The network's line goes first, so a network past its own limit spends nothing from everyone's. A refused plan falls back to the words as typed and sets `search.plan.failure` to `ModelCallRefused`. A refused query embedding runs the plan it has on full text alone, with the filters and ranking the planner read, and reports `fallback` too, so a plan the model was paid for still shapes the answer. Either way the search still answers. A meter that cannot be read refuses the call the same way, because a refusal costs only quality. `stargrep_model_calls_refused` counts refusals by call and by line, never by network. An hourly cron deletes the lines the clock has passed, because a passed line reserves the same as no row, so the table holds only the networks that asked for something recently.

  A page of `stars` that misses the answer cache takes one reservation in the network's `stars/<key>` line, 60 pages a minute with a burst of 60, before it reads the account, so logins Stargrep never synced cost turns too. A new cursor always misses the cache, so without this line one network could read distinct pages as fast as the binding below let it through. A page costs a database read and no GitHub request or model call, so no line holds everyone's pages. Past the line, `stars` answers `TOO_MANY_REQUESTS`, and a line that cannot be read answers `SERVICE_UNAVAILABLE`, as the page read would.

  The Workers rate limit bindings are a cheap layer that turns away most of a burst before it costs anything. One `RateLimiter` service holds them: `SYNC_PER_CALLER` allows 5 syncs a minute per network and `SYNC_OVERALL` 60 for everyone, `SEARCH_PER_CALLER` 120 searches a minute per network, and `STARS_PER_CALLER` 60 pages of stars a minute per network. The owner's own sync takes from neither sync binding, because it runs on their token at most once a minute. `lookupFacets` takes from `SEARCH_PER_CALLER` too. `search` and `stars` take theirs only when the answer cache misses. Cloudflare counts each binding per location and only approximately. In a burst test on a preview stage, 350 searches from one network got through in about 30 seconds, and 150 pages of `stars` at distinct cursors in 2.3 seconds, so these are not caps. Past a binding, the procedure answers `TOO_MANY_REQUESTS`, and a binding that fails answers `SERVICE_UNAVAILABLE`.

  In front of the Workers, prod's zone has one rate limiting rule, so most of a flood never reaches a Worker. `apps/web/zone-rate-limit.ts` declares it, and only the `prod` stage deploys it. The rule has no hostname condition, so it also counts requests to the previews, which serve on the same zone, and one address's requests to prod and its previews share one count. It counts requests to `/api`, `/rpc`, `/mcp`, and `/auth` and everything under them, per IP and Cloudflare location. It reads those paths from `apiPrefixes` in `apps/web/src/server/api-prefixes.ts`, which the web Worker routes by, so a new transport is limited the day it is served. Past 150 requests in 10 seconds, Cloudflare answers 429 itself for the next 10 seconds. That answer is Cloudflare's HTML page, not the API's error, so the browser's `wireCode` reads any 429 the API didn't answer as `TOO_MANY_REQUESTS`. A blocked tab then says its network sent lots of requests, and remembers that refusal for a minute rather than the 10 minutes it keeps the others. Assets never reach a Worker, and `/icons` answers from the Workers cache or R2, so neither counts. Pages don't count either. A page renders in the web Worker on every request, but it calls the API in process, where the Workers bindings still count its searches and star pages. The zone is on the Free plan, which allows one rule, a 10 second period and block, IP counting only, and path matching without regular expressions. One tab on a preview stage made about 8 limited requests per 10 seconds while importing 805 stars, and 34 in its busiest 10 seconds while typing a query at 300 ms a key during the import. That pace is just slower than the 250 ms search debounce, so every key sends a search. So 150 leaves room for a few such tabs behind one address. The deploy owns the zone's whole `http_ratelimit` phase, and Alchemy adopts the zone itself without changing it and keeps it on destroy.

MCP currently exposes only public procedures and has no OAuth sign-in. Signed-in MCP would need an authorization server and bearer-token verification before calling session-required procedures.

### Admission

`SyncRequests` in `packages/core/src/stars/sync-requests.ts` admits every sync. A unit is one GitHub request. One flow admits every requester. `policyOf` turns each kind of requester into a policy: whose token pays for the sync, which network pays for the lookup and a first read, how long a finished sync holds the login, and whether a due weekly full read runs. A requester whose own token pays never waits in the `all` line.

#### The order of a signed-out request

1. It reads the login's row and the account. A sync that finished inside the 10-minute cooldown, or a request made inside it, answers its status. A `missing` row inside it answers `LOGIN_NOT_FOUND`.
2. It reads the wait of the `all` line. A turn more than 2 hours away answers `SYNC_BUSY`, before the request costs its network anything.
3. It reserves 1 unit on its network's line, then looks the login up. A lookup GitHub refuses for a spent budget answers `SYNC_BUSY`. A lookup GitHub answered pays 1 unit into the `all` line, forced, because the request is spent whatever comes of the sync.
4. It claims the row with the outcome already known. A missing login claims `missing`. An org claims and records an empty sync. A user claims `claimed`, takes its turn in the `all` line, sends its message, and moves the row to `pending` with `starts_at`. A turn the `all` line refuses releases the claim and answers `SYNC_BUSY`.

Anything that stops a request after its claim and before it sends its message, whether a refusal, a failed query, or an interruption, releases the row, or marks it `failed` when the queue refused the message, and releases every charge made after the claim. An interruption during the send waits for it to finish, so once the send starts only the queue's refusal undoes the claim. A request that loses the claim answers from the winner's row, so every trigger for a missing login answers `LOGIN_NOT_FOUND`. No request waits on another's lookup. Requests for one login at once each pay a lookup, and the network's line bounds that cost. A `claimed` row reads as `queued`, because its message goes out next. One narrow window answers `queued` with no job behind it: a trigger that reads a claim whose turn the `all` line then refuses. The request checked the line's wait just before its claim, so a refusal there means the line filled within that moment. The message goes out before the row moves to `pending`, so a crash in between leaves a `claimed` row that reads as `queued` while its job waits in the queue.

The owner skips the lookup and the network line, never waits, and reserves nothing in the `all` line, because their sync runs on their own token. A held row answers its status. The owner's claim takes over a request still waiting in line, and its sync is a full read when one is due. So a visitor who signs in from "is this you? skip the wait" gets their sync queued at once, on their token.

A signed-in request for another login follows the signed-out order without the `all` line. It skips the line's wait, keeps its network's charges for the lookup and a first read, and starts now. Like the owner's, its claim takes over a signed-out request it read as waiting in line, and that takeover charges no first read, which the waiting request's network already paid. A signed-out request that claims the login while a signed-in request looks it up wins, and the signed-in request answers from its row. The lookup still runs on the server's token and pays its unit into the `all` line.

#### The lines

`rate_lines` keeps each line as one time, `busy_until`, the generic cell rate algorithm with weighted cells. `packages/core/src/limits/rate-line.ts` names every line and holds its rate: the units it pays out per period, its burst, and how long a reservation may wait. A line's burst is how many one-unit reservations start at once when it is clear, so a reservation starts once the line owes at most its burst less one unit. A heavier reservation starts on the same terms and can leave the line owing more than its burst. It is one `insert … on conflict do update … where` statement, so concurrent reservations queue on the row lock and never get the same start. A forced reservation never refuses, for work that pays into a line but never waits. A reservation returns a receipt with the time by which the line has paid out its cost, and a release gives back only the part of that cost still due when the release runs. A release can also give back only the end of a reservation, such as the units a sync did not use. So a release that lands late, such as a queue refusal after its charge has drained, never credits work reserved after it. Every write to a line is a reservation or a release, and each line keeps a running total of the time given back from it. A release takes everything given back since its reservation as having been ahead of it, so time given back behind it makes the release smaller, never larger. The prune deletes a line only once it has paid out every reservation on it, and a recreated line is a new generation, so a receipt from the deleted one releases nothing into it. An hourly cron in the main Worker deletes the lines the clock has passed, which reserve the same as no row.

- **The `all` line.** It holds every signed-out sync. `githubAll` pays out 80% of `GITHUB_BUDGET_SHARE` of the token's 5,000 REST requests an hour, 3,600 units on the App's share of 0.9 and 2,000 on a personal token's 0.5, with a burst of 200. Both Workers bind the same share. The other 20% of the share is left to enrichment. A signed-in user's sync pays into the `all` line only for the requests that fell back to the server's token, after it runs, and never waits in it. Enrichment never pays into the `all` line, on either token. Its requests on the server's token, a user's fallbacks included, come out of the 20% left to enrichment. Lookups and counts spend GitHub's separate GraphQL window, so counting them as units overcounts on purpose.
- **A network's line.** `githubNetwork` pays out 150 units an hour with a burst of 150, and a reservation there never waits. Every signed-out lookup takes 1 unit, so a network that owes its burst gets `TOO_MANY_REQUESTS` before any lookup or claim. A login that never synced also puts its first read on its network, after the lookup prices it. That charge is refused once the network already owes its burst, so a network starts one huge import at a time, and a 100,000-star import holds its network for about 6 hours. A first read goes back to the network when anything stops the request before its message goes out, such as a turn the `all` line refuses. "Limits" says how the network key is made.

#### The cost model

`costOf` prices a sync before it runs, and its test lists sample prices. A first or full read costs the account read, two GraphQL counts, and one request per page of 100 stars, 28 units for 2,431 stars. An incremental read stops at the first star older than the newest one stored, so it costs the account read and the pages that hold the stars added since, 2 units when nothing is new. Admission prices a sync from the lookup's starred total. The price is an estimate. Stars removed or starred again since the last full read, stars swapped at an unchanged total, and a stale `starred_count` all move it, so each sync reconciles after it runs.

#### Reconciliation

The `sync-stars` message carries `reserved`, the units admission put in the `all` line for the sync's own requests, without the lookup, and the line's receipt for them. A signed-in user's message reserves nothing. The consumer runs each message over `TokenGate.counting` on the server's gate, which counts each request sent on the server's token, the GitHub client's retries and failed requests included. A request on the user's token is not counted. After each delivery, whether it succeeded or failed, the consumer hands the count to `SyncRequests.billDelivery`, which bills the `all` line:

- A first delivery bills what the sync spent past its reservation as a forced reservation. When it spent less, it releases the end of the reservation it did not use through the receipt, so it gives back only what the line still owes for those units. A delivery that settles after the line paid its reservation out gives back nothing.
- A later delivery bills its whole count.
- A deferred message goes out again without `reserved`, which `SyncRequests.resent` strips, because its first delivery already settled it.
- A message without `reserved`, such as one from the debug Worker, bills its whole count. A message queued before receipts carries only the units, so it bills what it spent past them and gives nothing back.

So a dead-lettered message is already settled. A message the queue refuses at admission gives its reservation and its network's first read back at once. A reconciliation that fails to write is logged, and the message still settles, because a retry would read GitHub again. `GitHubGate`'s share stays the hard cap.

#### Waiting

A request records `starts_at` when its message is sent, set to now or to the start of its turn. When the turn starts later than now, the message goes out at once with `delaySeconds` set to the wait. `syncStatus` says `waiting`, with `startsAt` and how many waiting syncs start before it, and turns `queued` at `startsAt`. The claim's cooldown counts from `starts_at`, so a waiting login is not claimed again, except by its owner. The waiting message still runs after the owner's sync, which costs one more incremental sync. A request that is queued and no longer waiting holds the owner for its 10 minutes, as "Sync" says.

`stargrep_sync_admissions` counts each decision: `started`, `waiting`, `deduped`, `org`, `not-found`, `caller-limit`, `line-full`, `github-budget`, and `lookup-failed`. The `SyncRequests.request` span carries the decision, the cost, and the wait.

## Caching

| Layer | What it caches |
|---|---|
| Browser | The user's library in TanStack DB |
| Workers cache | Demo search answers and first rendered answers, fresh for 5 minutes and served stale for up to a day during refresh. Public `stars` pages for 10 seconds. Stargrep's own GitHub star count for the header, for an hour, or 10 minutes after a read that got none |
| KV | Query plans and query embeddings, through the `SearchCache` port |
| Postgres | Summaries and embeddings, shared across accounts |
| R2 | README text by object ID, so GitHub serves each README once |
| R2 and the Workers cache | Repo icons as WebP, keyed by output version plus the git blob ID or the SHA-256 of the source bytes. The web Worker serves them at `/icons/<key>` on its own origin, through `caches.default`, with `immutable` caching. A change to the normalized output, or to what the normalizer rejects, bumps the version, so an icon URL never shows other bytes and a re-check never reuses an icon the new rules reject. The icon backfill counts a row whose key has another version as due, and every version stays servable until that row's next check |

The landing page answers the demo account's default query at first paint, and its server render calls `search` in the same Worker over `/rpc`. The web Worker keeps the first answer it renders beside the demo's search answers, under the same windows, and never when the planner fell back. Its key names the library revision, the sync time and read counts from `syncStatus`, so a completed sync or a newly read star answers again, and a per-build ID, so a deploy never serves a view an older page model built. Its freshness runs from when the API stored the search answer it holds, which the API sends as `x-answer-stored-at`, so an answer the API served stale is never kept as fresh. A render on a hit reads the sync and the cache, and the page answers with `x-answer-cache` and `server-timing` too. The browser asks for the semantic answer again once its library settles on another revision. So the answer cache lives in the API package, not in front of HTTP GETs, and every transport gets it. `packages/api/src/answer-cache.ts` owns the policy: how long an answer stays fresh, the refresh, the `x-answer-cache` header, and the `stargrep_answer_cache` metric. The `AnswerCache` port only stores. `search` keeps answers only for the demo login, compared without case, in the `stars` scope, keyed by login, scope, limit, the normalized filter, and the query trimmed, collapsed, and lowercased as the plan cache keys it. The filter's key sorts its atoms and groups, so the same atoms in another order share an answer and a filtered search never receives an unfiltered one. A hit builds no database, search, or model service. An answer older than 5 minutes is still served for up to a day while a refresh runs through the request's `background`. The web Worker runs it under `waitUntil` from `cloudflare:workers` with a freshly built request layer, because the request's own services close with its response, and gives up after 25 seconds. A stale answer starts at most one refresh per key per isolate every 5 minutes, however the refresh ends. A refresh that fails with an error the API answers below 500, such as a filter by a subject curation has since rejected, deletes the stale answer, so the next request gets that error rather than a day of stale answers. An answer the planner could not plan, `planSource: "fallback"`, is never kept, so after such a refresh the stale answer stays and the next refresh waits 5 minutes. `stars` reads and caches pages of 100 stars for any limit up to 100 and pages of 1,000 above it, keyed by login, page size, and cursor, and answers the first `limit` repos with `nextCursor` at the last one it answered. So a client cannot miss the cache by asking for another limit. `caches.default` holds the answers under the request's origin, because result icons carry absolute URLs, and under a version made of the planner and embedding models the stage's provider serves, `PlannerPrompt.version`, and `Compile.version`, so a deploy that changes any of them starts cold. `searchModels` in `packages/runtime/src/ai-key.ts` names those models from the same `AiSetup` that `layerSearch` serves, so a preview that switches between the fakes and the gateway never serves the other provider's answers. A cached answer never takes from the caller's rate limit. Each cached procedure answers with `x-answer-cache: hit`, `stale`, or `miss`, and `stargrep_answer_cache` counts them. `config` answers with `cache-control: public, max-age=300` and `stars` with `public, max-age=10`. A shared link with any other query paints without a search. The server paints its `?q=` keyword matches from a library an import has written, and reads the answer by meaning with `cachedSearch` in `packages/api/src/router.ts`. That read decodes its input as `search` does, uses `search`'s key, demo rule, and windows, and answers `hit`, `stale`, or `miss`. It builds no service, takes no rate limit turn, and starts no refresh, so a shared link with a custom query spends no model work during server rendering. The web Worker calls it in process, and no transport serves it. On a hit the page paints the answer, and the browser does not search for it again. On a stale answer the page paints it too, and the browser asks `search`, which serves the stale answer and starts the refresh, so the answer stays on screen until the new one lands. On a miss the page paints keyword matches alone, and the browser asks for the search by meaning through the API. The page answers with `x-answer-cache` for the read. The demo default query can call search on a cache miss. The server also looks up the repo its `?repo=` opens, so the panel opens as the page hydrates.

## Product analytics

Prod sends product events, model usage, and errors to PostHog, project 740269 on US Cloud. Every other stage sends nothing. The project token is public, so it lives in `packages/analytics/src/project.ts`, and no stage binds a secret for PostHog.

`packages/analytics` holds the port. `Analytics` is a `Context.Reference` whose default sink drops every event, so tests, local tools, and every stage but prod need no layer. `CurrentActor`, another reference, names who an event is about: `User` with the Better Auth user ID, `Network` with the caller key "Limits" describes, or `Stargrep` for work no visitor asked for in that moment. `Event` is a tagged union of every event Stargrep sends, and no case has a field for a query, a prompt, model output, a README, a token, or an address, so no caller can send one. `layerMemory` is the fake tests read events from.

Each Worker binds `STARGREP_STAGE`. `layer` in `packages/runtime/src/analytics.ts` gives prod the PostHog sink and the error logger, and every other stage, a Worker without the binding included, an empty layer.

- **One request per run.** The PostHog layer keeps a run's events in memory and sends them in one request to `https://us.i.posthog.com/batch/` when the run's scope closes. A run is one API request, one sign-in request, one background answer refresh, one queue batch, or one cron run. The send runs after the response under `waitUntil`, so no request waits on PostHog. A Worker invocation holds at most six connections, so one request per run leaves the rest to the database, R2, and the queues. A send that fails or takes more than 10 seconds is logged as a warning and its events are dropped. A run keeps at most 1,000 events.
- **Who an event names.** PostHog's `distinct_id` is the user ID for a signed-in user. For anyone else it is the first 32 hex characters of a SHA-256 of the caller key, so it matches no row in Postgres, and the address never leaves the Worker. Work no visitor started, such as enrichment and the crons, is `stargrep`. Only users get a person profile. The web Worker names every API request's network, and a handler that knows more names the user. A signed-out sync's message carries its caller key, so its end names the same network as its start.
- **Every event carries `stage`.** Only prod sends, so it reads `prod`.

| Event | Sent by | Properties |
|---|---|---|
| `signed_up` | Better Auth's user-create hook, once per new user | none |
| `monthly_picks_opted_in` | `setMonthlyPicks`, when it adds the user to the waitlist | `$set` of the person property `monthly_picks` to true, so the waitlist is the count of persons with it |
| `monthly_picks_opted_out` | `setMonthlyPicks`, when it takes the user off the waitlist | `$set` of `monthly_picks` to false |
| `stars_import_started` | admission, once the sync's message is queued | `stars` (the starred total admission priced the import from, null before any lookup), `signed_in`, `mode`, `first_import`, `wait_seconds` |
| `stars_import_finished` | the `sync-stars` consumer, after a sync succeeds | `stars` (stars the sync listed), `added`, `enqueued`, `signed_in`, `mode`, `duration_seconds`, `since_request_seconds` |
| `search` | the `search` procedure, for every search a transport answers, a cached one included | `plan_source`, `results`, `latency_ms`, `answer_cache` (`hit`, `stale`, `miss`, or `none` for a search the cache never keeps), `cache_hit`, `transport` |
| `summary_generated` | `EnrichRepo`, once per summary it saves | `model` |
| `$ai_generation` | the `TextGeneration` port, once per call | `$ai_provider`, `$ai_model`, `$ai_span_name` (`summary` or `plan`), `$ai_trace_id`, `$ai_latency`, `$ai_input_tokens`, `$ai_output_tokens`, the cache token counts, `$ai_total_cost_usd`, `$ai_is_error`, `$ai_error` |
| `$ai_embedding` | the `Embeddings` port, once per call | the same, with input tokens only and `$ai_span_name` `repo` or `query` |
| `$exception` | the error logger, for each error-level log | `$exception_list`, `source` (the log's message), `trace_id`, and the log's `queue` and error tag (`error_tag`) when it names them |
| `github_star_clicked` | the browser, when a visitor clicks the header's star on GitHub link | none |

Model calls are for spend. The port's `make` sends every call whatever its outcome, so a call that timed out still shows. The Gateway reports what it billed in the answer's provider metadata as a decimal string. The adapter sends `gatewayCost`, which adds any surcharge, else `cost`, with `$ai_cost_passthrough`. Without either, PostHog prices the call from the vendor, the model, and the tokens. Batch API calls run only from local tools, which send nothing. A search's planner and query embedding name the searcher, and enrichment's calls name `stargrep`.

A failure logged at error level is one no caller handled, so the logger turns each into an exception event. Every boundary that catches an unexpected failure already logs it that way: API failures outside the error map, mapped failures of 500 and up, failures outside the API and in sign-in, page loaders, the web Worker's top-level handler, the crons, and dead letters. A queue batch whose handler fails, such as one whose runtime layers could not build, is logged as `Queue <name> batch failed`. The event takes each failure's type, message, and stack from the log's cause. Stargrep's errors build their messages from bounded fields, and the event cuts a message at 1,000 characters.

The browser loads `posthog-js` only on `stargrep.com`, so previews, `localhost`, and tests never load it. The root shell starts it once the page hydrates, and it loads in a chunk of its own when the browser is idle, so its loader adds about 640 bytes to the landing chunk, which both budgets count, and `posthog-js` itself, about 123,000 bytes, counts in neither. It sends through PostHog's managed reverse proxy at `tortilla.stargrep.com`, a CNAME on Stargrep's zone that ad blockers do not list. It runs in cookieless mode, so it keeps no cookie and nothing in local or session storage, and PostHog's servers hash each visitor instead. So no banner asks for consent. It captures a pageview on load and on each path change, a pageleave, a click on the header's star on GitHub link, and every error the route's error page or the window's error events report, each with `stage`. It uses the build that fetches no script from PostHog, so nothing such as session replay can load later.

What is never sent:

- The words of a search, from the server or the browser. The browser sends every URL without its query string and fragment, a referrer's and an error message's included, so a page's `?q=`, its filters, and its open repo stay behind. `before_send` does this in `apps/web/src/lib/analytics.ts`, and a test checks it.
- Prompts, README text, model output, keys, and tokens.
- Addresses and caller keys. The hash of a caller key names a network.
- GitHub logins. No server event names the account it is about. A page view sends its path, such as `/ada`, which names the public page the visitor opened.
- Clicks, text, or input from autocapture, session replays, surveys, and feature flag requests. The browser turns each off.

The repo is the source of truth. Each concern has one file or folder that defines it.

| Concern | Source of truth |

| Neon projects and branches | `infra/database.run.ts` owns the projects. Each stage's branch is declared with the Hyperdrive that binds it, in `apps/worker/src/database.ts`, which also decides that `prod` keeps its branch on destroy and that preview branches expire |

| Models and prompts | `packages/ai` |
| Repo knowledge | `packages/knowledge/src/registry.ts` defines the dimensions, closed values, and roles. It generates `registry.sql` and the facets block the summary prompt will carry, and tests fail when a copy drifts. `docs/knowledge.md` explains the model |
| Search metrics | `packages/core/src/search/metric-registry.ts` names each metric for the planner, and `packages/db/src/queries/search-statement.ts` maps its family to `repo_metrics` columns. Both use `MetricFamily`, so the compiler keeps `MetricFamily`, `metricColumns`, and `nouns` in step |
| Search quality | The query set and its expected results in the repo. CI runs the recorded recall fixture without model calls |
| GitHub App | Its manifest in the repo. Creating the app from it takes one click in the browser |

A deploy applies each migration in one transaction and sends each chunk between `--> statement-breakpoint` markers to Neon as its own round trip, a chunk of comments alone included, so a lock on a table the running Workers use lasts until the commit. From `20261107193409_knowledge` on, a migration locks a table that existed before it only in its last statement, which can be a `DO` block holding several commands. `knowledge-migration.test.ts` checks it. It splits each file with Alchemy's own `splitSqlStatements` and treats every `public` table that existed before the migration as one the Workers may use, so a table the migration creates may be locked anywhere. On a branch of prod, that migration held `repos` for 3 round trips, 645 ms from a laptop about 200 ms from Neon. A migration whose lock blocks reads, such as dropping a column, sets `lock_timeout`, because every read of the table queues behind it while it waits. `20261110095534_drop_repos_kind` sets 1 second. A long statement on `repos` then fails the deploy before the Workers deploy, and a rerun retries it. A Drizzle insert or select on `repos` names its columns, because the bare form names every column the schema has and fails on a running Worker while a migration that drops one runs ahead of the deploy. The Biome rule `packages/config/repos-named-columns.grit` enforces it, and `bun run check` runs it against `packages/config/fixtures/repos-named-columns`.

Some things stay outside the repo. Secret values live in Cloudflare secrets and GitHub Actions environment secrets, and the repo holds only their names. Only jobs on `main` can read the `production` environment's secrets. Previews read separate credentials from the `preview` environment. Account creation, billing plans, and domain registration are one-time manual steps, listed in `docs/setup.md`.

### Stages

The Alchemy program has two stacks, so no app stage's state holds a Neon project. `infra/database.run.ts` owns the projects in its only stage, `shared`. `infra/alchemy.run.ts` is the app stack, deployed once per stage: `pr-<number>` for each pull request and `prod` for `main`. Each app stage references one project and owns one branch of it, so destroying a stage deletes its branch and never the project. `prod` uses `stargrep-us-east`, and every preview stage uses `stargrep-previews-us-east`, both in `aws-us-east-1`, so a Neon key scoped to the previews project can't reach prod's branch. Only the deploy from `main` deploys `shared`. A pull request stage fails with a missing reference until `main` has deployed once.

`prod` deploys only the Worker, its database, the queues, R2 bucket, and Durable Object the pipeline needs, and the web Worker with its KV namespace. It serves on `stargrep.com`, and `www.stargrep.com` redirects there. The Worker holds the custom domain, and a zone route sends every path to the web Worker, because routes take precedence over custom domains. The web Worker passes `/health`, with any query string, to the Worker through a service binding, so the health check still reads the Worker's database connection. Cloudflare matches route patterns against the query string too, so a `/health` route would miss `/health?x=1`. Prod has no workers.dev URLs, so every request passes the zone's rules. A `pr-<number>` stage has none either. Its web Worker serves on the custom domain `pr-<number>.stargrep.com` and its debug Worker on `pr-<number>-debug.stargrep.com`. Each is one level under the zone, because the zone's Universal certificate covers only `*.stargrep.com`, and the `pr-` prefix keeps them apart from prod's names. Its main Worker has no URL, because the web Worker passes `/health` to it as in prod. Destroying a stage deletes each Worker, and Alchemy first detaches that Worker's own custom domains, which removes their DNS records. `stageHosting` in `apps/worker/src/domain.ts` holds these names per stage. Every stage other than prod also deploys a debug Worker with a queue and consumer, KV, R2, two Durable Objects, and an hourly cron, so the checks in `docs/setup.md` can drive them. Its routes take a bearer token that the stack generates per stage, and a Durable Object caps them at 300 units of work a minute.

Previews pay for no model calls. `stageSettings` gives each `pr-<number>` stage the provider `fake`, and prod and local stages the gateway. `withStageAi` in `packages/runtime/src/ai-key.ts` wraps the config the whole app stack reads. So a stage on the fakes never binds `AI_GATEWAY_API_KEY`, even when its deploy has one, and its Workers bind `STARGREP_AI_PROVIDER=fake`. A deploy with `STARGREP_AI_PROVIDER=gateway` opts a preview in, and the preview workflow sets it while the pull request has the `preview-ai` label, read from GitHub right before each deploy. Prod hides that variable, so its bindings stay the same whatever the deploy's environment holds. The stand-ins cost nothing, so opening a preview imports the demo account's real stars, and that import is how a preview gets real-looking data. A branch keeps the embedding model its first request recorded, so a preview picks its provider when it is created and keeps it. Every non-prod stage's output records `aiProvider`, and when the labels ask for another provider, the preview workflow destroys the stage and deploys it fresh. A preview therefore never holds more than one branch, and no request from one provider's Workers reaches the other provider's database.

Deployed stages keep Alchemy state in the Cloudflare account through `Cloudflare.state()`. Under `alchemy dev`, state stays in `infra/.alchemy/` and the stage declares no Neon resources, so a local stage needs no credentials.

## Testing

- `packages/core` tests use `bun test` with in-memory layers. They cover behavior, such as "an unstarred repo gets `unstarred_at`", not internal calls. Time runs on `TestClock`, so tests never sleep. `packages/testing` provides `it.effect`, `it.live`, and `it.layer` for Bun Effect tests. Transport and runtime tests also run Effects at their framework boundaries. Typed database fixtures live under `@stargrep/db/testing`. `docs/effect.md` section 7 shows how to use it.
- `packages/db` runs each query test twice, on PGlite and on Postgres 17 with pgvector through `pg`. The `pg` run creates and migrates a database for each test file in the local container from the root `compose.yaml`, and CI starts the same container. The PGlite run starts each database from a migrated data directory that the first test process builds and keeps in the temp directory, keyed by the PGlite and pgvector versions and the migration files, because initdb takes seconds on a busy machine.
- `apps/web` and `apps/worker` tests run on workerd through `@cloudflare/vitest-plugin`. Both apps set `testTimeout` to 30 seconds to allow for workerd module loading. Workerd test files are named `*.workerd-test.ts`, which `bun test` never matches from any folder, and the vitest config includes only that pattern. `bunfig.toml` ignores `repos/`, so a root `bun test` runs the other `*.test.ts` and `*.test.tsx` files in the repo.
- The worker test command also runs `vitest.runtime.config.ts`. It bundles the real Worker through Alchemy and exercises its bindings, queues, Durable Objects, and per-invocation database layers on workerd with a separate migrated Postgres database.
- Web polling and reveal programs use `TestClock` in Bun tests, with separate DOM integration tests.
- A `*.test.tsx` file is a DOM test. The root `bunfig.toml` preloads `packages/testing/src/dom.ts`, which registers happy-dom when a `.test.tsx` file loads, before its imports. A `*.test.ts` file gets no DOM and keeps Bun's `fetch`, `Request` and `Response`.
- `bun test` runs with `--parallel`, not `--concurrent`, so a test that times out still interrupts its fiber and runs its finalizers.

## Settled by prototypes

These ran locally on 2026-11-03, with no cloud account.

- **Alchemy 2.0 beta covers every resource Stargrep uses.** Under `alchemy dev` with Bun, one local stage ran a Worker with a queue producer and consumer, a Durable Object, KV, R2, a cron, a Workflow, and Hyperdrive to a local Postgres. Neon projects, branches, roles, and connection strings and GitHub secrets exist in its source. State needs an explicit store. Stargrep uses `Cloudflare.state()`, so CI needs only a Cloudflare token.
- **TanStack Start, oRPC 2.0 beta, and Effect run together on workerd.** One procedure with an Effect Schema input and an Effect handler answered over RPC, REST, and MCP, and the OpenAPI spec generated. The client bundle stayed free of Effect with type-only contract imports. One runtime import of the contract added about 27 KB gzipped, so a lint rule enforces type-only imports. Every `@orpc/*` package pins `2.0.0-beta.48`, because npm's `latest` tags mix 1.x and different betas.
- **`drizzle-orm/effect-postgres` works on workerd with `prepare: false`, and Stargrep does not adopt it.** With default prepared statements, 68 of 360 transactions failed behind a transaction-mode pooler. Better Auth's adapter fails on it. `pg` measured no slower and serves both core and auth.
- **`drizzle-kit` does not emit `CREATE EXTENSION vector`.** The first migration adds it by hand.
- **The `bun test` helper works.** It lives in `packages/testing`, and its tests cover what the prototype checked.
