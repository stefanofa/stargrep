# Stargrep architecture

This doc explains how Stargrep is built and why. `docs/product.md` explains what it does. The Drizzle schema and oRPC contracts define the stored data and public API. This doc describes the running system.

## Principles

- **Headless core.** All domain logic lives in `packages/core` as Effect programs. Each program declares the services it needs, such as `Db`, `GitHub`, `TextGeneration`, `Embeddings`, `Queue`, and `BlobStore`. Core has no imports from TanStack Start, Cloudflare, or oRPC. `bun test` runs it with in-memory layers and no network.
- **Effect conventions.** `docs/effect.md` sets how services, layers, errors, schemas, config, tracing, and tests are written. It follows T3 Code's conventions, adapted to Workers and `bun test`.
- **Platforms are layers.** Each service has one production layer, such as `Queue` on Cloudflare Queues, and one in-memory layer for tests. Moving a service to another platform means writing one new layer. Core does not change.
- **Parse at the boundary.** Effect Schema parses GitHub responses, environment config, model output, and API input into domain types. Code inside trusts those types and does not validate again.
- **One schema library.** Every schema in our code is an Effect Schema. Our code never imports zod, even though some dependencies install it. Schemas leave our code in two places, each with one bridge. oRPC takes Effect schemas directly through `@orpc/effect`. `packages/ai` wraps a schema with `Schema.toStandardSchemaV1` and `Schema.toStandardJSONSchemaV1` before passing it to the AI SDK or to a coding-agent CLI.
- **Shared repos, per-user stars.** Each repo is fetched, summarized, and embedded once, however many accounts starred it. An account's stars are rows that point at shared repos.
- **GitHub numeric IDs as keys.** Accounts and repos are keyed by GitHub's numeric IDs. Logins and repo names change on rename.
- **Idempotent pipeline steps.** Every ingestion step converges to the same state when it runs twice. Queues retry, so steps must survive retries.

Production code runs on the Workers runtime, not Bun. Code in `apps/` and every package they import must avoid Bun-only APIs. Bun runs installs, scripts, and tests.

oRPC 2.0 and Alchemy 2.0 are betas, and Drizzle 1.0 is a release candidate. Pin one exact version of each and upgrade on purpose.

`Db` exposes query functions from `packages/db`, each returning an Effect with a typed error. It never exposes the Drizzle database object, so core does not import Drizzle types. Tests use `layerMemory` from `@stargrep/db/memory`, which runs the same migrations and query code on PGlite, Postgres compiled to WASM with pgvector, inside the test process. Transactions are a separate service. A driver change then touches only `packages/db`.

The `Db` service uses `pg` because Hyperdrive documents `pg` and because Better Auth's Drizzle adapter awaits queries, which only the promise-based driver supports. One driver then serves both core and auth. Drizzle's JIT row mapping stays off, because Workers block `new Function`.

TanStack DB holds the browser library. React holds view and request state. The server renders the stars page, and hydration loads the stars engine, including Effect and TanStack DB. The browser uses an Effect `Stream` to debounce search and cancel stale requests. API imports in client code are type-only, so the oRPC contract adds no runtime dependency.

App code talks to Postgres through Hyperdrive with a standard driver and uses no Neon-only APIs, so moving to another Postgres host is a dump and restore. Development and preview branches scale to zero. Production does not scale to zero, because a woken compute starts with an empty cache and the first vector searches then read from remote storage.

Every stage's database runs in `aws-us-east-1`, and the main Worker and the web Worker have the placement hint `aws:us-east-1`, so Cloudflare runs their `fetch` handlers in the data center nearest that region. A request crosses the distance to the caller once, and its queries stay near the database. Placement moves only `fetch` handlers. Cron triggers, queue consumers, and Durable Objects run where Cloudflare starts them, and the debug Worker has no placement.

## Data model

Better Auth owns `user`, `session`, `account`, and `verification`, declared in `packages/db/src/auth-schema.ts` so they migrate with the rest of the schema. Stargrep adds these tables.

| `repos` | GitHub repo ID | owner, name, GitHub node ID, description, topics, language, license, homepage, kind (`app`, `library`, `cli`, `framework`, `list`, and so on), created time, `pushed_at`, archived, README object ID from the latest facts fetch, summary with the README object ID it describes and the summary recipe that made it, keywords, `embedding halfvec`, embedding model, whether the embedding describes an older summary of the same README, full-text column, how many times enrichment failed since the repo was last read and when it last failed, and the knowledge columns: the input hash, the current receipt, `gone_at`, and one array of closed atoms per role and dimension |
| `repo_metrics` | GitHub repo ID | current totals and 30-day and 90-day changes for stars, forks, commits, active contributors, new contributors, merged pull requests, closed issues, and releases. Enrichment writes star and fork totals. Growth and activity rollups have no producer yet |

| `follows` | follower ID and followee ID | source (`github` or `stargrep`), created time |
| `collections` | ID | owner, slug, title, description, kind (`user` or `editorial`) |

| `api_usage` | key and day | request counts per procedure |

| `rate_lines` | line key | the row's generation, the time given back from the line in all, and the time until which it is busy: `all` for every signed-out sync, and `caller/<key>` for one network's lookups and first reads, and `model/all` and `model/<key>` for planner and query embedding calls, see "Admission" and "Limits" |

The knowledge tables (`receipts`, `extraction_batches`, `decisions`, `subjects`, `subject_labels`, `subject_canonical`, `subject_closure`, `subject_matches`, and `repo_facets`) hold what the summary model said about each repo, the curated vocabulary, and each repo's subject atoms. `docs/knowledge.md` explains them. Enrichment keeps every summary answer as a receipt, projection writes atoms and mints subjects, and a one-off backfill wrote legacy receipts for summaries made before receipts.

The schema also reserves follows, collections, search events, and API usage. Their presence does not mean the app imports follows, serves collections, or records search analytics.

## GitHub access

GitHub limits each user token to 5,000 requests per hour. That budget is shared with every other app the user authorized. The Stargrep GitHub App's installation gets its own 5,000 requests and 5,000 GraphQL points an hour, and more only past 20 repositories or 20 organization members. Stargrep uses incremental reads, content-addressed READMEs, and separate user and server budgets.

1. **Incremental sync.** A sync reads newest first and includes every star at its stop timestamp. An unchanged user sync costs an owner read and one star page. ETags do not help here. Each star list page embeds live repo stats such as `pushed_at`, so its ETag changes when any of its 100 repos changes, even when no star changed.
2. **README object IDs.** GraphQL returns the README's object ID with the repo. Stargrep fetches a README again only when that ID changes. A new summary recipe can also require a new summary. An object ID names fixed content, so R2 keeps each README under its ID, and a README already in R2 costs no request.
3. **The user's own token.** Work a signed-in user starts reads GitHub with their token: their own sync, the weekly full sync, an import of another login they start while signed in, and the facts batches and README reads that enrich the repos those syncs bring in. Stargrep takes at most 20% of what remained in each of the user's rate-limit windows when it opened, read from `x-ratelimit-remaining`. The user's gh CLI, IDE, and CI share the same 5,000 requests an hour, and a 3,000-star full sync needs about 33 of them.
4. **The server's token.** Prod reads with the Stargrep GitHub App's installation token, and previews and local stages with a personal token. It pays for signed-out syncs, account lookups, sweeps, crons, icons, and the part of a user's work that falls back from their token. Every signed-out sync first waits its turn in an admission line sized to the token's share, as "Admission" in "API and MCP" explains.

A user's token is used only for work that user started. Stargrep never pools user tokens to crawl other accounts, and never uses one for a sweep or a cron. The token never leaves the server. The main Worker reads it from Better Auth by user ID when a job sends its first GitHub request, and queue messages carry only the user ID.

`packages/github` sends requests one after another per token through a Durable Object. GitHub's best practices ask for serial requests per token, which keeps Stargrep under the secondary limit of 100 concurrent requests. An in-memory lock cannot enforce this across isolates. The sync reads the REST star list, which is faster per page than GraphQL `starredRepositories`. The object tracks remaining budget from response headers across Worker isolates. `packages/github/src/rate-limit.ts` classifies HTTP and GraphQL replies for the client, fallback gate, and installation-token mint. `packages/github/src/errors.ts` shares permanent-failure classification between enrichment and queue settlement.

## Ingestion pipeline

The sync and enrichment consumers are idempotent. A separate `fetch-icon` queue discovers and normalizes repo icons.

1. `sync-stars` fetches an account's star list newest first. It stops at the first star older than a star the last completed sync saw unchanged, so it reads every star that shares that star's `starred_at`. An account's first sync has no stop line, so it reads every star. After that, the owner's `viewer` call asks for a full sync once the last full read is a week old. For 3,000 stars a full sync takes 32 GitHub requests: two GraphQL owner reads and 30 REST pages. The first owner read supplies both the account facts and the initial count. Incremental user syncs and org syncs each spend one GraphQL point for owner facts instead of one REST account call. The admission lookup is a separate GraphQL point. Stars that are gone mark `unstarred_at`. The list pages by offset, so a full read counts the stars through GraphQL before and after. When the counts differ, the read shifted, and the sync writes what it read but skips the unstars and does not record the run. A star added and another removed at different page boundaries during one read leave the counts equal, so that read can hide one star until the next full sync. An org cannot star repos, so its count is zero without a GraphQL request. A finished sync only moves the account's sync time forward, so an older run that finishes last cannot pull the stop line back. It enqueues the repos that need enrichment after it reads the last page, because enrichment shares the token's one request at a time and would otherwise hold it between the sync's pages.
2. `enrich-repo` runs for repos that are new or whose README object ID or other prompt inputs changed. It stores the README in R2, keeps the model's answer as a receipt, writes the summary and keywords, projects the facts the answer states, and computes the embedding. It also fetches repo facts, such as license and homepage. `docs/knowledge.md` explains receipts and projection.

Bulk enrichment, such as a backfill of popular repos, uses the Gateway batch API for summaries and `embedMany` for embeddings. The batch path serves the CLI and backfills only, because a batch job can take minutes to hours.

`apps/worker` runs these queue consumers. `src/queues.ts` declares each queue, its dead-letter queue, and its consumer settings.

- A consumer decodes each message, calls one service method, and settles the message. Success acks it. `afterFailure` in `src/consumers/settle.ts` maps every failure tag to one settlement, and a new tag fails typecheck until it has a row.
- A failure that can pass on a second try, such as a lost database connection, a deadlock, a GitHub 5xx, a GitHub 403 that names no rate limit, or a model timeout, retries up to five times a minute apart, and then Cloudflare moves the message to the dead-letter queue. An enrichment failure that counts against the repo instead starts its backoff, so those retries settle as `Backoff` and the sweep owns the next try. A failure that cannot, such as a missing token or key, an unknown account, or a body that does not decode, goes to the dead-letter queue on its first attempt. A failure while the runtime layers build, such as a lost database connection or an embedding model conflict, fails the whole batch before any message is settled, and Alchemy retries every message in it.
- A spent token budget or a GitHub rate limit is not a failure. GitHub names the time the limit lifts, or asks for a minute when a secondary rate limit names no time, so the consumer sends the message again with that delay and acks the original. A long pause then spends none of the five retries.
- The `enrich-repo` consumer takes up to 100 messages per batch and runs one batch at a time. It runs and settles them 10 at a time, so a chunk's messages are acked or retried before the next chunk starts. Ten minutes after the batch starts, a chunk still running stops, and its messages and every later one retry, well before Cloudflare ends a queue invocation at 15 minutes. Deferrals are cached for the batch by the token that hit its limit. Each failure keeps that token even if a later request in the same job falls back. Later jobs consult the selected token's wait before sending. Signed-out chunks can skip the run, while a signed-in job can use its user's reset allowance even while the server still waits. The Worker's text-generation layer has no batch API, so `enrichRepos` answers each repo with its own model call. It saves each summary as its answer arrives, so a chunk the deadline stops keeps every summary it paid for, and its retry only embeds them. It reads each repo id once. A repo several accounts starred arrives once per account, and a later batch finds it enriched.
- GitHub answers each repo in a facts batch on its own. A repo it does not return, or reports as `FORBIDDEN`, settles as gone, and the rest of the batch enriches. The client logs the node IDs of forbidden repos. Any other GraphQL error fails the whole batch.
- A repo is read once it has a summary of its current README and an embedding, which is `unreadEnrichment` in `packages/db/src/schema.ts`, negated. Enrichment is also due for a read repo whose summary an older recipe made, or other prompt inputs than the ones `saveFacts` last saw, such as a new description or topic set. `saveFacts` stores those inputs as `input_hash`, and a saved summary records the hash it answered as `summary_input_hash`. `summaryRecipe` in `packages/ai/src/models.ts` versions the summary model, prompt, and output schema, and a test pins it to them. Such a repo stays read. Its new summary is saved as soon as it arrives, and its old embedding stays, marked `embedding_stale`, until the embedding of the new summary replaces it, so search keeps finding it and a failed embedding never costs a second summary. `pendingEnrichment` is the wider predicate, and the sweep and its partial index use it. A gone repo is never pending. `summary_recipe` defaults to the current recipe, and the partial index names it, so a recipe bump comes with a migration that rebuilds the index and changes that default. `EnrichRepo` counts a repo's own failures when each batch chunk finishes: gone or forbidden, no node ID, a README GitHub no longer serves, a 4xx other than 403 on its README, or model answers that do not decode. A fact the model wrote that does not decode never counts. A failure every repo would hit, such as a missing token or key, an outage, a rate limit, or a batch that aborts, never counts. Each counted failure adds one to `enrich_failures` and sets `enrich_retry_at` from `retryDelays` in `packages/core/src/repos/enrich-retry.ts`. A failure before the retry time has passed is a copy of one already counted and changes nothing. Saving the embedding sets both back. A pending repo with `enrichFailureCap` failures, 3, counts as failed, so a library's progress can reach its end.
- `enrich_retry_at` is also the attempt's lease. Before its paid summary calls, `EnrichRepo` leases the repos it will ask about, in one statement that takes only repos whose summary is due and that no other attempt holds. A repo due only for its embedding is never leased, so an attempt that planned a summary pays nothing once another attempt has saved one. It skips a repo it cannot lease as `Backoff`, so two consumers given the same repo make one paid call. A lease lasts `attemptLease`, 15 minutes, which outlasts the queue consumer's 10-minute deadline. An attempt that sends a provider batch of two or more prompts leases for the batch's timeout plus 15 minutes, 24 hours and 15 minutes on the Gateway, so no other attempt pays for a repo while the batch waits. The lease's end time names it, so capture clears only the lease its answer's attempt holds, saved or stale, and a late answer never frees a repo a later attempt holds. A failed call is settled while its attempt still holds the lease, before the chunk projects or embeds anything, in one statement. A counted failure adds one to `enrich_failures` and turns the lease into the failure's backoff, and any other failure gives the lease back. A paid answer Postgres refuses fails only its own repo as `AnswerNotSaved` and counts toward the cap, so its chunk-mates are still saved. An answer capture could not save for a reason any repo could hit, such as a lock timeout, a lost connection, or a deadlock, counts nothing and keeps its lease. The queue dead-letters both, so the sweep sends the repo again after its backoff or once the lease runs out, and a repo that just reached the cap is not paid for again. A run cut short keeps its lease until it runs out, so the repo waits for the sweep instead of being paid for twice. A batch run that dies holds its repos for the whole batch lease, and a rerun inside it skips them, so the batch it paid for is never collected. Once the lease runs out, the sweep or a rerun pays for those repos again. Resuming a paid batch is the prefill driver's job, with its own manifest.
- An incremental sync lists only new stars, so it never sends a pending repo again. A cron in `apps/worker/src/crons.ts` runs `EnrichRetry.sweep` every 10 minutes instead, with a 5-minute timeout. It sends at most 100 pending repos under the cap whose retry time has passed, the earliest first and then repos that never failed, such as one whose message was lost. A repo waits 10 minutes after its first failure and an hour after its second, so a repo GitHub forbids costs at most three lookups, each one node in a batched GraphQL request. A message that reaches a repo before its retry time, such as a queue retry of a counted failure or a second sweep send, settles as `Backoff` with no GitHub call. A partial index holds only pending repos under the cap, so capped repos never slow the sweep. A full sync or another account's first sync still sends a capped repo again.
- Each dead-letter queue has a consumer that logs the message ID, its attempts, and the IDs in its body, or only the body's type when the body does not decode. An enrich dead letter changes no failure count, because only `EnrichRepo` knows whether a failure was the repo's own. A sync dead letter marks its request `failed`. When that write fails, the dead letter retries up to five times a minute apart, and on its last attempt it is logged and acked, because a dead-letter queue has no dead-letter queue of its own.

The `GitHubGate` Durable Object holds the Worker's GitHub credential. Every GitHub request on the server's token from every isolate goes through it, so it sends them one at a time. It keeps the rate-limit windows GitHub reported in its storage and takes its share of each window from `GITHUB_BUDGET_SHARE`, so a restart keeps the windows and a new share applies at once. `STARGREP_GITHUB_SERVER_TOKEN` picks the credential: `app`, the default of the prod deploy, or `pat`, a personal token in `STARGREP_GITHUB_TOKEN` and the default everywhere else. Each Worker binds the kind it deployed with, and reads only that kind's credential. The share follows the token: 0.9 on the App, whose budget no one else spends, and 0.5 on a personal token, whose owner keeps half for their own tools. A preview stage may set another number above 0 and at most 1, and a `prod` deploy fails with any share but its token's. Requests and replies cross the RPC boundary as plain data, and the credential never leaves the object. A pull request stage may deploy without a token. It then binds no `GitHubGate`, and every GitHub call fails with `GitHubTokenMissing`.

The gate takes a `TokenSource` and reads its token once a request holds the gate, so a request that waited never sends one that expired meanwhile. A personal or user token is fixed. On the App, `AppToken.makeInstallationTokens` in `packages/github/src/app-token.ts` signs an RS256 JWT with WebCrypto and the App's client ID, finds the installation on the account that owns the App with `GET /app` and `GET /users/{owner}/installation`, and mints an hour's token with `POST /app/installations/{id}/access_tokens`. Installs on other accounts never change it. GitHub hands out the key as PKCS#1, which WebCrypto cannot import, so `app-jwt.ts` wraps it in PKCS#8. The token lives in memory only, and one state decides each request: use the held token, use it and start one refresh in the background in its last five minutes, wait while GitHub said to, or mint. The background refresh runs in a scope the object owns, and a request mints in the foreground only when no token has a minute left, so a slow or failing refresh delays no request. A 401 drops the held token and sends the request once more with a new one, because GitHub revokes an installation's tokens when its App is installed again, and a 404 for the known installation looks it up again. A rate limit on the App's endpoints defers the message until the time GitHub names, and no mint goes out before then. A refusal, such as a revoked key or a suspended App, fails the call with `GitHubTokenMissing` and logs the reason. `packages/github/src/rate-limit.ts` decides what counts as a rate limit, for the GitHub client, the fallback from a user's token, and the mint alike: `retry-after`, else the window's reset when nothing remains, else a minute.

A job a signed-in user started carries their user ID in its message: `userId` on `sync-stars` and on the `enrich-repo` messages that sync sends. `UserGates` in `apps/worker/src/user-gate.ts` gives the job a gate that reads the user's token once, through `GitHubTokens` in `packages/auth/src/tokens.ts`, and sends each request to the `UserGitHubGate` Durable Object named by that user ID. GitHub counts all of a user's tokens against one budget, so one object per user keeps their requests in order and their windows in storage, with `FallbackGate.userShare`, 0.2, as the share. The token comes with each call and is never stored. `FallbackGate.prefer` sends the job through the user's gate until the first of four reasons, then through `GitHubGate` for the rest of the job:

- `budget`: the user's share of the window is spent.
- `unauthorized`: GitHub answered 401, because the token expired or the user revoked the app.
- `rate-limited`: GitHub returned a classified rate limit with nothing remaining, because the user's own tools spent the window.
- `token-unavailable`: Better Auth gave no token: the user has no GitHub account, GitHub refused the refresh, or the read took more than 10 seconds.

The first move logs once, as a warning for every reason but `budget`, and counts `stargrep_github_fallbacks` by reason. A secondary rate limit leaves quota, so the client waits it out on the user's token. `GitHubTokens` builds a Better Auth with only the GitHub provider and token encryption, on one connection it closes before the read returns. Alchemy evaluates a Worker's props again each time the Worker starts, against that Worker's own bindings, so `tokenClientBindings` reads every value as optional and gives the same bindings at deploy and at start. Better Auth refreshes a token within five seconds of its expiry with the app's client secret and stores the new one encrypted. GitHub refuses a used or revoked refresh token with a 200 that names an error. Better Auth would then write back the refresh token it read, over the one a concurrent refresh just stored, so `githubProvider` in `packages/auth/src/auth.ts` fails a refresh that returns no access token before Better Auth writes anything. Jobs of one user in one invocation also share one token read, so they never refresh the same token twice. Previews sign in through prod and bind no client secret, so a preview's expired token falls back instead of refreshing.

The `sync-stars` consumer runs the messages of a batch at once, so a user's sync never waits behind syncs on the server's token. The `enrich-repo` consumer groups a batch by `userId` and enriches each group over its own gate, so a group that aborts fails only its own messages.

The main Worker has four crons in `apps/worker/src/crons.ts`. `*/10 * * * *` runs two sweeps from one handler, one for due enrichment and one that projects stale repo knowledge. `20 4 * * *` starts the icon backfill, `30 3 * * *` recounts the repos each subject holds and then runs the usage floor, and `40 * * * *` prunes admission requests and rate lines. Every cron runs on a sweep minute on purpose. Neon suspends a compute after 5 idle minutes, and a query at any other minute would leave no idle window, so the database would never scale to zero. A failed sweep logs its error and never stops the other.

## Search

Search normally combines full text and vectors. If the model allowance refuses the query embedding, it uses full text alone. Any other embedding failure fails the search with `SERVICE_UNAVAILABLE`. Full-text search and vector search run in one SQL query, and reciprocal rank fusion merges the two lists. Full text matches the words the user typed. The vector side embeds the planner's description of a matching repo, or the query itself when the planner is skipped. It keeps only repos within the embedding model's `maxMatchDistance` of the query, a cosine distance of 0.36 for `voyage/voyage-4` in `packages/ai/src/models.ts`, before the lists merge. Search reads the value from the model it runs, so the fake hash model in tests uses its own. Every query has nearest neighbors, so without that floor gibberish such as "dfsfgdsrg" came back with 20 results. `docs/evals.md` calibrates the floor. A repo whose name or `owner/name` equals a keyword query ranks first.

- **Your stars.** The candidate set is one account's stars, at most tens of thousands of rows. An exact vector scan over that set takes milliseconds, so this path uses no vector index.

### Query plans

A query such as "open source apps like Wispr Flow with growing contributors" needs filters and a ranking, not only text matching. The planner turns each natural-language query into a typed `QueryPlan`. Growth and activity metrics parse today but match nothing until a rollup producer fills `repo_metrics`.

- **Scope.** The public API accepts only `{ kind: "stars", login }`. Core rejects other scopes with `SearchScopeUnavailable`. The caller sets the scope, never the model.
- **Semantic text.** The text to embed. "Like Wispr Flow" becomes a description of what Wispr Flow does, because the product has no repo to compare against.
- **Filters.** Kind, license, language, archived, starred date, and bounds on any metric. A bound is strict or inclusive, so "more than 200 stars" leaves out a repo with exactly 200. Kinds, licenses, and languages become atoms, described under "Atoms in search" below. A language filter matches a repo written in that language or for it, from GitHub's language, a language topic, or the summary model's claims, because a Python package manager is often written in Rust. A JavaScript filter also matches TypeScript.
- **Ranking.** Relevance alone, or the best matches reordered by a metric such as 90-day contributor growth. A metric never lifts a repo that did not match into the results.

The planner is `anthropic/claude-haiku-5.5` with structured output and reasoning turned off. With reasoning on, a plan took 2.1 to 4.6 seconds from a laptop, and with it off 1.2 to 2.1 seconds. It chooses metrics from a registry in `packages/core/src/search/metric-registry.ts`. Each entry holds an ID, the description the model reads, and a family and variant, such as stars and 90-day growth, that `packages/db` turns into SQL over `repo_metrics`. The model never writes SQL. The plan is parsed at the boundary, and a plan that names an unknown metric is rejected. When the planner fails or returns a plan that does not parse, search runs the query as typed.

The planner sets only the filters a query states, and code holds it to that after decoding. A kind filter stays only when the query restricts the kind with a word such as "only" or "not". The model returns each language with the words from the query that named it, such as Python with "питоне". A language stays only when those words appear in the query and are the language's name, one of its aliases, or a word in a non-Latin script, such as "питоне" or "パイソン". In Chinese, Japanese, and Thai, which have no spaces between words, the words match anywhere in the text. So a language named in any script stays, and one quoted from a framework, such as Java from "spring boot", is dropped. A quote in a non-Latin script is trusted as naming the language, so a transliterated framework name, such as "लारावेल" for Laravel, can still keep a language filter. `packages/core/src/search/vocabulary.ts` holds the language names and aliases these guards read and the words that send a query to the planner. In the recall eval, filters the model inferred dropped relevant repos, such as Rich for "python framework for text user interfaces", because the summarizer called it a library. `docs/evals.md` has the numbers.

Search returns the values that ranked each result. Growth metrics remain unpopulated until a rollup producer exists.

### Atoms in search

Search filters and boosts by the atoms `docs/knowledge.md` describes. `compileQuery` in `packages/core/src/search/compile.ts` turns the query into atom groups. It is pure, so it reads no database and calls no model. `packages/db/src/queries/search.ts` turns the groups into predicates inside the one hybrid statement.

- **Clauses.** The compiler splits the words into clauses, one per cue word. A clause with no cue describes the results. "for", "in", "on", "with", "using", "built with", "runs on", and "written in" make a relation, "alternative to" and a trailing "alternative" make a comparison, and "not", "without", "no", "non", "except", and "excluding" negate. A relation, a comparison, or a negation reaches only its first run: either content words, which form label keys and split into alternatives at "or" and commas, or kind, platform, and status words that "or" or a comma joins. The words after that run describe neither the cue's target nor the results. So "no dependency cli tool" excludes "dependency" and leaves CLIs alone. "no-code", "non-blocking", and "no-std" are words, not negations. A generic noun such as "tool" or "repos" ends the words before it, as a kind word does, and names nothing.
- **Where closed atoms come from.** Languages and licenses come only from the planner's guarded output, as the filters above did, so a language word the planner did not report stays an ordinary word. A language or platform takes the role its relation names: "built with node" is `with:platform:node`, "runs on linux" is `runs-on:platform:linux`, and "written in rust" is `written-in:lang:rust`. "for", "in", and "on" name no role, so they reach every default role. A negated relation excludes that role alone. Kinds come from the planner's guarded kinds, or else from the last kind word "only" narrows in the clause that describes the results, so "only libraries for building apps" asks for libraries alone.
- **How each group applies.** `policy` in `compile.ts` is a table with one row per kind of run. Each row gives a mode, and a second mode for a clause "only" narrows, when "only" opens or ends it. Languages, licenses, relation targets, and a language or platform whose role the cue names filter. A negated run excludes. Platforms, comparisons, and bare subject words boost. Kind and status words apply only when "only" narrows them. A relation's words that a closed word cuts short, as "local" in "for local models", boost, because the closed word is most likely the noun they describe. "built with", "built on", and "made with" reach `with:` atoms alone. "with" and "using" can name a feature or a dependency, so they reach member and `with:` atoms both, and so does a bare negation such as "without electron". A boost is a third rank list, fused like full text and vectors, over the candidates those two found, so it reorders results and never removes one.
- **Subjects resolve in the statement.** A subject group applies only when every key names exactly one accepted public subject, which `knowledge_key_meanings` decides. The web server keeps every label key with an accepted meaning per isolate, read at most every 5 minutes (`acceptedKeysTtl`), and `search.hybrid` drops a group with a key outside that set before it writes any SQL. So a word no accepted subject holds costs nothing, and a subject accepted since the last read applies within 5 minutes. When every filter's keys are in the set, the statement also leaves out today's pipeline, and a key that turns out ambiguous passes every row of the probe shape. Full text and vectors see every word either way. The caller's explicit selection always filters, survives a refused query embedding, and fails the search with `FacetUnavailable` when it names a subject that does not exist, is private, or is rejected.
- **Closed atoms read `repos`.** A closed group is an array test on the `repos` row the statement already reads, ORed over every role the atom reaches, with the registry's expansions.
- **Subject filters read `repo_facets` in one of two shapes.** The statement holds three pipelines and runs one. Pipeline a is today's statement and runs when no subject filter resolved. Pipeline b, the index shape, reads the filter's matches from a GIN index and runs when they fit in the account's star count. `subjects.repo_count` skips that scan when the subject is broader than the library. Pipeline c, the probe shape, reads one `repo_facets` row per starred repo by primary key. A negated filter uses an anti-join in place of b.
- **Two known slow cases.** A subject broader than the library takes the probe shape. On a branch of prod with every subject accepted and 1,786 stars, two searches ran over the 3 ms target at p95, measured against today's statement. "apps without react" excludes such a subject, so it keeps most rows and ran 8.4 ms slower. "state management in react" filters on one and boosts the other words, and ran 3.7 ms slower. No subject is accepted in prod yet, so neither applies until curation accepts one.
- **The envelope.** Every row of the result carries what SQL resolved: each subject group's subjects, their labels, and the explicit subjects that are unavailable. `Search` returns them as `applied`, with the span of the query each atom came from.

`Compile.version` hashes the grammar and the policy, and the answer cache's version includes it. `bun run evals/recall.ts --accept-floor` measures recall with every subject accepted that the curation floor would accept, and `--bare-filters` adds the promotion of bare subjects to filters.

`QueryPlanner.plan` and `QueryPlanner.planWithModel` set `search.plan.source` on their spans to `keyword`, `cache`, `model`, or `fallback`. `Search` counts each search once in `stargrep_search_plans`, under the source of the plan it ran, so a keyword search that needed the planner counts as `model` or `cache`. A fallback also sets `search.plan.failure` to the error tag, such as `AiTimeout`, so traces show how often Haiku's tail latency sends a search to the typed text.

A repo name, an `owner/name`, or two plain words skip the planner. When such a query matches no name, no word, and no repo within that distance, search plans it with the model and runs that plan, which is how a misspelled name such as "zustnad" still finds `pmndrs/zustand`. Gibberish costs that one planner call and still finds nothing. Words that still match as a prefix of a word in the account's stars skip that call, because they are most likely a word the user is still typing, such as "zust" on the way to "zustand". The web client searches as the user types, and on the eval corpus the prefixes of 28 typed queries would call the planner 151 times without that rule and 34 times with it, 24 of them for typos. When the planner fails, search answers with nothing instead of running the same words again. A query with a word that can name a filter, such as a language, a kind, a license, "only", "more", or a number, goes to the planner, so "only MIT libraries" keeps its filters. The `SearchCache` port caches plans and query embeddings under a SHA-256 of the normalized query text. Each entry records when it expires, 30 days after it was written, so an old entry is a miss on every backend. A corrupt entry is a miss too. A plan with a date filter is reused only on the day it was planned, because "starred last year" depends on today. Tests use the memory layer. The web Worker keeps entries in a KV namespace and sets each one's KV expiration from its TTL, at least the 60 seconds KV accepts.

## AI providers

`packages/ai` has two ports, because they have different providers. Production summarizes with `anthropic/claude-haiku-5.5` and embeds with `voyage/voyage-4` at 1,024 dimensions. `docs/evals.md` records the bakeoff that chose them. The query planner uses `anthropic/claude-haiku-5.5` with reasoning off through its own `TextGeneration` layer, `layerPlannerTextGeneration`, with a 4-second timeout and no retries. `TextGeneration` turns a prompt into a value of an Effect Schema, for summaries, query plans, and later reranking. `Embeddings` turns texts into vectors. Core code imports only the ports.

| Port | Adapters | Where it runs |
|---|---|---|
| `TextGeneration` | AI Gateway, Claude Code CLI, fake | Gateway on prod, local stages, and opted-in previews. The fake on other previews and in local tools. Claude Code only on a developer's machine |
| `Embeddings` | AI Gateway, fake | Gateway on prod, local stages, and opted-in previews. The fake on other previews and in local tools |

An adapter only sends the request and returns the raw output and token counts. The port's `make` does the rest for every adapter: it applies the adapter's timeout, decodes the output with the request's Effect Schema, counts tokens in `stargrep_ai_tokens`, and opens the span. So every adapter fails with the same typed errors: `AiOutputInvalid`, `AiRequestFailed`, `AiUnavailable`, `AiTimeout`, and `AiModelNotFound`. `AiUnavailable` is a failure the provider marks as worth a retry, such as a rate limit or a 5xx. The port never retries. The Gateway adapter lets the AI SDK retry each provider request three times, so `embedMany` retries only the request that failed. The SDK waits as long as the provider's `retry-after` asks when that is under a minute, and backs off exponentially from two seconds otherwise. The port's timeout covers the whole call, retries included, and a call that spends it fails with `AiTimeout`. No caller retries a model call again. Gateway batch API calls have no SDK retries, so the adapter retries those itself. Error fields hold short facts such as an exit code or an HTTP status, never a prompt, README text, model output, or key.

`TextGeneration.generateBatch` answers many prompts with one schema and streams each item with its answer as soon as that answer is ready, so one bad answer fails only its own repo and a caller can keep an answer before the slowest one arrives. The gateway adapter submits one AI Gateway batch job through the AI SDK's experimental batch API, which accepts text requests only. The job's idempotency key is a hash of the requests, so a run that stops while it waits finds the same job again instead of paying for a second one. A replayed job returns its stored failures too, so a failed item gets one direct call. Adapters without a batch API, and a batch of one prompt, answer each prompt with its own call.

Deployed code uses the layers from `@stargrep/ai/gateway`. `layer` serves both ports with the models in `models.ts` and reads `AI_GATEWAY_API_KEY` through `layerProviderConfig`. `layerModels` serves both ports with a given provider and options. Each Worker reads `aiSetup` from `@stargrep/runtime/ai-key` once. It holds `STARGREP_AI_PROVIDER` and, for the gateway, the key. `layerModels` there serves the main Worker's summaries and embeddings through `layerModelsForKey`, with no batch API, and `layerSearch` serves the web Worker's planner and embeddings through `layerSearchForKey`. Without a key, or with an empty one, both gateway layers serve the ports with calls that fail with `AiKeyMissing`. With `fake`, both serve the stand-ins from `@stargrep/ai/stand-in` instead, and make no network call. A stand-in summary is the repo's description and the start of its README, with the facts its description, language, and topics state: kind and platform words, the language, each topic, a named alternative, and a stated deprecation. A stand-in embedding hashes the words under the model ID `fake/hash-embedding`, and the stand-in planner fails with `AiKeyMissing`, so search runs the words as typed. Local tools use `layer` from `@stargrep/ai/local` instead. It reads `AI_TEXT_PROVIDER` (`gateway`, `claude-code`, or `fake`) and `AI_EMBEDDINGS_PROVIDER` (`gateway` or `fake`), both `gateway` by default, and needs Bun to spawn the CLI.

**The Claude Code CLI is for local development only.** It runs `claude -p` with the developer's own subscription, for experiments, small eval runs, and summary samples. Anthropic's terms let a person use the unmodified Claude Code binary with their own subscription, but products and pipelines must use API keys. So deployed stages, CI, and bulk backfills always use the AI Gateway. Four checks enforce this.

| Check | What it stops |
|---|---|
| The `@stargrep/ai` exports map has no `./claude-code` entry | Code outside the package cannot build the harness without `@stargrep/ai/local` |
| `@stargrep/ai/local` fails with `AiProviderNotAllowed` at startup unless `STARGREP_MODE=local` and `CI` is unset | A local tool run in CI, or with the wrong environment, cannot reach the harness or the fakes |
| The Biome rule `packages/config/no-local-ai-import.grit` | Code in `apps/`, except tests, cannot import `@stargrep/ai/local`, `@stargrep/ai/fake`, `@stargrep/ai/summarize.fake`, `@stargrep/ai/stand-in`, or `@stargrep/ai/claude-code`. Deployed code reaches the stand-ins only through `@stargrep/runtime/ai-key`, which picks them by stage |
| The gateway layer's type does not require `ChildProcessSpawner` | A Worker that uses it never needs a process spawner, so typecheck catches a Worker wired to the local layer |

**Embeddings from different models cannot be compared.** Each database has one embedding model and size. The one-row `embedding_settings` table records them, and a migration creates it. When the `Db` layer starts, it reads that row. In a fresh database it writes the configured model once, and when the configured model or size differs from the stored one, the layer fails with `EmbeddingModelConflict` before any query runs. Reading the row costs one query per `Db` build. The Worker builds `Db` per request, because a Hyperdrive socket opened in one request cannot serve another, and passes a `Ref` it keeps for the isolate's lifetime. So only an isolate's first request reads the row. So a local run configured with fake or foreign embeddings can never write into a database that production reads. Every embedding carries the ID of the model that made it, every `repos` row stores it in `embedding_model`, and `saveEmbedding` refuses a vector from any model other than the stored one with `EmbeddingModelMismatch`. No `Db` function changes the stored model. To switch models on purpose, write a migration that clears `embedding` and `embedding_model` on every repo and updates `embedding_settings`, then re-embed every repo with the new model.

## Sign-in

People sign in with GitHub through a GitHub App, whose manifest is `.github/app-manifest.json`. `packages/auth` configures Better Auth on `pg` and `drizzle-orm/node-postgres`, the same driver as `Db`, with its own pool for each request that connects only when a query runs. Better Auth serves `/auth/*`, because `/api/*` is the REST API. The session cookie carries a five-minute cache of the session, so most API calls read no session row. Linking a GitHub account reads the session row, so a cookie copied before sign-out cannot start a link. Better Auth stores the user's GitHub token encrypted. The main Worker binds the same `BETTER_AUTH_SECRET` and the app's client ID and secret, so it can read and refresh that token for the user's own work, as "GitHub access" explains.

A new session imports the GitHub account with the user's own token: `GET /user` for the login and profile, and one GraphQL call for the number of repos the account starred. It claims the `github_accounts` row for the user and queues a sync. If that import fails, the first `viewer` or `library` call runs it again. Each `viewer` call also asks for a sync as the account's owner, so a star made on GitHub shows up when the user opens the search page. The page reads `syncStatus` only after `viewer` answers, so its first read already sees that sync as `queued`. The sync page compares the library's size with the starred count to show progress.

A GitHub App cannot match callback URLs by wildcard, and each preview stage has its own workers.dev host. So previews sign in through prod with Better Auth's `oAuthProxy` plugin. The preview sends GitHub's redirect to prod's callback and packs its own state, PKCE verifier included, into GitHub's `state`, encrypted with `AUTH_PROXY_SECRET`. Prod exchanges the code and redirects to the preview with the profile and tokens encrypted for 60 seconds. The preview creates the user and session in its own database. Prod creates neither. `AUTH_PROXY_ORIGIN` decides: unset, a stage signs in directly with the client secret, and set, a stage proxies through that origin and never reads the client secret.

Any branch's workflow can read the `preview` environment, so the design assumes the proxy secret leaks. Two guards on prod keep that leak inside preview databases. Prod installs the plugin without its endpoints and keeps only the hooks that forward a preview's sign-in, so prod has no route that turns a profile encrypted with the proxy secret into a session, under any provider ID. Prod forwards a sign-in only to its own origin or to a preview Worker of this account, so a forged state cannot send a user's GitHub token to another host.

## Client

`src/routes/{-$login}.tsx` serves `/` and `/{login}`. `/` selects the viewer's stars or the demo account. `/@{login}` also accepts reserved path names, and `/search` redirects home. `src/lib/load-page.ts` loads the session on the server and uses an isomorphic page loader for server rendering and browser navigation. `src/lib/page-view.ts` builds the shared presentation model. Route errors and missing pages use `src/components/problem-page.tsx`.

The server paints keyword matches for shared `?q=` links from stars already imported. It never starts an import or spends model work for such a link. The browser loads the whole library into a TanStack DB collection, filters and sorts locally, and appends semantic results after keyword matches. The URL holds the query, language, sort, view, and open repo. The `stargrep-view` cookie preserves the chosen view for the server's next paint.

`src/lib/sync-watch.ts` polls visible pages every 10 seconds while waiting, 2 seconds while queued, 5 seconds while enrichment is incomplete, and 30 seconds when idle. A visibility change wakes the poll. Unknown accounts trigger admission only in a visible browser tab. Refused triggers wait for the visitor to retry. Library reloads follow the first import, a transition out of queued, or changes to total or read counts, rather than every poll.

The home page starts with light landing chunks, then hydration immediately loads the stars engine. `bun run --cwd apps/web budget` enforces two named gzip budgets in `bun run check` and CI. The landing budget covers the entry, the stars route at `src/routes/{-$login}.tsx`, and their static dependencies. It allows 130,000 bytes and forbids Effect, TanStack DB, skullet, and oRPC. The engine budget covers `src/components/stars.tsx` and all its static dependencies, including shared landing chunks, once each. It allows 355,000 bytes. These are sums of each emitted JS chunk compressed with gzip level 9, excluding CSS and source maps.

## API and MCP

`packages/api` defines the oRPC contract, one router that implements it, the wire errors, and one instrumentation middleware. `apps/web` is a TanStack Start app on Workers, and `src/server.ts` serves the router three ways before TanStack Start sees the request.

- `/rpc` serves the typed oRPC client.
- `/api` serves REST, and `/openapi.json` is the OpenAPI document generated from the contract.
- `/mcp` serves every procedure as an MCP tool over Streamable HTTP, named by its `operationId`.

The procedures are `search`, `triggerSync`, `syncStatus`, `getRepo`, `stars`, `config`, `viewer`, and `library`. The first six are public. `config` returns the demo account, `STARGREP_DEMO_LOGIN` or `stefanofa` by default in `packages/api/src/public-config.ts`, with its default query and example queries. It builds no database or model service. `stars` returns a login's synced stars newest first, up to 1,000 a page, ordered by `starred_at` and repo ID so a cursor of the last row's time and ID continues the page. A partial index holds each account's current stars in that order, so a page reads only its own rows. The cursor decodes during input validation, so one Stargrep never issued answers `BAD_REQUEST` with its issues. It answers `ACCOUNT_NOT_SYNCED` when the login has no `github_accounts` row. `viewer` and `library` read the session cookie and answer `UNAUTHORIZED` without one, so they stay out of the MCP tool list and the OpenAPI document until MCP clients can sign in.

- **Errors.** Every outcome other than success is a tagged error, such as `AccountNotSynced` from search, `RepoNotFound` from `Db`, or `RateLimited` from the rate limiter. The router maps domain tags through an exhaustive error table. The oRPC instrumentation middleware wraps every procedure, records its span and outcome, and bounds unexpected failures. A wire error has a stable `code`, such as `ACCOUNT_NOT_SYNCED` or `SERVICE_UNAVAILABLE`, a fixed message, and the call's `traceId` in `data`. `packages/api/src/errors.ts` holds each code's status and message. A failure outside the table becomes `INTERNAL_SERVER_ERROR` with the trace ID and no detail. oRPC decodes a request body before any middleware runs, so the web Worker's handler interceptor gives a body it cannot decode `BAD_REQUEST` with the request's trace ID, and MCP's own JSON-RPC errors, such as a parse error, carry it in `error.data`. Every API response, the OpenAPI document included, also has an `x-trace-id` header. A path under `/api`, `/rpc`, or `/mcp` that matches no procedure answers `NOT_FOUND` in that transport's error shape with the trace ID, and a failure outside the API answers `INTERNAL_SERVER_ERROR` the same way.
- **Services per request.** A Hyperdrive socket cannot outlive its request, so the web Worker builds `Db`, search, and sync services for each request, and only once a procedure has validated its input. A database outage then fails a search with `SERVICE_UNAVAILABLE`, while validation, the tool list, and the OpenAPI document keep working.
- **Tracing.** The middleware opens `Api.<procedure>` under the request's `Web.<transport>` span and sets `api.transport` and `stargrep.trace_id`. No span holds the query, the plan, or results. Cloudflare's own request span and invocation log record the full URL, so search takes its query in a POST body. Each response carries a `Server-Timing` header with the handler's total time and the procedure's time, so a stage measures transport overhead apart from the work.
- **Sync.** `triggerSync` and the signed-in owner's `viewer` call claim the login's row in `sync_requests` and queue a `sync-stars` message only when the claim wins. The claim is one `insert … on conflict do update … where` statement, which takes the row only when the login has no request or its request is at least one cooldown old, so of many triggers at once exactly one queues a job. `SyncRequests` sets the cooldown per requester. Anyone waits 10 minutes, and the owner waits 1 minute, so the owner's page loads queue at most one sync a minute and a trigger from anyone still waits 10 minutes after the owner's. While a request is queued, everyone waits 10 minutes for it, because its sync may still be reading pages and an account's first sync has no stop line. The owner's minute counts from the last finished or failed sync. A login synced inside the cooldown is not queued again either, and a request older than a day is forgotten. The owner's request is a full sync when the account's last full read is a week old and no request is queued, because only a full read finds unstars. A request still waiting in line has not started reading, so it does not hold back a full read that is due. Every other request is incremental. An incremental sync of an account that has synced before and has no new stars costs two GitHub requests, the account lookup and the first star page. An account that has never synced has no stop line, so its first sync reads every star whatever the mode. A `viewer` call whose sync fails to queue still answers and logs a warning. When the queue refuses the message or the main Worker dead-letters it, the row is marked `failed`. The message carries its request time, and a dead letter marks the row only while the row still holds that request, so a late dead letter never fails a newer claim. An hourly cron in the main Worker deletes requests older than a day, so the table holds about a day of logins. `syncStatus` reads the row and the account's star sync time and says `waiting`, `queued`, `failed`, `done`, or `unknown`. The wire schema is a union keyed by `state`, so waiting always has a start and place in line, and done always has a sync time. Both procedures also return `enrichment`, the login's current stars counted as `total`, `read`, and `failed`. The router reads it by login in one query over `stars` joined to `repos`, beside the sync status. Repos are shared, so `read` can start above zero. Right after `triggerSync` the total is 0, and reading goes on after `state` leaves `queued`, so reading is finished only when `state` is not `queued` and `read + failed == total`.
- **Login check.** A signed-out request asks GitHub about the login before it claims it, with one GraphQL `repositoryOwner` request. The answer says whether the login exists, whether it is a user or an org, the account's facts, and its starred total. The web Worker has no GitHub token and no `GitHubGate` binding, so it calls `lookupOwner`, an RPC method on the main Worker's default export that the internet cannot reach, and gives up after 5 seconds. The lookup writes the account's facts and `starred_count`, and a first or full sync writes the total it counts too. `syncStatus` returns that total as `starredTotal`, so the page can show 640 of 2,431. A login GitHub does not have claims its row as `missing`, and `triggerSync` answers `LOGIN_NOT_FOUND` from that row without asking GitHub again until the 10-minute cooldown passes. An org cannot star repos, so its claim records an empty sync, starts at once, and answers `done` with a total of 0. Owners skip the lookup, because sign-in already read their account. "Admission" below gives the order of the steps.
- **Renamed logins.** GitHub lets a user rename their login, and Stargrep deletes nothing when one does. An account synced under the old login keeps answering `done` from `syncStatus` and keeps serving `stars/{old}`, because both read the account row. A trigger of the old login looks it up, finds no owner, and answers `LOGIN_NOT_FOUND`. A trigger of the new login upserts the account by its GitHub ID, which moves the row to the new login, so `stars/{new}` serves the stars and `stars/{old}` stops answering.
- **Admission.** Every sync a signed-out caller starts spends GitHub requests from the main Worker's token, so it first takes a turn in a rate line in Postgres, as "Admission" below explains. A signed-in caller's sync runs on their own token and takes no turn. `triggerSync` reads only the session for this, so a session it cannot read imports as a signed-out request.
- **Limits.** Each request works out its network once. A network is an IPv4 address, or the /64 of an IPv6 address, because one subscriber usually holds a whole /64. An IPv4-mapped IPv6 address counts as its IPv4 address, and a request without `cf-connecting-ip` is local and shares the network `unknown`. `Caller` carries the address and its key, the first 32 hex characters of an HMAC-SHA256 of the address under the stage's random `CALLER_KEY`. The address keys only the Workers rate limit bindings and is never stored or logged. Rows in Postgres hold the key.

  Four limits are exact, because they live in Postgres and hold across every Cloudflare location. The per-login claim above. The admission line. Each network's own line, the `caller/<key>` row of `rate_lines`, counted in GitHub units as "Admission" describes. And the model allowance. Every planner call and every query embedding that misses its cache takes one reservation in the network's `model/<key>` line, 30 calls a minute with a burst of 30, then one in `model/all`, 6,000 calls an hour with a burst of 600. Each reservation is one atomic upsert, so concurrent calls never share a slot. The network's line goes first, so a network past its own limit spends nothing from everyone's. A refused plan falls back to the words as typed and sets `search.plan.failure` to `ModelCallRefused`. A refused query embedding runs the typed words on full text alone and reports `fallback` too. Either way the search still answers. A meter that cannot be read refuses the call the same way, because a refusal costs only quality. `stargrep_model_calls_refused` counts refusals by call and by line, never by network. An hourly cron deletes the lines the clock has passed, because a passed line reserves the same as no row, so the table holds only the networks that asked for something recently.

  The Workers rate limit bindings are a cheap layer that turns away most of a burst before it costs anything. One `RateLimiter` service holds them: `SYNC_PER_CALLER` allows 5 syncs a minute per network and `SYNC_OVERALL` 60 for everyone, `SEARCH_PER_CALLER` 120 searches a minute per network, and `STARS_PER_CALLER` 60 pages of stars a minute per network. `search` and `stars` take theirs only when the answer cache misses. Cloudflare counts each binding per location and only approximately. In a burst test on a preview stage, 350 searches from one network got through in about 30 seconds, so these are not caps. Past a binding, the procedure answers `TOO_MANY_REQUESTS`, and a binding that fails answers `SERVICE_UNAVAILABLE`.

  In front of the Workers, prod's zone has one rate limiting rule, so most of a flood never reaches a Worker. `apps/worker/src/domain.ts` declares it, and only the `prod` stage deploys it, because previews have no zone. It counts requests to `/api`, `/rpc`, `/mcp`, and `/auth` and everything under them, per IP and Cloudflare location. Past 150 requests in 10 seconds, Cloudflare answers 429 itself for the next 10 seconds. Pages, assets, and `/icons` never count. The zone is on the Free plan, which allows one rule, a 10 second period and block, IP counting only, and path matching without regular expressions. One tab on a preview stage made about 8 limited requests per 10 seconds while importing 805 stars, and 34 in its busiest 10 seconds while typing a query at 300 ms a key during the import. That pace is just slower than the 250 ms search debounce, so every key sends a search. So 150 leaves room for a few such tabs behind one address. The deploy owns the zone's whole `http_ratelimit` phase, and Alchemy adopts the zone itself without changing it and keeps it on destroy.

MCP currently exposes only public procedures and has no OAuth sign-in. Signed-in MCP would need an authorization server and bearer-token verification before calling session-required procedures.

### Admission

`SyncRequests` in `packages/core/src/stars/sync-requests.ts` admits every sync. A unit is one GitHub request. One flow admits every requester. `policyOf` turns each kind of requester into a policy: whose token pays for the sync, which network pays for the lookup and a first read, how long a finished sync holds the login, and whether a due weekly full read runs. A requester whose own token pays never waits in the `all` line.

#### The order of a signed-out request

1. It reads the login's row and the account. A sync that finished inside the 10-minute cooldown, or a request made inside it, answers its status. A `missing` row inside it answers `LOGIN_NOT_FOUND`.
2. It reads the wait of the `all` line. A turn more than 2 hours away answers `SYNC_BUSY`, before the request costs its network anything.
3. It reserves 1 unit on its network's line, then looks the login up. A lookup GitHub refuses for a spent budget answers `SYNC_BUSY`. A lookup GitHub answered pays 1 unit into the `all` line, forced, because the request is spent whatever comes of the sync.
4. It claims the row with the outcome already known. A missing login claims `missing`. An org claims and records an empty sync. A user claims `claimed`, takes its turn in the `all` line, sends its message, and moves the row to `pending` with `starts_at`. A turn the `all` line refuses releases the claim and answers `SYNC_BUSY`.

Anything that stops a request after its claim and before it sends its message, whether a refusal, a failed query, or an interruption, releases the row, or marks it `failed` when the queue refused the message, and releases every charge made after the claim. An interruption during the send waits for it to finish, so once the send starts only the queue's refusal undoes the claim. A request that loses the claim answers from the winner's row, so every trigger for a missing login answers `LOGIN_NOT_FOUND`. No request waits on another's lookup. Requests for one login at once each pay a lookup, and the network's line bounds that cost. A `claimed` row reads as `queued`, because its message goes out next. One narrow window answers `queued` with no job behind it: a trigger that reads a claim whose turn the `all` line then refuses. The request checked the line's wait just before its claim, so a refusal there means the line filled within that moment. The message goes out before the row moves to `pending`, so a crash in between leaves a `claimed` row that reads as `queued` while its job waits in the queue.

The owner skips the lookup and the network line, never waits, and reserves nothing in the `all` line, because their sync runs on their own token. A held row answers its status. The owner's claim takes over a request still waiting in line, and its sync is a full read when one is due. So a visitor who signs in from "is this you? skip the wait" gets their sync queued at once, on their token.

A signed-in request for another login follows the signed-out order without the `all` line. It skips the line's wait, keeps its network's charges for the lookup and a first read, and starts now. Like the owner's, its claim takes over a signed-out request it read as waiting in line, and that takeover charges no first read, which the waiting request's network already paid. A signed-out request that claims the login while a signed-in request looks it up wins, and the signed-in request answers from its row. The lookup still runs on the server's token and pays its unit into the `all` line.

#### The lines

`rate_lines` keeps each line as one time, `busy_until`, the generic cell rate algorithm with weighted cells. `packages/core/src/limits/rate-line.ts` names every line and holds its rate: the units it pays out per period, its burst, and how long a reservation may wait. A line's burst is how many one-unit reservations start at once when it is clear, so a reservation starts once the line owes at most its burst less one unit. A heavier reservation starts on the same terms and can leave the line owing more than its burst. It is one `insert … on conflict do update … where` statement, so concurrent reservations queue on the row lock and never get the same start. A forced reservation never refuses, for work that pays into a line but never waits. A bill moves a line by a signed number of units, and never earlier than now. A reservation returns a receipt with the time by which the line has paid out its cost, and a release gives back only the part of that cost still due when the release runs. So a release that lands late, such as a queue refusal after its charge has drained, never credits work reserved after it. Each line also keeps a running total of the time given back from it, by releases and by bills below zero. A release takes everything given back since its reservation as having been ahead of it, so time given back behind it makes the release smaller, never larger. The prune deletes a line only once it has paid out every reservation on it, and a recreated line is a new generation, so a receipt from the deleted one releases nothing into it. An hourly cron in the main Worker deletes the lines the clock has passed, which reserve the same as no row.

- **The `all` line.** It holds every signed-out sync. `githubAll` pays out 80% of `GITHUB_BUDGET_SHARE` of the token's 5,000 REST requests an hour, 3,600 units on the App's share of 0.9 and 2,000 on a personal token's 0.5, with a burst of 200. Both Workers bind the same share. The other 20% of the share is left to enrichment. A signed-in user's sync pays into the `all` line only for the requests that fell back to the server's token, after it runs, and never waits in it. Enrichment never pays into the `all` line, on either token. Its requests on the server's token, a user's fallbacks included, come out of the 20% left to enrichment. Lookups and counts spend GitHub's separate GraphQL window, so counting them as units overcounts on purpose.
- **A network's line.** `githubNetwork` pays out 150 units an hour with a burst of 150, and a reservation there never waits. Every signed-out lookup takes 1 unit, so a network that owes its burst gets `TOO_MANY_REQUESTS` before any lookup or claim. A login that never synced also puts its first read on its network, after the lookup prices it. That charge is refused once the network already owes its burst, so a network starts one huge import at a time, and a 100,000-star import holds its network for about 6 hours. A first read goes back to the network when anything stops the request before its message goes out, such as a turn the `all` line refuses. "Limits" says how the network key is made.

#### The cost model

`costOf` prices a sync before it runs, and its test lists sample prices. A first or full read costs the account read, two GraphQL counts, and one request per page of 100 stars, 28 units for 2,431 stars. An incremental read stops at the first star older than the newest one stored, so it costs the account read and the pages that hold the stars added since, 2 units when nothing is new. Admission prices a sync from the lookup's starred total. The price is an estimate. Stars removed or starred again since the last full read, stars swapped at an unchanged total, and a stale `starred_count` all move it, so each sync reconciles after it runs.

#### Reconciliation

The `sync-stars` message carries `reserved`, the units admission put in the `all` line for the sync's own requests, without the lookup. A signed-in user's message reserves 0. The consumer runs each message over `TokenGate.counting` on the server's gate, which counts each request sent on the server's token, the GitHub client's retries and failed requests included. A request on the user's token is not counted. After each delivery, whether it succeeded or failed, the consumer hands the count to `SyncRequests.billDelivery`, which bills the `all` line:

- A first delivery moves the line by the count minus `reserved`. It bills what the sync spent past its reservation and gives back what it did not use.
- A later delivery bills its whole count.
- A deferred message goes out again without `reserved`, which `SyncRequests.resent` strips, because its first delivery already settled it.
- A message without `reserved`, such as one from the debug Worker, bills its whole count.

So a dead-lettered message is already settled. A message the queue refuses at admission gives its reservation and its network's first read back at once. A reconciliation that fails to write is logged, and the message still settles, because a retry would read GitHub again. `GitHubGate`'s share stays the hard cap.

#### Waiting

A request records `starts_at` when its message is sent, set to now or to the start of its turn. When the turn starts later than now, the message goes out at once with `delaySeconds` set to the wait. `syncStatus` says `waiting`, with `startsAt` and how many waiting syncs start before it, and turns `queued` at `startsAt`. The claim's cooldown counts from `starts_at`, so a waiting login is not claimed again, except by its owner. The waiting message still runs after the owner's sync, which costs one more incremental sync. A request that is queued and no longer waiting holds the owner for its 10 minutes, as "Sync" says.

`stargrep_sync_admissions` counts each decision: `started`, `waiting`, `deduped`, `org`, `not-found`, `caller-limit`, `line-full`, `github-budget`, and `lookup-failed`. The `SyncRequests.request` span carries the decision, the cost, and the wait.

## Caching

| Layer | What it caches |
|---|---|
| Browser | The user's library in TanStack DB |
| Workers cache | Demo search answers and first rendered answers, fresh for 5 minutes and served stale for up to a day during refresh. Public `stars` pages for 10 seconds |
| KV | Query plans and query embeddings, through the `SearchCache` port |
| Postgres | Summaries and embeddings, shared across accounts |
| R2 | README text by object ID, so GitHub serves each README once |
| R2 and the Workers cache | Repo icons as WebP, keyed by output version plus the git blob ID or the SHA-256 of the source bytes. The web Worker serves them at `/icons/<key>` on its own origin, through `caches.default`, with `immutable` caching. A change to the normalized output, or to what the normalizer rejects, bumps the version, so an icon URL never shows other bytes and a re-check never reuses an icon the new rules reject. The icon backfill counts a row whose key has another version as due, and every version stays servable until that row's next check |

The landing page answers the demo account's default query at first paint, and its server render calls `search` in the same Worker over `/rpc`. The web Worker keeps the first answer it renders beside the demo's search answers, under the same windows, and never when the planner fell back. Its key names the library revision, the sync time and read counts from `syncStatus`, so a completed sync or a newly read star answers again, and a per-build ID, so a deploy never serves a view an older page model built. Its freshness runs from when the API stored the search answer it holds, which the API sends as `x-answer-stored-at`, so an answer the API served stale is never kept as fresh. A render on a hit reads the sync and the cache, and the page answers with `x-answer-cache` and `server-timing` too. The browser asks for the semantic answer again once its library settles on another revision. So the answer cache lives in the API package, not in front of HTTP GETs, and every transport gets it. `packages/api/src/answer-cache.ts` owns the policy: how long an answer stays fresh, the refresh, the `x-answer-cache` header, and the `stargrep_answer_cache` metric. The `AnswerCache` port only stores. `search` keeps answers only for the demo login, compared without case, in the `stars` scope, keyed by login, scope, limit, and the query trimmed, collapsed, and lowercased as the plan cache keys it. A hit builds no database, search, or model service. An answer older than 5 minutes is still served for up to a day while a refresh runs through the request's `background`. The web Worker runs it under `waitUntil` from `cloudflare:workers` with a freshly built request layer, because the request's own services close with its response, and gives up after 25 seconds. A stale answer starts at most one refresh per key per isolate every 5 minutes, however the refresh ends. An answer the planner could not plan, `planSource: "fallback"`, is never kept, so after such a refresh the stale answer stays and the next refresh waits 5 minutes. `stars` reads and caches pages of 100 stars for any limit up to 100 and pages of 1,000 above it, keyed by login, page size, and cursor, and answers the first `limit` repos with `nextCursor` at the last one it answered. So a client cannot miss the cache by asking for another limit. `caches.default` holds the answers under the request's origin, because result icons carry absolute URLs, and under a version made of the planner model, `PlannerPrompt.version`, and the embedding model, so a deploy that changes any of them starts cold. A cached answer never takes from the caller's rate limit. Each cached procedure answers with `x-answer-cache: hit`, `stale`, or `miss`, and `stargrep_answer_cache` counts them. `config` answers with `cache-control: public, max-age=300` and `stars` with `public, max-age=10`. A shared link with any other query paints without a search. The server paints its `?q=` keyword matches from a library an import has written, and the browser asks for the search by meaning through the API, so a shared link with a custom query spends no model work during server rendering. The demo default query can call search on a cache miss. The server also looks up the repo its `?repo=` opens, so the panel opens as the page hydrates.

## Everything as code

The repo is the source of truth. Each concern has one file or folder that defines it.

| Concern | Source of truth |
|---|---|
| Workers, bindings, queues, crons, routes, DNS | The Alchemy program. Each resource is declared in the module that binds it, such as `apps/worker/src`, and `infra/` holds the stacks, providers, state, and which Workers each stage deploys. Each pull request deploys to its own stage |
| Neon projects and branches | `infra/database.run.ts` owns the projects. Each stage's branch is declared with the Hyperdrive that binds it, in `apps/worker/src/database.ts`, which also decides that `prod` keeps its branch on destroy and that preview branches expire |
| Database schema | Drizzle schema in `packages/db`, with migrations generated by `drizzle-kit`. Each stage's Neon branch applies them before its Worker deploys |
| API, REST, and MCP | oRPC contracts in `packages/api`. The OpenAPI spec and MCP tool list are generated from them |
| Environment variables | `packages/runtime/src/stage.ts` derives stage settings. Entry-point Effect `Config` definitions validate bindings and secrets |
| Models and prompts | `packages/ai` |
| Repo knowledge | `packages/knowledge/src/registry.ts` defines the dimensions, closed values, and roles. It generates `registry.sql` and the facets block the summary prompt will carry, and tests fail when a copy drifts. `docs/knowledge.md` explains the model |
| Search metrics | `packages/core/src/search/metric-registry.ts` names each metric for the planner, and `packages/db/src/queries/search.ts` maps its family to `repo_metrics` columns. Both use `MetricFamily`, so the compiler keeps `MetricFamily`, `metricColumns`, and `nouns` in step |
| Search quality | The query set and its expected results in the repo. CI runs the recorded recall fixture without model calls |
| GitHub App | Its manifest in the repo. Creating the app from it takes one click in the browser |
| Design tokens | `packages/ui` |
| CI and deploys | GitHub Actions workflows. Only CI deploys to production |

A deploy applies each migration in one transaction and sends each chunk between `--> statement-breakpoint` markers to Neon as its own round trip, a chunk of comments alone included, so a lock on a table the running Workers use lasts until the commit. From `20261107193409_knowledge` on, a migration locks a table that existed before it only in its last statement, which can be a `DO` block holding several commands. `knowledge-migration.test.ts` checks it. It splits each file with Alchemy's own `splitSqlStatements` and treats every `public` table that existed before the migration as one the Workers may use, so a table the migration creates may be locked anywhere. On a branch of prod, that migration held `repos` for 3 round trips, 645 ms from a laptop about 200 ms from Neon.

Some things stay outside the repo. Secret values live in Cloudflare secrets and GitHub Actions environment secrets, and the repo holds only their names. Only jobs on `main` can read the `production` environment's secrets. Previews read separate credentials from the `preview` environment. Account creation, billing plans, and domain registration are one-time manual steps, listed in `docs/setup.md`.

### Stages

The Alchemy program has two stacks, so no app stage's state holds a Neon project. `infra/database.run.ts` owns the projects in its only stage, `shared`. `infra/alchemy.run.ts` is the app stack, deployed once per stage: `pr-<number>` for each pull request and `prod` for `main`. Each app stage references one project and owns one branch of it, so destroying a stage deletes its branch and never the project. `prod` uses `stargrep-us-east`, and every preview stage uses `stargrep-previews-us-east`, both in `aws-us-east-1`, so a Neon key scoped to the previews project can't reach prod's branch. Only the deploy from `main` deploys `shared`. A pull request stage fails with a missing reference until `main` has deployed once.

`prod` deploys only the Worker, its database, the queues, R2 bucket, and Durable Object the pipeline needs, and the web Worker with its KV namespace. It serves on `stargrep.com`, and `www.stargrep.com` redirects there. The Worker holds the custom domain, and a zone route sends every path to the web Worker, because routes take precedence over custom domains. The web Worker passes `/health`, with any query string, to the Worker through a service binding, so the health check still reads the Worker's database connection. Cloudflare matches route patterns against the query string too, so a `/health` route would miss `/health?x=1`. Prod has no workers.dev URLs, so every request passes the zone's rules. Every other stage serves only on its workers.dev URLs and also deploys a debug Worker with a queue and consumer, KV, R2, two Durable Objects, and an hourly cron, so the checks in `docs/setup.md` can drive them. Its routes take a bearer token that the stack generates per stage, and a Durable Object caps them at 300 units of work a minute.

Previews pay for no model calls. `stageSettings` gives each `pr-<number>` stage the provider `fake`, and prod and local stages the gateway. `withStageAi` in `packages/runtime/src/ai-key.ts` wraps the config the whole app stack reads. So a stage on the fakes never binds `AI_GATEWAY_API_KEY`, even when its deploy has one, and its Workers bind `STARGREP_AI_PROVIDER=fake`. A deploy with `STARGREP_AI_PROVIDER=gateway` opts a preview in, and the preview workflow sets it while the pull request has the `preview-ai` label, read from GitHub right before each deploy. Prod hides that variable, so its bindings stay the same whatever the deploy's environment holds. The stand-ins cost nothing, so opening a preview imports the demo account's real stars, and that import is how a preview gets real-looking data. A branch keeps the embedding model its first request recorded, so a preview picks its provider when it is created and keeps it. Every non-prod stage's output records `aiProvider`, and when the labels ask for another provider, the preview workflow destroys the stage and deploys it fresh. A preview therefore never holds more than one branch, and no request from one provider's Workers reaches the other provider's database.

Deployed stages keep Alchemy state in the Cloudflare account through `Cloudflare.state()`. Under `alchemy dev`, state stays in `infra/.alchemy/` and the stage declares no Neon resources, so a local stage needs no credentials.

## Testing

- `packages/core` tests use `bun test` with in-memory layers. They cover behavior, such as "an unstarred repo gets `unstarred_at`", not internal calls. Time runs on `TestClock`, so tests never sleep. `packages/testing` provides `it.effect`, `it.live`, and `it.layer` for Bun Effect tests. Transport and runtime tests also run Effects at their framework boundaries. Typed database fixtures live under `@stargrep/db/testing`. `docs/effect.md` section 7 shows how to use it.
- `packages/db` runs each query test twice, on PGlite and on Postgres 17 with pgvector through `pg`. The `pg` run creates and migrates a database for each test file in the local container from the root `compose.yaml`, and CI starts the same container. The PGlite run starts each database from a migrated data directory that the first test process builds and keeps in the temp directory, keyed by the PGlite and pgvector versions and the migration files, because initdb takes seconds on a busy machine.
- `apps/web` and `apps/worker` tests run on workerd through `@cloudflare/vitest-plugin`. Both apps set `testTimeout` to 30 seconds to allow for workerd module loading. Workerd test files are named `*.workerd-test.ts`, which `bun test` never matches from any folder, and the vitest config includes only that pattern. `bunfig.toml` ignores `repos/`, so a root `bun test` runs the other `*.test.ts` and `*.test.tsx` files in the repo.
- The worker test command also runs `vitest.runtime.config.ts`. It bundles the real Worker through Alchemy and exercises its bindings, queues, Durable Objects, and per-invocation database layers on workerd with a separate migrated Postgres database.
- Web polling and reveal programs use `TestClock` in Bun tests, with separate DOM integration tests.
- `bun test` runs with `--parallel`, not `--concurrent`, so a test that times out still interrupts its fiber and runs its finalizers.

## Settled by prototypes

These ran locally on 2026-11-03, with no cloud account.

- **Alchemy 2.0 beta covers every resource Stargrep uses.** Under `alchemy dev` with Bun, one local stage ran a Worker with a queue producer and consumer, a Durable Object, KV, R2, a cron, a Workflow, and Hyperdrive to a local Postgres. Neon projects, branches, roles, and connection strings and GitHub secrets exist in its source. State needs an explicit store. Stargrep uses `Cloudflare.state()`, so CI needs only a Cloudflare token.
- **TanStack Start, oRPC 2.0 beta, and Effect run together on workerd.** One procedure with an Effect Schema input and an Effect handler answered over RPC, REST, and MCP, and the OpenAPI spec generated. The client bundle stayed free of Effect with type-only contract imports. One runtime import of the contract added about 27 KB gzipped, so a lint rule enforces type-only imports. Every `@orpc/*` package pins `2.0.0-beta.48`, because npm's `latest` tags mix 1.x and different betas.
- **`drizzle-orm/effect-postgres` works on workerd with `prepare: false`, and Stargrep does not adopt it.** With default prepared statements, 68 of 360 transactions failed behind a transaction-mode pooler. Better Auth's adapter fails on it. `pg` measured no slower and serves both core and auth.
- **`drizzle-kit` does not emit `CREATE EXTENSION vector`.** The first migration adds it by hand.
- **The `bun test` helper works.** It lives in `packages/testing`, and its tests cover what the prototype checked.
